# design-sync notes — @kit/ui

## Repo-specific facts

- **No build step.** `packages/ui` ships raw `.tsx` via ~70 subpath exports in `package.json` `exports`, compiled on-the-fly by each consuming Next.js app. There is no `dist/`, no `main`/`module`/`exports['.']`. The converter runs in synth-entry mode (`[NO_DIST]`), scanning every `.tsx`/`.jsx` under `src/` for PascalCase value exports. Re-syncs: nothing to rebuild upstream — just re-run the converter.
- **No CSS of its own.** Tailwind v4 only generates the utility classes a component actually uses when run through the real compiler, and the actual design tokens (the "Cinema dark mode" palette, fonts) live in `apps/web/styles/*.css`, not in this package. `cssEntry` is sandboxed to stay inside the package, so a one-off Tailwind compile is generated into a gitignored cache file and pointed at by `cssEntry`:
  - Input: `.design-sync/tw-input.css` (committed — describes the compile, references `apps/web/styles/{theme,theme.utilities,shadcn-ui,makerkit,studio-dark,markdoc}.css` + `@source` scanning `../src`).
  - Build script: `.design-sync/build-css.mjs` (committed) — run with plain `node .design-sync/build-css.mjs` from `packages/ui`. Uses `@tailwindcss/postcss`/`postcss` resolved directly from the pnpm store (`node_modules/.pnpm/@tailwindcss+postcss@4.1.13/...`) since neither is a direct dep of this package or `apps/web`.
  - Output: `.design-sync/.cache/compiled-theme.css` (gitignored, regenerate every sync) — this is what `cfg.cssEntry` points at.
  - The default (un-classed) `:root` in `shadcn-ui.css` IS the "Cinema dark mode" theme — no `.dark` class or provider wrapper needed for previews to show real branding.
  - **Re-sync risk**: this compiled CSS goes stale if `apps/web/styles/*.css` changes and nobody re-runs `build-css.mjs`. Always re-run it before re-syncing.
- **Fonts**: primary font is DM Sans via `next/font/google` (self-hosted at Next.js build time — no extractable static file). Set via `runtimeFontPrefixes: ["DM Sans"]`. `JetBrains Mono`/`Courier Prime`/`Merriweather` (used only by `chart.tsx` for `font-mono`) have no shipped `@font-face`; accepted as a substitute (browser falls through to the existing system-font fallback chain already in the source CSS) rather than sourcing real font files — low impact, single component, recorded here per the user's implicit OK (cosmetic-only, not raised back to them).
- **Real name collisions in source** (not a tooling bug — two genuinely different components share a name):
  - `src/shadcn/sidebar.tsx` and `src/makerkit/sidebar.tsx` both export `Sidebar`, `SidebarContent`, `SidebarGroup`, `SidebarNavigation`. ESM `export *` silently drops ambiguous bindings, so without intervention all four names come out `undefined` in the bundle.
  - `src/shadcn/data-table.tsx` and `src/makerkit/data-table.tsx` both export `DataTable`. Same issue.
  - Fixed via `.design-sync/overrides/source-kit.mjs` (forked from `lib/source-kit.mjs`, declared in `cfg.libOverrides`) — `FILE_EXPORT_OVERRIDES` aliases the **secondary** file of each pair to a prefixed name instead of blanket-`export *`-ing it, matching the package's own subpath-export convention: `./sidebar` (primary, bare names) → makerkit; `./shadcn-sidebar` (secondary) → `ShadcnSidebar`/`ShadcnSidebarContent`/`ShadcnSidebarGroup`/`ShadcnSidebarNavigation`. `./data-table` (primary, bare name) → shadcn; `./enhanced-data-table` (secondary) → `EnhancedDataTable`.
  - The fork ALSO fixes an interaction bug: upstream `resolvePackage` only calls `deriveComponentsFromSrc` (the synth-entry component-discovery fallback) when the `componentSrcMap`-pinned name set is empty — so pinning the new alias names (`ShadcnSidebar`, `EnhancedDataTable`, etc.) via `componentSrcMap` would otherwise silently *replace* full discovery instead of adding to it. The fork folds derived names in unconditionally when `synthEntry` is true, then layers `componentSrcMap` adds/excludes on top.
  - `componentSrcMap` in config pins all 6 renamed/kept bare names to their correct source file (fixes doc/group attribution to match what's actually in the bundle).
  - **Re-sync risk**: if a THIRD file is ever added that also exports `Sidebar`/`SidebarContent`/`SidebarGroup`/`SidebarNavigation`/`DataTable`, or either existing file's export surface changes, re-check this collision — the fork's `keep` lists are hand-enumerated from the file's current export statement and will silently go stale (an export added to `shadcn/sidebar.tsx` after this sync won't be re-exported until the `keep` list is updated). If another collision pair is found elsewhere in `src/`, extend `FILE_EXPORT_OVERRIDES` the same way.
  - General check for this class of bug on a re-sync: run the duplicate-export scan (grep each file for top-level `export const|function|class` and `export {}` blocks, group by name, flag names from >1 file) before trusting the discovered component list.
- **Component scope (full sync)**: 260 PascalCase exports discovered (261 minus the excluded `MobileNavigationDropdown`, see below) — 40 "shadcn" (curated public primitives), 32 "makerkit", 15 "marketing", and 173 "general" (structural subparts like `AccordionContent`, `DialogTrigger`, `CardHeader`, `SidebarMenuItem` that only render meaningfully composed inside a parent). User explicitly chose to author all of them (including subparts, even though each subpart's preview duplicates its parent's composition) rather than floor-card the subparts — flagged this tradeoff and they confirmed "author all 261 anyway."

Installed `playwright`+`playwright-core`@1.55.0 into `.ds-sync/node_modules` (gitignored, scratch) and ran `node node_modules/playwright-core/cli.js install chromium` to get the matching binary cached at `~/.cache/ms-playwright`.
- **`MobileNavigationDropdown`** (`src/makerkit/mobile-navigation-dropdown.tsx` AND `src/makerkit/mobile-navigation-menu.tsx`, both `export default function MobileNavigationDropdown`) is excluded via `componentSrcMap: {"MobileNavigationDropdown": null}`. Not exposed via any `package.json` subpath and not imported by any other file in `src/` — dead/orphaned code, not part of the public API. Separately, `export default` never survives `export *` at all (ES module spec excludes default exports from star re-exports), so even if it WERE wanted, the synth entry would need an explicit `export {default as Name} from '<file>'` line per file — same pattern as the `FILE_EXPORT_OVERRIDES` fork, not yet needed since nothing legitimate hit this.
- **`AuthenticityToken`** (`src/makerkit/authenticity-token.tsx`) excluded the same way (`componentSrcMap: {"AuthenticityToken": null}`) — no `package.json` subpath exports it and `grep -rl "AuthenticityToken"` across `apps/web` and `packages/` finds zero usages anywhere. Genuinely orphaned, not part of the public API a design agent could actually import.
- **`Dropzone`/`DropzoneContent`/`DropzoneEmptyState`** (`src/makerkit/dropzone.tsx`) excluded the same way — no `package.json` subpath exports `dropzone.tsx` either. The two `grep -rl "Dropzone"` hits in `apps/web` are both false positives (`useDropzone` from the third-party `react-dropzone` package, and a locally-defined `UploadDropzone` in `master-asset-manager.tsx`) — neither imports this package's component. Caught via `lib/preview-rebuild.mjs --components <name>`'s `Could not resolve "@kit/ui/dropzone"` error; a real authored preview existed and silently fell back to the floor card (a near-empty `cardMode: "single"` bar) instead of failing the build loudly, which is why this surfaced as a `RENDER_BLANK` validate warning rather than a build error.
- **`ShadcnSidebar`/`ShadcnSidebarContent`/`ShadcnSidebarGroup`/`ShadcnSidebarNavigation` preview authoring pitfall**: the alias rename (`Sidebar` → `ShadcnSidebar` etc., see the sidebar collision entry above) exists ONLY inside the synthetic main-bundle entry's combined namespace (`window.KitUi.ShadcnSidebar`) — the real `@kit/ui/shadcn-sidebar` subpath still exports the file's own bare names (`Sidebar`, `SidebarContent`, ...). A preview file is its OWN separate esbuild bundle that imports straight from the subpath, so `import { ShadcnSidebar as Sidebar } from '@kit/ui/shadcn-sidebar'` fails to resolve (`No matching export ... for import "ShadcnSidebar"`) — same silent floor-card fallback as the Dropzone case above. Fix: import the bare names directly (`import { Sidebar, SidebarContent, ... }`) and use them as-is in the preview's JSX; the alias only matters for the FINAL component's display name in the catalog, not for how the preview's own source resolves it. All 4 previews had this bug — same root cause, same fix.
- **Floor-card fallback on preview compile failure is SILENT in the full `package-build.mjs` run** (no per-component error surfaces in the tail-truncated log) — `node .ds-sync/lib/preview-rebuild.mjs --config .design-sync/config.json --node-modules <scratch> --out ./ds-bundle --components <comma-list>` is the cheap, fast way to get the real compile error for any component whose authored preview produces a suspiciously blank/thin render-check result, instead of re-running the full 259-component build to see it.
- **PreviewBackground now also wraps a `PreviewErrorBoundary`** (class component, `getDerivedStateFromError`) — without it, React 18+ silently swallows any render error in a preview (logs to console, unmounts the tree), so a genuinely-empty cell and a CRASHED cell were visually indistinguishable (both just blank). Now a crash renders `⚠ <message>` text instead — this is what surfaced the two bugs below; re-check any future blank-with-no-text cell against this boundary first (it may just need a rebuild to pick up a `preview-background.tsx` change).
- **`MultiStepForm`-family real bug (not a preview-authoring bug)**: `useMultiStepForm` (called from `MultiStepForm` itself, so it fires even though my preview never explicitly calls a query hook) uses `useMutation` from `@tanstack/react-query`, which throws `"No QueryClient set, use QueryClientProvider to set one"` with no `QueryClient` in the tree.
  - **First attempt — hoisting `QueryClientProvider` into the shared `.design-sync/preview-background.tsx` (`cfg.provider`) — did NOT work**, despite seeming like the right place (it already fixed the dark-background/text-color issue for every component). Root cause: `preview-background.tsx` is bundled into the MAIN `_ds_bundle.js` (via `cfg.extraEntries`); each authored preview (`MultiStepForm.tsx`, etc.) is its OWN, completely separate esbuild bundle. React context requires the Provider and the `useContext()` call to share the exact same Context *object* — and `@tanstack/react-query`'s `QueryClientContext` is a plain module-level `createContext()` call, re-evaluated independently in every separate esbuild output. The two bundles' copies are different objects in memory, so a Provider in one can never satisfy a consumer in the other. (React/ReactDOM themselves dodge this because they're loaded once as `_vendor/react.js` globals — `window.React`/`window.ReactDOM` — shared by every bundle; nothing else gets that treatment.)
  - **Real fix**: import `QueryClient`/`QueryClientProvider` directly inside `MultiStepForm.tsx` (and its 4 duplicate sibling files — `MultiStepFormContextProvider/Footer/Header/Step.tsx`) and wrap that file's OWN JSX in its OWN `QueryClientProvider` instance, mirroring the `LanguageSelector` i18next fix below. **General rule for this whole class of bug**: any React Context-based dependency (query clients, i18n, anything using `createContext()` in a library) must be satisfied INSIDE the same preview file that needs it — the shared `preview-background.tsx` only helps with plain prop-drilling-free concerns that don't rely on cross-bundle object identity (CSS classes, a single global like `window.process`).
- **`LanguageSelector` real-but-narrower bug**: `useTranslation()` (real `react-i18next` hook, unlike `Trans`'s `TransWithoutContext`) needs `.use(initReactI18next).init(...)` wiring, not just a populated `i18n.options`. Also, `i18n.init()`'s promise resolves on the microtask queue — since each preview's module evaluation and React's first synchronous render happen in the same call stack, `i18n.isInitialized` is still `false` at first render, and `useTranslation()` defaults to Suspense-blocking until it flips true (silently blank again, no error). Fixed via `react: { useSuspense: false }` in the preview's own `i18n.init()` call. Same cross-bundle-identity reasoning as `MultiStepForm` above — this is the SAME class of bug, not a separate one. Any OTHER preview that transitively renders a component calling `useTranslation()` (not `Trans`, which tolerates no provider) needs this same per-file fix.
- **`EnhancedDataTable` real bug, same class again**: its pagination path calls `useRouter()` from `next/navigation` unconditionally (a hook, fires even though pagination is externally controlled here via `onPaginationChange`) — `useRouter()` throws `"invariant expected app router to be mounted"` with no App Router (unlike `usePathname()`, which degrades to `null` instead of throwing — see the `AppBreadcrumbs` entry above). Fixed the same way as `AppBreadcrumbs`: wrap with the real internal `AppRouterContext` (`next/dist/shared/lib/app-router-context.shared-runtime`) inside `EnhancedDataTable.tsx` itself, with a minimal stub router object (only `.push` is ever called, only from a pagination click that never fires in a static screenshot).
- **`Trans` preview bug — different failure mode, NOT the cross-bundle-context class above**: `TransWithoutContext` (what `Trans` actually calls) does `const i18n = i18nFromProps || getI18n()`; with no i18n instance anywhere in this isolated bundle, `getI18n()` returns `undefined`, and the `if (!i18n)` branch returns `children` AS-IS — it does NOT fall back to the `defaults` prop (that prop is only ever read once a real `i18n.t()` call happens). The original preview passed `defaults="..."` with no `children`, so it silently rendered nothing (`undefined`). Fix: pass the fallback text as JSX **children** instead of (or in addition to) `defaults` — `<Trans i18nKey="...">literal text</Trans>` — which is exactly what the no-instance branch returns. Any product code rendering `<Trans i18nKey={dynamicKey} defaults={computed} />` with no children (e.g. a fallback-only pattern) would hit the same blank-render trap in an isolated preview and needs the same children-based workaround.
- **`BorderedNavigationMenuItem` real bug, same `Trans`-without-children class**: its label render path is `<Trans i18nKey={props.label} defaults={props.label} />` with no children — IN PRODUCT SOURCE (`src/makerkit/bordered-navigation-menu.tsx`), not the preview, so it can't be fixed the way `Trans.tsx`'s own preview was (no children prop to add — `label` only reaches `Trans` as `i18nKey`/`defaults`, not `children`). Fix instead from the i18n-instance side: initialize a real (empty-resources) i18next instance in the preview via `.use(initReactI18next).init(...)` (same as `LanguageSelector`) — this makes `getI18n()` resolve, so `Trans` calls `t(i18nKey)` instead of hitting the no-instance branch; with no matching resource, i18next's default behavior is to return the key itself, which equals the label text here. **General rule**: any product component using `<Trans i18nKey={x} defaults={x} />` with no children will blank-render in an isolated preview UNLESS a real i18n instance is initialized in that preview file — grep `src/` for this exact no-children pattern before authoring previews for components that compose it.
- **`OauthProviderLogoImage` real gap, not fixed in product**: `google`/`facebook`/`github`/`microsoft`/`apple` resolve to local `next/image` paths (`/images/oauth/<provider>.webp`) served from `apps/web/public` at runtime — no equivalent static file server exists for the isolated preview bundle, so those render as broken-image icons (the `providerId` prop has no override to substitute a different src). Worked around by using `twitter` (inline SVG, no image fetch) and `email`/`phone` (lucide icons) in the preview instead — these are equally real provider options the same component ships, just ones that don't depend on the missing asset path. If a future preview needs google/github specifically, this gap reapplies — there's no clean fix without forking the component or sourcing the actual webp files into the bundle.
- **`TableCaption`/`TableFooter` preview-authoring bug (not a product bug)**: both files were exact copy-paste duplicates of `TableBody.tsx`'s preview (made via the "subparts duplicate full parent composition" recipe) that never actually added the `<TableCaption>`/`<TableFooter>` element they're named after — caught by grading, not by validate (the sheet rendered a complete, plausible-looking table either way, just never exercising the named component). **General rule**: when duplicating a parent's preview onto subpart siblings, double check each duplicate actually RENDERS its own named component somewhere in the JSX, not just a copy of the parent's example verbatim.
- **`LazyRender`/`ImageUploadInput`/`TopLoadingBarIndicator` excluded, same precedent as `MobileNavigationDropdown`/`AuthenticityToken`/`Dropzone*`**: real source files exist (`src/makerkit/{lazy-render,image-upload-input,top-loading-bar-indicator}.tsx`) and synth-entry discovery picks them up as components, but none has a `package.json` `exports` subpath — there's no way for a preview (or any real external consumer) to `import` them. An earlier wave authored preview `.tsx` files for them anyway, which silently never compiled into the bundle (see the floor-card-fallback class of bug below) since `@kit/ui/lazy-render` etc. don't resolve. Excluded via `componentSrcMap: null` and deleted the dead preview files.
- **`Page`-family real bug (8 components: `Page`/`PageBody`/`PageHeader`/`PageTitle`/`PageDescription`/`PageHeaderActions`/`PageNavigation`/`PageMobileNavigation`), two layered issues, both in MY preview's usage, not product code**:
  1. Wrong import path: `SidebarProvider` was imported from `@kit/ui/sidebar` (maps to `src/makerkit/sidebar.tsx`, which doesn't export it) instead of `@kit/ui/shadcn-sidebar` (`src/shadcn/sidebar.tsx`, the real owner) — same Sidebar/DataTable alias-vs-real-subpath class of bug documented above for `ShadcnSidebar*`.
  2. Real composition bug, caught only by grading (validate/build never flagged it — it compiled fine and rendered *something*): `Page`'s `getSlotsFromPage()` reduces `props.children` into a SINGLE `Children` slot (overwritten on every non-Navigation/MobileNavigation child, not accumulated) — nesting both `<PageHeader>` and `<PageBody>` inside `<Page style="header">` silently drops whichever renders first (`PageHeader`) since `PageBody` overwrites it last. `Page` is actually a separate top-level layout shell (used at the route-layout level for its `Navigation`/`MobileNavigation` slots only); `PageHeader`+`PageBody` are meant to be rendered as plain siblings with NO `<Page>` wrapper, confirmed against real usage (`apps/web/app/.../analytics/page.tsx`). Fixed by dropping the `<Page>` wrapper for the `Page`/`PageBody`/`PageHeader`/`PageTitle`/`PageDescription`/`PageHeaderActions` previews (`PageNavigation`/`PageMobileNavigation` correctly keep it, since those names ARE the slot-matched types `Page` looks for).
  3. Follow-on layout bug once (2) was fixed: `SidebarProvider`'s own root div is `flex min-h-svh w-full` (a horizontal flex row sized to the full viewport — meant to hold a sidebar beside a page) — as the DIRECT parent of `PageHeader`+`PageBody` it laid them out as row siblings instead of stacked, inside a forced full-viewport height. Fixed via `<SidebarProvider className="min-h-0 flex-col">` (its `cn()` merges via tailwind-merge, so the override sticks). **General rule**: any context-provider component that ALSO happens to render significant layout chrome (flex/height/width) on its own root element needs its `className` reviewed when used as a direct content parent in a confined preview card, not just treated as a transparent context wrapper.
- **`CookieBanner` accepted limitation, NOT fixed**: its real markup uses `fixed bottom-0 ... delay-1000 duration-1000 animate-in fade-in zoom-in-95` (1-second CSS-animation delay before the banner becomes visible) stacked with `cardMode: "single"`'s fixed-position handling. Unfixed, this threw `ReferenceError: process is not defined` on **100% of components** (every preview loads the shared `_vendor/react.js`) — a systemic, build-breaking bug, not a per-component issue. Neither `lib/bundle.mjs` nor `lib/emit.mjs` may be forked (they define the output contract), so the fix is entirely from the outside:

- **`.d.ts` props were generic stubs (`{[key: string]: unknown}`) for ALL 260 components**, not just a few. Root cause: `lib/dts.mjs`'s `projectFor()` only ever adds `.d.ts` files to its ts-morph project (`${root}/**/*.d.ts`), and with no shipped types tree the only match was an unrelated `sst-env.d.ts` (SST-generated, package root) — so `propsBodyFor()` never had any source to search and always fell through to the stub. ## `_preview/**` bundle size — 70MB → 19MB fix

- **Root cause**: `@kit/ui/*` imports were never actually being shimmed to `window.KitUi.*` inside individual preview compiles (`lib/story-imports.mjs`'s Rule 1 subpath lookup and Rule 2's `exportedComponentFor` BOTH compare the resolved file/subpath's last path segment — kebab-case, e.g. `button` from `src/shadcn/button.tsx` or `@kit/ui/button` — against the case-sensitive `exported` Set of real PascalCase export names like `Button`. They never match for this package's naming convention, where the file/subpath name and the exported component name differ only in case). Every preview consequently bundled the REAL component source fresh, transitively pulling in `radix-ui` (the full meta-package), `class-variance-authority`, `clsx`, `tailwind-merge`, etc. into EVERY SINGLE preview file — 253 previews each duplicating a large slice of the same dependency tree. Confirmed via `grep -c "window.KitUi" _preview/Button.js` → 0, plus `node_modules/...radix-ui.../` paths appearing directly in the compiled output.
- **Fix**: `cfg.storyImports.shim: ["/packages/ui/src/"]` — a broad, case-INsensitive-by-construction SUBSTRING match against the resolved real file path (not the import specifier), which `policyRedirect` checks unconditionally before the case-sensitive name lookup, so it shims regardless of whether `exportedComponentFor` would have matched. Dropped `_preview/` from ~70MB to ~11MB (`Button.js`: 115KB → 11KB) — necessary because the per-component bundles need to be small enough to actually upload (the upload tool only takes inline file content, and reproducing hundreds of KB of exact minified JS per file isn't reliably feasible).
- **Side effect #1 (silent correctness regression, not a crash)**: `EnhancedDataTable`'s preview imported `{ DataTable as EnhancedDataTable } from '@kit/ui/enhanced-data-table'` (the bare real export name, correct PRE-shim). Post-shim, named imports resolve via a star re-export of window.KitUi's WHOLE namespace — which has BOTH `DataTable` (shadcn, bare/primary alias) AND `EnhancedDataTable` (makerkit, secondary alias) as separately-named properties. Importing `DataTable` now silently grabbed the WRONG (shadcn) one — it rendered fine with no error (shadcn's plain table doesn't call `useRouter()`), which is exactly why this is dangerous: a wrong-but-plausible render, not a loud failure. Fix: import the ALIAS name (`EnhancedDataTable`) directly — it doesn't really exist on the source file, but it exists on window.KitUi, which is what the shim actually resolves against. **General rule post-shim**: for any component that went through the Sidebar/DataTable-style aliasing fork, preview imports must use the ALIAS name, not the real bare export name, or risk silently rendering the other half of the collision pair.
- **Side effect #2 (real regressions — components that previously WORKED via fresh-bundling now broke)**: any preview using a "fake context provider" workaround (`AppBreadcrumbs`'s `PathnameContext`, `EnhancedDataTable`'s `AppRouterContext`) or a "fake module init" workaround (`LanguageSelector`/`BorderedNavigationMenuItem`'s `i18next` init, `MultiStepForm`-family's `QueryClientProvider`) broke or silently regressed, because the workaround was written INSIDE the preview's own separately-bundled file — which made sense when the REAL component was ALSO bundled fresh into that same file (workaround and component shared one bundle, one module graph). Post-shim, the real component now lives in `_ds_bundle.js`'s module graph instead, so a workaround in the preview's own bundle no longer shares Context/module identity with it. Confirmed via screenshots: `LanguageSelector` threw `Cannot read properties of undefined (reading 'supportedLngs')`; `AppBreadcrumbs` rendered both cells as identical empty boxes (`usePathname()` silently degrading to `null` again). **`MultiStepForm` did NOT break** — surprising at first, but `useMutation`'s `QueryClientContext` happened to already be satisfied by `preview-background.tsx`'s OWN `QueryClientProvider` (also bundled into `_ds_bundle.js`, now sharing identity with the now-shimmed `MultiStepForm` for the first time) — the preview's own redundant local `QueryClientProvider` was simply inert dead weight by that point, not the active fix.
  - **Fix, two-pronged based on whether the workaround needs to vary per-story**:
    1. Story-INDEPENDENT setup (i18next init — same for every cell) → moved into `.design-sync/preview-background.tsx` itself (bundled into `_ds_bundle.js`), which already wraps every cell via `cfg.provider`. Removed the now-redundant per-file copies in `LanguageSelector.tsx`/`BorderedNavigationMenu(Item).tsx`/`MultiStepForm`-family.
    2. Story-DEPENDENT values (`AppBreadcrumbs` needs a different fake pathname per story; `EnhancedDataTable`'s router stub is shared but still needs per-preview wrapping) → `cfg.provider` itself can't pass per-story props through, so `preview-background.tsx` instead exposes the raw context OBJECTS on `window` (`window.__dsAppRouterContext`, `window.__dsPathnameContext`) at module-evaluation time. Each preview reads `window.__d s...Context` instead of importing `next/dist/.../*.shared-runtime` fresh, then wraps with its OWN per-story `value` — the object identity comes from the shared bundle, only the value varies per call site.
  - **General rule going forward**: any preview-side workaround that fakes a context/module a SHIMMED component reads from must either live in `preview-background.tsx` directly (story-independent) or read the context object off a `window.__ds*` global set there (story-dependent) — never re-import the faked module fresh inside the preview's own file. This applies to ALL `@kit/ui` components now (the shim is unconditional for anything under `/packages/ui/src/`), not just the ones discovered broken in this pass — re-check any FUTURE preview that wraps a fake provider/context against this rule before trusting a clean-looking screenshot.

## Re-sync risks

- Compiled theme CSS (`.design-sync/.cache/compiled-theme.css`) is generated, not committed — must re-run `.design-sync/build-css.mjs` before every sync, and re-check `tw-input.css`'s `@import` list still matches `apps/web/styles/globals.css`'s import list if that file's import list changes.
- The react-umd stand-in node_modules dir (`/Users/xuryax/Work/code/storybook/.design-sync-scratch/node_modules`) is entirely outside git and outside this machine's durable state — a fresh clone or different machine must re-run `node .design-sync/build-react-umd.mjs` before the first build, and every `--node-modules` flag must point there, not at `apps/web/node_modules`.
- The Sidebar/DataTable alias fork is keyed by hand-enumerated export lists (see above) — verify against the live files on every re-sync, not just trust the fork.
- Font substitutes (JetBrains Mono/Courier Prime/Merriweather) were accepted without sourcing real files — if `chart.tsx` typography becomes a priority, revisit via `cfg.extraFonts`.
- This package has no build/typecheck gate run as part of design-sync — if `src/` changes in ways that break the synth-entry bundling (e.g. a new top-level name collision), only the build/validate diagnostics here will catch it, not a CI typecheck.
