## KB-190 — The upstream editor's get_audio_analysis crashes the StorybookStudio window: Chromium's decodeAudioData segfaults the renderer

> **Fixed (2026-10-05), #645, in aroundAI/storybookstudio#29.** It reaches
> users with the next StorybookStudio pin bump. The window no longer decodes
> audio. `get_audio_analysis` and the timeline's beat markers call
> `window.electronAPI.analyzeAudioFile` (`media:analyzeAudio`).
>
> The main process runs each analysis in its own Electron utility process
> (`electron/studio/audioAnalysisProcess.js`). There ffmpeg decodes only the
> analysed range to 22.05 kHz PCM, and the same DSP (moved to
> `src/studio/audio/analysis.js`) runs on it. The result keeps its shape:
> beats, onsets, loudness, curve and silences. A source over 30 minutes is
> refused at the limit, not decoded whole.
>
> Red/green: the MCP test in `tests/studio/audio-analysis-main.test.mjs`
> drives `get_audio_analysis {clipId}` against a real file. With the old
> renderer code it fails because the window decoded 31 181 bytes. With the
> fix it passes.
>
> Measured on the pulled "The Night Lab – E01", before and after:
>
> | App | Call | Time | Window afterwards | New `Helper (Renderer)` report |
> | --- | --- | --- | --- | --- |
> | `electron:dev`, old renderer | dialogue `clip-21` | 60 s MCP timeout | crashed | `Electron Helper (Renderer)-2026-10-05-173032.ips` |
> | `electron:dev`, fixed | dialogue clips | 142–293 ms | alive | none |
> | Packaged (arm64), fixed | dialogue clips | 231–251 ms | alive | none |
> | Packaged (arm64), fixed | 99 s music asset | 550 ms | alive | none |
> | Packaged (arm64), fixed | 29 min stereo AAC | 7.7 s | alive | none |
>
> During the 29-minute analysis, the window's IPC round trips stayed at or
> under 7 ms. Run in the main process instead, the same file took 31 s and
> 1.4 GB, which is why each analysis gets a utility process.

**Severity:** Medium — any call to the upstream editor's MCP tool `get_audio_analysis` (expert profile) on a clip whose file is on disk kills the Studio window's renderer, and with it the MCP action bridge. Every later MCP call then times out after 60 s until the window reloads. The agent profile no longer reaches it: storybookstudio#14 moved FILM-2013's compile-time reads to the main process (ffmpeg). The tool itself is still exposed in the expert profile, and the upstream editor's own UI paths that decode audio in the renderer may be affected the same way. **Found:** by t2015 while driving FILM-2015's end-to-end test on a pulled episode in the packaged app (`studio_edit` died with no answer). Reproduced by t2013 in `electron:dev` while fixing that (storybookstudio#14).

**What happens.** `get_audio_analysis` (`src/services/mcpActions.js` `handleGetAudioAnalysis` → `src/services/audioAnalysis.js` `analyzeAudioSource`) reads the file over `readFileAsBuffer` and calls `AudioContext.decodeAudioData` in the renderer. On this machine (Electron 28.3.3 / Chromium 120, macOS 26 "Darwin 25.4"), the decode segfaults the renderer:

- The crash is EXC_BAD_ACCESS, SIGSEGV at 0x0 on `CrRendererMain`.
- macOS writes a report to `~/Library/Logs/DiagnosticReports/Electron Helper (Renderer)-*.ips`, or `StorybookStudio Helper (Renderer)-*.ips` in the packaged app.
- No console error or `pageerror` precedes it.

**Reproduced** (2026-10-05, fork main ecc9c0d, `npx electron . --remote-debugging-port=9223`, Runtime.evaluate in the window):

| In the window | Result |
| --- | --- |
| `window.electronAPI.readFileAsBuffer(<22.05 kHz mono MP3>)` | ok, 30 137 bytes |
| `new OfflineAudioContext(1, 1, 44100).decodeAudioData(<those bytes>)` | renderer dies |
| The same line converted to WAV, decoded the same way | renderer dies |
| A page-allocated copy of the bytes (`new Uint8Array(...)`) | renderer dies |
| `new OfflineAudioContext(1, 44100, 44100)`, then an oscillator and `startRendering()` | ok |
| MCP `get_audio_analysis {clipId}` on a pulled dialogue clip | the call times out after 60 s; the renderer is gone |

So decoding crashes on any input and any allocation, while creating and rendering an audio context does not. The likely cause is the decoder in this Electron/Chromium build on macOS 26. It has not been tried on an older macOS or a newer Electron.

**Proposed fix.** Decode audio outside the renderer: run ffmpeg in the main process, as `electron/studio/audioReads.js` now does for the compilers (silencedetect, plus ebur128 loudness). Point `get_audio_analysis` at it for its silences and loudness; beat tracking would need an ffmpeg-based onset pass or the decode in a utility process. Alternatively, upgrade Electron and re-test.

**Acceptance criteria:**
- `get_audio_analysis {clipId}` on a pulled episode's dialogue clip answers with silences and loudness in `electron:dev` and in the packaged app on macOS 26.
- The window is still alive afterwards.
- No new `Helper (Renderer)` crash report appears.
- A test drives the tool over MCP against a real audio file.
