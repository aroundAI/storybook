## KB-199 — MCP list_channels shows no channel for a project whose channels are linked but have published nothing

> **Fixed (2026-10-18), #676.** `list_channels(projectId)` now calls
> `listPublishingChannelsService` → `listProjectLinkedChannels`
> (`packages/features/content-analytics/src/server/channels.ts`): the
> project's linked channels, read by `getProjectChannelIds` — the one
> definition scheduling's `assertConnectionOfProject` also uses, now paged
> with `fetchAllRows` — plus any channel the project published from that is
> no longer linked, each flagged `linked: true|false`, linked first. The
> analytics callers keep `listProjectChannels` (published channels): the
> Deep Dive and Video Log channel filter, the daily digest, the
> performance reader and the subscriber series filter figures, which only a
> published channel has. The tool's description and the workflow guide say
> it lists exactly what `schedule_publish` and `schedule_release` accept.
> The fix also found that `schedule_release` with `preview: true` placed
> posts on a channel outside the episode's project, which the real schedule
> then refused at preflight; both previews (cadence and breaking) now refuse
> it with the same sentence. Tests: `list-channels-linked.test.ts` (studio-mcp;
> production's shape, red on main), the preview refusal in
> `schedule-release.service.test.ts`, and the E2E
> `apps/e2e/tests/mcp/list-channels-linked.spec.ts`, which links three
> channels on the Publish screen and then lists them and previews a release
> to them over MCP (red on main: `[]`). Guards KB199-U1..U6 in
> `tooling/mutation-guards/kb-199.json`, all unit: every mutated line is
> server code, which the guards README keeps out of E2E entries.

**Severity:** High — the owner's producer session (an MCP client) could
not schedule anything for either project: `schedule_release` takes a
`connectionId` "from list_channels", and list_channels returned none.

**Found:** 2026-10-18, by the owner's producer session over the MCP
connector. A read-only check of production showed
`project_publishing_configs` with Fault & Frontier and Ledger Autopsy each
linked to YouTube, Facebook and Instagram, all enabled, and no publish
with status `published`.

### What happened

`list_channels(projectId)` → `listChannelsService` → `listProjectChannels`,
which reads `publishes` with status `published` for the project's episodes
and returns their channels. That is the analytics meaning (a channel to
filter figures by), and it was the only meaning the tool had. Scheduling
reads another source: `getProjectChannelIds`, the project's enabled
`project_publishing_configs` rows (KB-195). Before a project's first
publish, the two disagree completely: every linked channel is accepted by
`schedule_release` and none is listed.

Reproduced as a unit test over the tool (`list-channels-linked.test.ts`:
three linked channels, no publishes → `[]` on main) and end to end
(`list-channels-linked.spec.ts`: channels linked on the Publish screen, then
`list_channels` over the real MCP endpoint → `[]` on main).

### Acceptance

- [x] `list_channels(projectId)` lists the project's linked channels before
  anything is published, each `linked: true`.
- [x] A channel the project published from and no longer links is listed
  `linked: false`; a channel neither linked nor published from is not.
- [x] One definition of "the project's channels": `getProjectChannelIds`,
  shared by the list and by scheduling, paged.
- [x] The analytics callers of `listProjectChannels` keep their meaning
  and their tests.
- [x] A release preview refuses a channel the schedule would refuse.
