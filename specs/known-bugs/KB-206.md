## KB-206 — Publish now leaves Instagram Reels and Facebook videos 'publishing' for ever

> **Fixed (2026-10-19), #684.** `publishToAllAction` no longer calls a
> platform: a publish made now is written `queued` and sent to the publish
> worker's SQS queue, the same message and worker scheduled publishes use
> (15-minute Lambda, 90-minute visibility). `retryPublishAction` queues the
> same way. The worker marks a row `publishing` with
> `metadata.publishingStartedAt` when it starts, and the scheduled-publish
> cron (every 5 minutes) fails any row still `publishing` 30 minutes after
> its attempt began (its creation, for rows with no stamp), with "Timed out
> while publishing; check the platform before retrying, in case the post
> went out." The Publish screen shows a queued row as running, polls the
> publishes list every 10 seconds while any row is queued or publishing,
> and refetches on the worker's socket message. Tests, red on main and green
> with the fix: `packages/features/publishing/__tests__/publish-actions.test.ts`
> ("queues an immediate request and calls no platform in the request",
> "queues an Instagram publish for the worker…", "…one the queue refuses")
> and `apps/web/lambda/scheduled-publish/__tests__/index.test.ts` ("fails a
> publish left publishing for over 30 minutes"); the sweep's window and
> worker stamp in `stale-publishing.test.ts`.

**Severity:** High: Publish now could not publish to Instagram at all, and
left Facebook long videos in a state nobody could retry (retry takes only
`failed` rows).

**Found:** 2026-10-19 in production. Publish now on an episode's Publish
screen, for 7 Instagram Reels and 2 Facebook long videos: all nine rows
stayed `publishes.status = 'publishing'`, and the Instagram account has no
posts.

### What happened

`confirmAndUpload` on the Publish screen calls `publishToAllAction` once per
platform. Without a `scheduledAt`, the action wrote the row `publishing` and
then uploaded inside the request: for Instagram, create the media container,
then poll until Instagram has processed the video, then publish it; for
Facebook, upload and fetch the video's status. The web app runs on Lambda
through OpenNext with a 30-second limit. Instagram's processing alone takes
longer than that for a Reel, so the request was cut off mid-poll: the row
was never moved to `published` or `failed`, and no code path ever touched a
`publishing` row again.

Scheduled publishes never had this: the cron sends them to SQS and the
publish worker, with a 15-minute limit, uploads them.

### The fix

- **Publish now and retry queue the worker.** Every refusal still happens
  in the request (token, channel, video ownership, X limits, YouTube
  audience); only the upload moves. A queue that refuses the message marks
  that row `failed` with its reason.
- **A stuck row is failed, not left.** The worker stamps when its attempt
  began; the scheduled job fails a `publishing` row 30 minutes after that
  (the worker cannot run longer than 15). The message says to check the
  platform first, because the post may have gone out. The nine production
  rows are failed by the first cron run after deploy.

### Not covered

- A row the worker leaves `queued` (a message that went to the dead-letter
  queue before the worker started it) is not swept: the queue's visibility
  timeout allows a legitimate wait of up to 90 minutes per attempt.
