## KB-175 — Two episodes in one project can carry the same number; the create code assumes a unique constraint that does not exist

> **Fixed (2026-10-04), #605.** `idx_episodes_project_number` is now a
> unique index on `(project_id, number) where deleted_at is null`: a plain
> index of that name from `20260528163000_performance_indexes.sql` was
> dropped and replaced, because `create unique index if not exists` would
> have kept the plain one and enforced nothing. The migration first resolves
> existing duplicates deterministically: per project and number the oldest
> live episode (`created_at`, then `id`) keeps its number; each later one is
> given the next free number above the project's highest live number, in
> number, rank, id order. Slugs are untouched, so URLs and the slug index are
> unaffected; soft-deleted rows are ignored, so it cannot fail on them. Every
> create path now handles the clash: `insertEpisode` (web dialog, MCP
> `create_episode`) retries an auto number and refuses a chosen one;
> `insertEpisodesAtNextNumbers` (new, in `episode.service.ts`) does the same
> for the batch outline commit and the season generator, which also now
> number across the project instead of per season (the season generator
> used the LLM's 1..N per season, which the index would have refused for
> every second season). The season-outline stage in `@kit/generation`
> already picks free numbers itself and is unchanged; it has no retry, so a
> concurrent create can still fail it with 23505. That is a known gap until
> the retry lands there.

**Severity:** Low — only a user (or an MCP client) who chooses an episode
number already in use is affected; auto-assigned numbers take the highest
plus one and do not collide. Once it happens the episode list shows two
"Episode 1" rows and the clash is silent. **Found:** FILM-1905's integration
test (`packages/features/studio-mcp/__tests__/tools/read-author.integration.test.ts`),
calling `create_episode` with `number: 1` in a project that already had an
episode 1.

**What happens.** `createEpisode` in
`packages/features/episodes/src/server/actions.ts` (now
`insertEpisode` in `src/server/episode.service.ts`) retries an auto-assigned
number on `23505` and refuses a caller-chosen number with "Episode N already
exists in this project", citing a constraint named
`unique_episode_number_per_project`. No migration creates it:
`git grep -n unique_episode_number_per_project apps/web/supabase` finds only
the comment in the code. The only per-project uniqueness on `episodes` is
`idx_episodes_project_slug` (`20251221082754_add_episode_slug.sql`), on the
slug `episode-<number>-<title-slug>`, live rows only. So the refusal fires
only when number **and** title repeat; the same number with a different
title inserts a second episode with that number.

**Reproduced** 2026-10-03 on the lane B stack through the MCP tool: with
episode 1 "Written over MCP" present, `create_episode({ number: 1, title:
'Clash' })` returned a new episode numbered 1; `create_episode({ number: 1,
title: 'Written over MCP' })` was refused by the slug index with the
"already exists" wording. The web dialog takes the same `CreateEpisodeSchema`
and the same path.

**Proposed fix.** A partial unique index `(project_id, number) where
deleted_at is null`, with a pgTAP test that inserts a duplicate and expects
`23505`, and a reconcile step for any existing duplicates (renumber the later
row) before the index. Then the refusal in `insertEpisode` says something
true. Until then the test in FILM-1905 asserts the slug refusal, not a number
refusal.

**Acceptance.** Inserting a second live episode with an existing number in
the same project fails with `23505`; a soft-deleted episode frees its number;
`insertEpisode` returns its refusal for a chosen number that clashes;
`pnpm --filter @kit/episodes test` and the pgTAP file pass.
