## KB-170 — Production's schema drifted from its migration history: the pending migrations failed on a renamed policy, and three objects are missing

> **Fixed (2026-10-02), #547.** Two changes. KB-26's migration
> (`20260923044054_kb26_scope_research_uploads.sql:90`) drops the
> external_sources read policy under either name. A new migration
> (`20261002135747_kb170-restore-drifted-objects.sql`) creates the three
> missing objects only where they are missing. Rehearsed against
> production's dumped schema, all 49 pending migrations apply. Production's
> end state then matches a database built from migrations. A database built
> from migrations is byte-identical to origin/main's (`pg_dump -s` of
> public, storage, kit and auth).

**Severity:** High. Production's deploy is blocked: `supabase db push`
applied migrations through `20260923042517` and stopped on the next one.
48 migrations are pending behind it. Separately, production owners cannot
replace or delete their own project assets (below). **Found:** the owner's
production deploy, 2026-10-02.

### What happened

`db push` ran `20260923044054_kb26_scope_research_uploads.sql` and stopped:

```
drop policy "Anyone can view active sources" on public.external_sources
ERROR:  policy "Anyone can view active sources" for table "external_sources" does not exist
```

### How it was reproduced

The owner dumped production's schema (structure only, public and storage)
after the failed push. A throwaway database `prodsim` was built in lane A's
Supabase container from that dump. Supabase's roles and extensions come from
the container. Auth comes from the lane's database. Kit comes from a database
built from the migrations through `20260923042517`. The dump omits kit, so
production's kit is assumed to match its history.

The positive control: prodsim has `public.external_sources` without
"Anyone can view active sources", as production does.

The 48 pending migrations were replayed in timestamp order, one
`psql -v ON_ERROR_STOP=1 --single-transaction` each, as `db push` runs them.
The run kept going after each failure:

| Migration | Error | Cause |
|---|---|---|
| `20260923044054_kb26_scope_research_uploads` | policy "Anyone can view active sources" does not exist | the drift below |
| `20260925115518_kb37_team_owned_research_sources` | column "project_id" does not exist | KB-26 did not apply |
| `20260927021032_kb99-team-account-guard` | column t.account_id does not exist (external_sources) | KB-37 did not apply |
| `20260930160000_generated-reports-team-account-guard` | function kit.require_team_account() does not exist | KB-99 did not apply |
| `20261001114902_channel-experiments` | function kit.require_team_account() does not exist | KB-99 did not apply |
| `20261002122828_genome-semantic-and-hypothesis-link` | relation public.channel_experiments does not exist | channel-experiments did not apply |

One root cause, five cascades. After the KB-26 fix, all 48 apply.

### What production has that its history does not say

The prodsim catalog was compared, object by object, with a database built
from the migrations through `20260923042517`. Ignored: storage-api's own
tables and functions, which are a newer storage version in production, and
`ARRAY[...]` deparse differences, which mean the same thing. Four app-level
differences remained:

| Object | History says | Production has | Probable cause |
|---|---|---|---|
| `external_sources` read policy | "Anyone can view active sources" | "Authenticated users can view active sources", same definition (`select to authenticated using (is_active = true)`) | `20260211200002` first shipped as `restrict_external_sources_rls.sql`, which renamed it (a496e309e). Production applied it. The file was then deleted (45a86b64c) and its version reused for `add_external_content_category_check.sql` |
| `external_content.chk_external_content_category` | present | missing | the same reuse: production records `20260211200002` as applied, so it never ran the new file |
| `projects.ix_projects_account_slug_active` | present | missing | `20260103120000` first shipped as `CREATE INDEX CONCURRENTLY`, which cannot run in a migration's transaction (331b11b88 removed it). The file's other three indexes exist in production. How production recorded the version without this one is not knowable from a structure dump |
| `storage.objects` policy `project_assets_select` | present (`20251207162036`) | missing | no migration drops it; most likely removed by hand (dashboard) |

`batch_assemble_edit_project`'s body also differs: its file was edited
after it shipped (7d7bf73a4…dd2250a99). FILM-607 drops it, so this does not
survive the deploy.

The rule this breaks: **a migration that has reached production is never
edited, deleted or renumbered.** `db push` compares version numbers only, so
a changed file under an applied version is skipped silently.

### The missing SELECT policy is a live production bug

Storage checks a SELECT policy before it replaces (upsert) or deletes an
object. Without `project_assets_select`, the owner-scoped `project_assets_update`
and `_delete` policies (KB-28) can never match. pgTAP was run against
prodsim's end state (49 migrations, seed.sql). In
`project-assets-storage-rls.test.sql`, tests 34–36 and 39–40 fail: the owner
may replace their own object, move it, delete it, and reads stay open. With
`20261002135747`, all pass.

### The fix

- **KB-26** drops either policy name (`drop policy if exists` for both).
  On a fresh database the second name never exists, so the end state is
  unchanged.
- **`20261002135747_kb170-restore-drifted-objects.sql`** creates the index,
  the CHECK and the policy only where missing (`create index if not exists`;
  a `pg_constraint` / `pg_policies` guard for the other two). Each has its
  original definition. On a fresh database it does nothing.

### Evidence

- Replay on prodsim: 6 failures before, 0 after (49 applied, including
  this one).
- End state against a fresh build of this branch: the catalogs are identical
  for tables, columns, constraints, indexes, policies, triggers, function
  bodies, views, table grants and function ACLs. Only storage-api's internal
  lifecycle check differs.
- Fresh build against origin/main's migrations: `pg_dump -s` of public,
  storage, kit and auth is identical (only pg_dump's random `\restrict`
  token differs).
- pgTAP, 94 files: fresh branch 94/94. Prodsim end state 93/94. The one
  failure is `account-permissions` tests 4 and 6: inserting `('owner', 4)`
  violates both `roles_pkey` and `roles_hierarchy_level_key`, and the error
  names whichever index was built first. A dump reload builds them in another
  order. Same rows, same constraints.

Rows were planted in prodsim to show the query finds what the deploy fails
on. A project on a personal account read 1, and the replay stopped at
KB-99 with "rows sit on personal accounts". An `external_content` row with
category `gossip` read 1, and the replay stopped at `20261002135747`.

Safe by construction, so not in the query:
- KB-26's `unique nulls not distinct (project_id, slug)`: production
  already has `external_sources_slug_key`, and `project_id` starts null.
- KB-37's checks and unique key: they follow from KB-26's key and the
  `account_id` it fills from projects.
- KB-23's unique index, which adds `currency`: production's
  `revenue_records_scope_check` already forbids a null scope, so the new
  `nulls not distinct` cannot join two rows that the old key kept apart.
- KB-49's `publishes_status_check` and the genome `content_tags_dimension_check`:
  each is a superset of production's current list.
- KB-22, KB-30 and the genome hypothesis check: their columns are new and
  start null.
- `not null default false` columns (KB-78, `publishes.ai_generated`).

The statements that change rows on purpose: KB-26 marks `manual-%` uploads.
KB-37 marks the built-in sources and fills `account_id`. KB-23 upper-cases
currencies. KB-98 deletes cross-account `publish_tags` / `experiment_tags`
and prints the publish ids to re-sync. KB-113 clears cross-account links.
`not-built-db-guards` nulls non-positive `audio_tracks.duration_seconds`.
`revenue-records-unmeasured` nulls API rows' zero revenue.
