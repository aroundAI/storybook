## KB-174 — Bulk asset creation's generation_jobs row fails the job_type CHECK and is only logged

> **Fixed (2026-10-03), #553.** Three changes. The migration
> `20261002201125_kb174-asset-creation-job-type.sql` adds `'asset_creation'`
> to `generation_jobs_job_type_check`, mirrored in
> `apps/web/supabase/schemas/30-film-studio.sql`. `GENERATION_JOB_TYPES`
> (`packages/features/prompt-engine/src/lib/generation-job-types.ts`) is the
> one TypeScript copy of the list; `generation-job-types.test.ts` parses the
> latest migration that defines the CHECK and the schema mirror and fails
> if either differs from it, and scans every `job_type:` literal a producer
> inserts under `packages/` and `apps/web/lambda/` for a value outside it.
> The llm-worker's `GenerationJobType` is now that list. The four bulk
> actions in `bulk-actions.ts` share `recordJobsThenQueue`: the rows are
> written first, and a refused row puts every episode in `failed` with the
> database's message and queues nothing, instead of a warn log and a queued
> job with no record.

**Severity:** Medium. Every bulk asset creation since the action shipped
ran with no `generation_jobs` row: nothing for progress, status or cost
tracking, and nothing for the worker's status updates to find. The work
itself still happened, because the SQS message was sent regardless, so no
assets were lost. **Found:** the Phase 19 Stage 1 audit, 2026-10-03, main
@0d307c58e.

### What happens

`batchCreateAssetsAction` (`packages/features/episodes/src/server/bulk-actions.ts`)
builds one `generation_jobs` row per episode with `job_type: 'asset_creation'`,
queues the SQS job `asset-creation` for each, and then inserts the rows in
one batch. `generation_jobs_job_type_check`
(`20260923025438_generation_jobs_refinement_job_types.sql`) allowed eleven
values and not that one, so the batch insert failed with `23514`. The
action caught the error, logged it at warn ("Failed to batch-create
generation jobs") and returned `queued: n, failed: []`. The three other
bulk actions had the same shape: send first, insert after, warn on failure.

KB-14 was the same bug for `story-refinement` and `screenplay-refinement`.
The list lived in four places (the migration, the schema mirror, the
worker's union, and each producer's literal) and nothing held them
together.

### Reproduced

pgTAP `generation-jobs-job-types.test.sql` against a throwaway Postgres
built from origin/main's 215 migrations, inserting each of the twelve
values the producers write:

```
generation-jobs-job-types.test.sql: plan=1..14 ok=12 not_ok=2 errors=0
 not ok 12 - a asset_creation job can be recorded
 not ok 13 - the worker's status update reaches the asset creation row
```

Unit, before the fix, `bulk-actions-job-rows.test.ts` with a fake client
whose `generation_jobs.insert` answers `23514 … generation_jobs_job_type_check`:
all four bulk actions sent before they inserted
(`expected [ 'send', 'insert' ] to deeply equal [ 'insert', 'send' ]`), and
each reported `queued: 1, failed: []` on the refused row. And
`generation-job-types.test.ts` against origin/main's migrations:
`check in 20260923025438_generation_jobs_refinement_job_types.sql: expected
[ 'audio_cue_generation', …(10) ] to deeply equal [ 'asset_creation', …(11) ]`.

### The fix

- **The CHECK allows `asset_creation`.** It is the only value any producer
  inserts today that the list lacked (`git grep "job_type: '"` over the
  repo: story, screenplay, shot_list, voice, audio_cue_generation,
  story-refinement, screenplay-refinement, asset_creation). The spelling
  stays the row's, with an underscore, as `shot_list` and
  `audio_cue_generation` do beside their hyphenated SQS job types; the
  worker's handler does not yet update this row (it never did), and
  FILM-1901 part A, which is rewriting `handlers/asset-creation.ts`, can
  call `markJobProcessing(…, 'asset_creation')` now that the type allows
  it.
- **One list, held to the CHECK.** `GENERATION_JOB_TYPES` is exported from
  `@kit/prompt-engine/generation-job-types`, a file with no imports so the
  esbuild-bundled worker can take it. The test parses the SQL rather than
  trusting a comment.
- **Rows before messages, refusals as values.** `recordJobsThenQueue` is
  what all four bulk actions now do after their loop. The worker updates a
  row by `(episode, job_type, status = 'queued')` and the story handler
  skips its write when it finds none (`story-generation.ts:408`), so the
  row has to exist before the message can be consumed; the old order was a
  race as well as a silent failure.

### Deliberately not done here

- The seven LLM job types that never insert a row at all (season-outline,
  season-analysis, story-ideation, fact-extraction,
  batch-translate-metadata, analytics-insights, language-insights) are not
  added to the CHECK. FILM-1903 part C gives generation_jobs a required
  `run_id` for LLM job types and adds rows for the remainder; adding bare
  values now would be a list nothing writes to.
- `GenerationJobType` in `packages/features/episodes/src/lib/types.ts` and
  the `jobType` enum in `generation-job-actions.ts` stay as four-value
  subsets: they name the types the single-episode UI polls, not what the
  table accepts.
- A row whose SQS send then fails stays `queued`. That was so before and
  is unchanged; the send failure is reported in `failed`.
