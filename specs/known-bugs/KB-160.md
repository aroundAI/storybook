## KB-160 — After a successful publish, the dialog shows no link to the post: it reads `url`, and the action returns `platformUrl`

> **Fixed (2026-10-01), #TBD.** The publish screen no longer restates the
> action's result by hand: `PublishOutcome` is derived from
> `publishToAllAction`'s own return type, and the success row is built by
> `publishedUploadStatus`, which reads `platformUrl`. Reading a field the
> action does not return is now a type error (TS2339), not an `undefined`.
> The link also got an accessible name ("View on YouTube"); it had none, which
> axe never reported because the link never rendered.

**Severity:** Low — every inline publish (Publish All → Confirm) ended with a
green tick and no "view on platform" link, on every platform. Nothing was
lost: the URL was saved on the publish row and the Published Content list
below links to it. **Found:** a teammate reading the publish dialog against
the action, on 2026-10-01.

### What happened

`publishToAllAction` (`packages/features/publishing/src/server/publish-actions.ts`)
returns `PublishResult[]`, whose link field is `platformUrl`. The publish
screen (`publish-screen.tsx`, `confirmAndUpload`) cast each element to
`{ status: string; url?: string; error?: string }` and copied `result.url`
into the dialog's row. The cast compiled because the two shapes overlap, and
`result.url` was always `undefined`, so `publish-progress-dialog.tsx` never
rendered its `ExternalLink` anchor (`{s.url && …}`).

### Reproduced

With the original read restored, `published-upload-status.test.ts` fails:
a `completed` result carrying `platformUrl` produces a row whose `url` is
`undefined` (mutation guard `KB-160 L1`, RED). Without the cast, the same
read fails `tsc` with TS2339, "Property 'url' does not exist on type
'PublishResult'".

`apps/e2e/tests/publishing/sandbox-publish.spec.ts` ("Publish All uploads to
YouTube…") now asserts that the dialog's `publish-platform-link` carries the
`platform_url` the publish row holds. Its run against the vendor sandbox,
and guard `L2` (the original cast restored), are still to be run: the
sandbox was down when this was filed.

### The class

Swept the other consumers of the publishing actions' results: the scheduling
path (`handleSchedule`) discards the result; `publish-status-row.tsx` and
`published-content-section.tsx` already read `platformUrl`; the publish
worker's `publish-success` socket message sends `url` and the screen reads
`msg.url`, which agree. This was the only hand-written restatement of an
action result in the publish screen.

### Acceptance criteria

- [x] The success row's link is the action's `platformUrl` —
  `published-upload-status.test.ts`, guard `L1` RED.
- [x] The screen reads the action's own result type; reading `url` off it
  does not compile.
- [ ] After a real publish the dialog links to the platform URL the publish
  row holds: `sandbox-publish.spec.ts` asserts it, and guard `L2` checks it,
  but neither has run yet (the vendor sandbox was down).
