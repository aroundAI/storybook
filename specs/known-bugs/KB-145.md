## KB-145 — The LinkedIn connection records the scopes the app requested, not the ones the person granted

**Severity:** Medium. Someone who unticks `w_member_social` on LinkedIn's
consent screen is stored as having granted it, so the app believes it can post
and the first publish fails at LinkedIn with `ACCESS_DENIED` instead of the
Platforms page saying the connection lacks the scope. It does not lose data or
cross accounts, and only a person who narrows the consent screen is affected,
which is why it is not High. **Found:** 2026-10-01, building the LinkedIn
sandbox connect spec (FILM-715).

The callback (`apps/web/app/api/platforms/callback/linkedin/route.ts:164-181`)
stores `LINKEDIN_OAUTH_CONFIG.scopes.personal` (or `.company`) whatever the
token response's `scope` says. The TikTok and Meta callbacks record the grant.

### Reproduced (2026-10-01)

`apps/e2e/tests/platform-connections/sandbox-connect-linkedin.spec.ts:191`
connects through the vendor sandbox, unticks `w_member_social`, and asserts the
stored scopes do not contain it (:206). It is marked
`test.fail(true, 'callback/linkedin records requested, not granted, scopes')`,
so it is reported as an expected failure today; Playwright flags an unexpected
pass when the bug is fixed, and the marker comes off then.

### Proposed fix

Record the `scope` the token response returns (split on spaces), falling back
to the requested set only when the response has none.

### Acceptance criteria

- [ ] The callback stores the granted scopes
- [ ] In `sandbox-connect-linkedin.spec.ts` the `test.fail(true, ...)` marker
      is removed and the test passes
