## KB-108 — Canon health dashboard reports recently touched threads as stale

> **Fixed (2026-09-25), #PRNUM.** `getCanonHealthAction` now resolves each
> thread's opening and touched episodes to numbers and asks the same
> function CANON_007 does (`lib/canon/thread-staleness.ts`): stale when
> last active at least the memory horizon ago; unknown is not stale. One
> rule, used by the memory context builder, CANON_007 and the dashboard.

**Severity:** Low — a dashboard count and list, not generation, but it tells
the owner to deal with threads that are live. **Found:** KB-72's sibling sweep
(lead `leads/2026-09-25-kb-72.md`), 2026-09-25. **Fixed** in #PRNUM.

`getCanonHealthAction` (`packages/features/episodes/src/server/canon-actions.ts:771-788`)
estimates a thread's last-touched episode as the opened episode's number
plus the *count* of touched episodes — the arithmetic KB-72 removed from
CANON_007 — and compares it with the memory horizon.

**Reproduced** (vitest with a mocked client, 2026-09-25): a short-film
project (horizon 10) at episode 30, one thread opened in episode 10 and
touched in 10 and 29. The action returns `issueCount: 1` with the thread
in `orphanedThreads`: it computes last touched = 12, so "18 episodes" since,
when the truth is one.

### Proposed fix

Resolve `opened_at` and `episodes_touched` to episode numbers (as the memory
context builder does since KB-72) and take the latest; treat a thread whose
episodes do not resolve as not stale.

### Acceptance criteria

- [x] A thread touched in the previous episode is not counted stale (unit test, seen red first)
- [x] Staleness on the dashboard and in CANON_007 comes from one function
