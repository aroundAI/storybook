## KB-165 — An E2E guard run can hang past Playwright's own timeouts and abort its shard

> **Fixed (2026-10-02), #518 and #533.** There was no frozen worker. Each
> guard's three attempts were Playwright's `--retries=2`, and they shared one
> 600s `--global-timeout`. A failed attempt costs far more than the 2-minute
> test timeout: Playwright then gives after-hooks and teardown, worker cleanup
> and trace saving a test timeout each. On a stalled runner three failing
> attempts ran past 600s. The line reporter prints an attempt's error only
> once the test is final, so the log stopped at `[3/1] (retries)`. Now
> run.py makes the attempts. Each attempt is one `--retries=0` command with
> its own 300s budget, and its report is printed. KB-95 E1 is no longer
> marked a known flake. See [Root cause](#root-cause-2026-10-02).

**Severity:** Medium. It is CI-only, and no user sees it. But each occurrence
ejects a PR from the merge queue and burns about 300 runner-minutes. **Found:**
#506 was ejected from the merge queue by it, and #504 then hit it too.

### What happened

| Run | Job | Guard before it (RED) | Hang |
|---|---|---|---|
| 36907848672 (#506) | 110522869036, 🧬 E2E guards (1) | KB-7 "a refused action no longer re-reads the change", 19:01:34 | `subprocess.TimeoutExpired` at 19:17:00 |
| 36913025632 (#504) | 110540230678, 🧬 E2E guards (1) | the same KB-7 guard, 19:47:11 | `subprocess.TimeoutExpired` at 20:03:18; the job was then cancelled at its 45-minute limit |

Both times the hang came in the **baseline** run of
`KB-95 E1 Delete only hides the card again` (`kb-95.json`), before any
mutation. The command was `npx playwright test
tests/storage/audio-library-delete.spec.ts … -g 'stays gone after a reload'`.
`run.py` called `subprocess.run(…, timeout=900)` and did not catch the
timeout. The traceback aborted the shard, and the guards after it never ran.
Playwright's output was discarded with it.

The same guard passed in #507's queue run (36907782405). In the evidence job
of the failing run, the same test passed in 4.1s.

### What the logs show (run 36907848672)

- **Supabase was up.** The start step printed `toomanyrequests: Rate
  exceeded` for six images. The CLI retried them, printed `Waiting for health
  checks...` and then `Started supabase local development setup.`, with no
  stopped services. The test's own storage upload (it asserts 200) and the
  app's `DELETE /storage/v1/object/project-assets` (200, in both attempts)
  went through. The rate limit is not the cause, so the start step is
  unchanged.
- **Attempt 1 stalled on the dev server.** The delete action finished at
  19:01:56. The reload's GET reached the server about 100s later
  (`GET …/audio-library 200 in 4513ms`, logged 19:03:43). That is the 120s
  test timeout. Reproduced locally by freezing the dev server (`SIGSTOP`) at
  the reload: the run fails cleanly in 219s with `page.reload: Timeout 60000ms
  exceeded`, then `page.goto` timeouts on both retries. This part is
  KB-3's class (a dev server slowed by earlier mutation cycles), and on its
  own it fails fast.
- **Attempt 2 reached its reload at 19:04:09. After that, nothing.** No
  third attempt ever reached the server, and Playwright did not exit for 13
  minutes.

### What can hang a run past Playwright's own timeouts (reproduced)

The test timeout (120s), expect timeout (10s) and navigation timeout (60s)
are all enforced **inside the worker process**. A worker that stops answering
cannot time itself out. Reproduced: freezing this run's own Playwright worker
4s into the test (`SIGSTOP`) left `npx playwright test` running and silent
for 330s, until it was killed, with no output past the test's start line.
That is the CI log's shape exactly. With `--global-timeout=60000`, which the
runner enforces from outside the worker, the same freeze ended in 61s with
`Timed out waiting 60s for the test suite to run` and `1 did not run`.

Why the CI worker stopped answering is **not known**. The output that would
say where it stopped was discarded by the crash. In both failures it ran
right after the KB-7 guard, which mutates and restores a change-log file
under the same dev server. That is a lead, not a cause.

### Fixed here

- `run.py` runs each guard command in its own process group. Past
  `GUARD_TIMEOUT` (900s), it kills the whole group, keeps what was printed,
  and reports **`TIMED OUT`**. It then goes on to the next guard, so the shard
  reports every guard. A `TIMED OUT` is never counted as `RED`.
- Every E2E guard command carries Playwright's `--global-timeout`: 600s by
  default, or the entry's `timeout`. A hung worker therefore ends with
  Playwright's own report, which names the test, in minutes rather than 15.
  `run.py` reads that line as `TIMED OUT`, because Playwright exits 1 for it
  and a mutated run would otherwise count it as `RED`.
- **Stopgap:** `KB-95 E1` carries `"timeout": 150` and `"known_flake":
  "KB-165"`. Its `TIMED OUT` is printed with Playwright's output but not
  counted. Its `NOT GREEN` and `STAYED GREEN` still fail the run. The guard
  itself stays.

Each rule was shown red first: `--self-test` crashed with the CI traceback
before the catch existed, and each new self-test check fails with its rule
removed. A real run of the guard with a 1s limit reports `TIMED OUT, not
counted … known flake (KB-165)` and Playwright's own lines, in 2s.

### Root cause (2026-10-02)

After #518, about a dozen guards "froze" in the merge queue: KB-7, KB-89,
KB-61, KB-99 E1, KB-16 E1 and E2, and KB158-E1. Each printed `[1/1]`,
`[2/1] (retries)`, sometimes `[3/1] (retries)`, then nothing. That is what
three attempts that all fail slowly look like under a single budget.

**The attempts failed. They did not hang.**
- Run 36936270679 (#525) has `KB-89 E2E panel keeps its own list` reported
  `NOT GREEN` in 474s. All three attempts fail with `Test timeout of 120000ms
  exceeded` at `page.reload`. The same guard elsewhere took 600-904s and was
  reported `TIMED OUT`.
- The dev server log of run 36939326951 (#519, shard 5) shows the stall:
  - a publish page served in 255821ms, and a server action in 82282ms;
  - Supabase sub-fetches at about 1.7s instead of about 20ms;
  - the experiments page never served in any of KB-7's three attempts.

**Why three attempts overran 600s.** Playwright 1.55
(`playwright/lib/worker/workerMain.js:315-380`) runs a failed attempt's
after-hooks and test-fixture teardown, then worker cleanup, then trace
saving. It gives each of those its own slot of one test timeout (120s). So a
failed attempt can take up to about 480s, and in CI it took about 200-250s
(timestamps in the #519 server log). Three of them did not fit in 600s, and
the global timeout ended the run during the last attempt. With `--retries`,
the line reporter holds an attempt's error until the test is final, so
neither failure was ever printed.

**Reproduced, scaled down** (test timeout 8s, a teardown that uses its 8s
slot, a 30s budget). Both runs used the real Playwright and run.py:
- The old runner (`--retries=2`, one budget) came back `TIMED OUT` in 36s.
  Its output was exactly the CI shape: `[1/1]`, `[2/1] (retries)`, `Timed
  out waiting 30s for the test suite to run`, `1 failed` and no error.
- The new runner came back `RED` in 70s. Each attempt was 22s and failed
  with `Test timeout of 8000ms exceeded`, and each attempt's report was
  printed.

**Ruled out, each by a local reproduction** under run.py's own spawn
(`start_new_session`, `--reporter=line --retries=2 --global-timeout`):
- A hung fixture teardown: Playwright bounds each teardown
  (`Tearing down "stuck" exceeded the test timeout`, `Worker teardown
  timeout … exceeded`).
- A worker busy-looping, or stuck in a navigation: Playwright ended the
  run at its global timeout, and the orphaned worker and browser exited
  within 30s.
- The process-group spawn and `--global-timeout` themselves: every probe
  returned at the global timeout.
- A Chromium leaked by the outer `SIGKILL`: none was left.

**The stalls follow how many queue runs were in flight.** Same guards, same
runner code:

| Wave (queue runs created) | Runs | Green | Runs with E2E guards `TIMED OUT` (KB-95's excused 150s ones aside) |
|---|---|---|---|
| 20:25-20:43 (#518, #504, #506, #508, #510, #515) | 6 | 6 | 0 |
| 21:38-21:48 (#517, #520, #514, #511, …) | 5 | 1 | 1 (#511: 3 guards) |
| 22:30-22:39 (#532, #519, #520, #511, #525, #513, #527, …) | 8 | 2 | 4 (3-7 guards each) |
| 23:10 (#533, #519, #520, #521, #525, #513, #527, …) | 9 | 0 | every run |

Each job has its own VM, so this is contention on shared hosts, not
anything a run does to another. The fix does not depend on it. A stall
still fails an attempt, but each attempt is bounded and reported. How many
groups the queue builds at once (the ruleset's `max_entries_to_build`) is
the owner's decision.

### Fixed here (#533)

- `run.py` makes each E2E guard's attempts itself (`run_attempts`). There
  are three, each one `npx playwright test … --retries=0
  --global-timeout=300000`, with its output kept under `--- attempt N/3:
  passed|failed (Ns) ---`.
- The baseline is green if any attempt passes. After an attempt that failed
  only on time (the test timeout or a navigation timeout), it waits 30s
  before the next. This extends #533's navigation-timeout re-run.
- The rule for `RED` is unchanged: every attempt fails. The README now
  states that a failure on a timeout counts as a failure. An attempt that
  never finished is `TIMED OUT`, never `RED`.
- `KB-95 E1` loses `"timeout": 150` and `"known_flake"`. The 150s budget
  was the attempts-share-one-budget bug in miniature: its `TIMED OUT` at
  152-154s on green runs #506, #517 and #520.
- `--self-test` checks the command (`--retries=0`, a per-attempt budget).
  It also runs six scripted attempt sequences: every mutated attempt failing
  or timing out (RED after 4 commands), one passing (STAYED GREEN), three
  failed baselines (NOT GREEN), a baseline passing on its third attempt
  after two pauses, and an attempt Playwright ended (TIMED OUT, with the
  earlier attempts kept). Red without the fix: with `E2E_ATTEMPTS = 1` it
  fails `got … ('RED', None, 2, 0), expected ('RED', None, 4, 0)`, and with
  `--retries=2` it fails `an e2e guard command lacks --retries=0`.
- Run for real against a local dev server: `KB-7 E2E edit form opens
  empty` came back `RED` in 68s. With the server frozen (`SIGSTOP`) for
  150s during the baseline's first attempt, it came back `RED (216s)
  [baseline passed on attempt 3]`.
