## KB-181 — In-app notifications never arrive live: the Realtime channel joins without the user's token

> **Fixed in #579.** The notifications hook joins through
> `subscribeWithAuth` (`packages/supabase/src/realtime/subscribe-with-auth.ts`),
> which sets the user's access token on the Realtime socket before the
> channel joins.

**Severity:** Medium. With `NEXT_PUBLIC_REALTIME_NOTIFICATIONS=true` the
bell never fills while a page is open; the notification shows only after a
reload. The flag defaults to `false` (`apps/web/config/feature-flags.config.ts:105`)
and no deployment config in the repo sets it, so today the bug is latent:
the hook is not mounted. It bites the day the flag is turned on.
**Found:** FILM-1910, which hit the same fault on `generation_runs` and
fixed it there; the notifications hook was the other `postgres_changes`
subscriber.

### What happens

`useNotificationsStream` called `client.channel(...).on('postgres_changes', …).subscribe()`
without putting the session's access token on the Realtime socket first. A
channel joined that way joins as `anon`. Realtime evaluates the table's RLS
as `anon`, `notifications_read_self` matches no row, and every event is
dropped. The channel still reports `SUBSCRIBED`, so nothing looks wrong.

### How it was reproduced

Lane B local stack, supabase-js 2.57.4, a seeded user signed in with
`signInWithPassword`, a channel subscribed exactly as the hook did (filter
`account_id=in.(<user id>)`), two rows inserted with the service role:

```
{"mode":"no setAuth","status":"SUBSCRIBED","events":0}
{"mode":"setAuth","status":"SUBSCRIBED","events":2}
```

In the browser: the Playwright spec `notifications/notifications-live.spec.ts`
with the hook as it was on `main` fails at the first assertion, the bell
count never appears (`Received: <element(s) not found>`, 10s); with the fix
it passes and the count reads 1 then 2 without a reload.

### Fix

One helper, `subscribeWithAuth(client, buildChannel)`: it reads the current
session, calls `client.realtime.setAuth(token)`, then builds and subscribes
the channel, and sets the token again on every auth state change. The
notifications hook uses it. A repo scan
(`packages/supabase/__tests__/realtime-auth-guard.test.ts`) fails any source
file that opens a channel (`.channel(` or `postgres_changes`) without it.

Every Realtime subscription in the repo, found with `git grep` for
`.channel(`, `postgres_changes` and `setAuth` across `packages` and `apps`:

| Subscription | Status |
|---|---|
| `packages/features/notifications/src/hooks/use-notifications-stream.ts` | fixed here |

(FILM-1910's `generation_runs` subscription sets the token inline in its own
branch; it is not on `main` at the time of writing. The scan accepts any file
that goes through the helper, so that file should move onto it when both have
landed.)

### Acceptance criteria

- [x] A notification inserted for the user's account while a page is open
      appears in the bell without a reload, twice in a row
      (`apps/e2e/tests/notifications/notifications-live.spec.ts`; red on the
      old hook, green on the fix).
- [x] The channel joins only after the token is set, and the token is set again
      when the session changes (`packages/supabase/__tests__/subscribe-with-auth.test.ts`).
- [x] No source file opens a Realtime channel outside the helper
      (`packages/supabase/__tests__/realtime-auth-guard.test.ts`; red on the old hook).
