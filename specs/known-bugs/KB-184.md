## KB-184 — executeServerRun cannot run screenplay/shots/season_outline/dialogue_translation: their server writer lives in worker handlers

**Severity:** Low — latent. No product path opens a stage-input server run
for these four stages today, so no user meets it. The first one that does
fails every time, at the output schema, before a word is checked. **Found:**
FILM-1902 criterion 10, running every registered stage in server mode
against the FILM-1803 AI sandbox.

**What happens.** A server run whose input is a stage target is driven by
`executeServerRun` (packages/features/generation/src/runs/execute-run.ts),
which calls `run.write(brief)`. That is the gateway's server writer
(packages/ai-gateway/src/writers/server-writer.ts). It renders the brief's
one prompt through `executeLLMForLambda` and returns the prompt's reply as
the stage's output. For four stages, that reply is not the stage's output
shape, whatever the model writes:

| Stage | Brief's prompt returns | Stage's outputSchema wants |
|---|---|---|
| `screenplay` | `{ screenplay: { scenes, metadata } }` (screenplay-conversion) | `{ scenes }` per part |
| `shots` | `{ sceneAnalyses, … }` (reel-scout), `{ shots }` (scene-shot-generation) | `{ kind: 'reel_scout' \| 'scene', … }` |
| `season_outline` | the `episodes` array (the executor unwraps `wrapper_key`) | `{ episodes }` |
| `dialogue_translation` | numbered text lines (`output.type: text`) | `{ translations: [{ sourceDialogueId, text }] }` |

In the worker, server mode for these stages never reaches the plain writer.
Each job handler passes `runStage` its own `generate`, which runs the
stage's orchestrator from `@kit/episodes` and adapts the result to the
stage's shape. Seven handlers in apps/web/lambda/llm-worker/handlers/ do
this:

- `screenplay-conversion.ts` (`writeScreenplay`, then `splitScreenplayIntoParts`)
- `shot-generation.ts` (`orchestratedShots`, then `runOrchestratorForParts`)
- `season-outline.ts` (`runSeasonOrchestrator` over `seasonOutlineOrchestratorInput`)
- `translate-dialogue.ts` (`runTranslationOrchestrator`)
- `story-generation.ts` (`runStoryOrchestrator`)
- `story-ideation.ts` (`runIdeationOrchestrator`)
- `audio-cue-generation.ts` (`runAudioCueOrchestrator`)

The last three stages' prompts happen to return their stage's shape, so
the plain writer runs them. The first four cannot be run by it.

**Why it is latent.** MCP runs are always external
(`mcp_runs_are_external`; `mcpRunCtx` in
packages/features/studio-mcp/src/server/tools/generation/service.ts), so
they are finalized, never written. Queued jobs open `job`-input runs, which
go through the handlers above. Three things open stage-input server runs
today, and none of them is one of the four:

- `episode_summary` (`extractCanonChangesAction`)
- `asset_description` (asset-link-actions)
- `audio_cues`, as the shots stage's follow-on child

**Reproduced.** apps/vendor-sandbox/__tests__/stage-matrix-sandbox.test.ts
runs every registered stage through `executeServerRun` with the gateway's
writer against a started sandbox. The four stages are rejected as
`StageOutputRejected`, with Zod codes only: `scenes invalid_type
(Required)`; `kind invalid_union_discriminator`; `<root> invalid_type
(Expected object, received array)`; `<root> invalid_type (Expected object,
received string)`. The test pins them in `SHAPE_GAP`, and fails when one
passes or fails another way.

**Proposed fix (option B).** Give a stage its server-mode generate, beside
`prepare`/`check`/`commit`: the orchestrator call and the adaptation each
handler now holds. The gateway's server writer uses it when the stage has
one, and the plain prompt when it does not. The seven handlers then call
`executeServerRun`'s path instead of carrying their own `generate`, and the
code that lives only in apps/web/lambda moves to where the stage, the
worker and the sandbox leg can all reach it. The owner decides whether it
lands in Phase 19.

**Acceptance criteria.**
- A stage-input server run of each of the four stages commits through
  `executeServerRun`, against the AI sandbox.
- `SHAPE_GAP` in stage-matrix-sandbox.test.ts is empty and removed, and the
  leg's passing set is every registered stage.
- The worker's job path and the stage-input path share one generate per
  stage; no handler keeps an orchestrator call of its own.
