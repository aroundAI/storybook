## KB-176 — Opening any app page whose URL carries error_description signs the user out in the browser

> **Fixed (2026-10-04), #TBD-KB176.** `getSupabaseBrowserClient` now turns
> `detectSessionInUrl` off on the client's auth object right after creating it,
> so a URL's `error_description` (or `access_token`, or `code`) is only a query
> parameter. The proposed fix, passing `auth: { detectSessionInUrl: false }`,
> does nothing: `@supabase/ssr` 0.7.0 `createBrowserClient` spreads the caller's
> `auth` options and then sets `detectSessionInUrl: isBrowser()` itself (red run
> with the option in place: 2 failed, cookie gone). Nothing relied on the
> detection: the code exchange is `/auth/callback`, server-side, and the real
> callback error page still renders. Covered by
> `apps/e2e/tests/authentication/url-error-params.spec.ts`, red without the fix.

**Severity:** Medium. A signed-in user who lands on any StoryBook page with
`?error=…&error_description=…` in its URL (a vendor's OAuth error redirect,
a link someone pasted, a bookmark) is silently signed out: the next
navigation goes to `/auth/sign-in`. Nothing in `main` today produces such a
URL for its own pages (the platform callbacks keep the vendor's
`error_description` inside a JSON body, `apps/web/app/api/platforms/callback/*/route.ts`),
so it needs a third party or a hand-typed URL; it affects every signed-in
page and the 404 page alike. **Found:** FILM-1907 (#563), driving the OAuth
consent flow through a page of our own as the test client's callback.

### What happens

The browser Supabase client (`@supabase/ssr` `createBrowserClient`,
`packages/supabase/src/clients/browser-client.ts`) runs auth-js with its
default `detectSessionInUrl: true`. On initialisation auth-js
(`@supabase/auth-js` 2.71.1, `GoTrueClient.js:1356`) treats the page URL as
an implicit-grant auth callback whenever it carries `access_token` **or
`error_description`**:

```js
_isImplicitGrantCallback(params) {
  return Boolean(params.access_token || params.error_description);
}
```

It then reads the URL as a failed login (`:1270`, any of `error`,
`error_description`, `error_code`), and, as for every failed login attempt
through a URL, removes the stored session (`_removeSession()` in
`_initialize`): the `sb-<ref>-auth-token` cookie is cleared from the
browser. The server never sees a sign-out; the next request simply arrives
without the cookie and the middleware redirects to sign-in.

### How it was reproduced

`main` @9703798c5, a dev server on lane B (port 3211), a seeded user signed
in with `signInAs`, cookies read with `context.cookies()` after each step
(a probe spec, not committed):

```
after sign-in                      [ 'sb-127-auth-token(2757)' ]
goto /home/<slug>/settings/platforms?error=access_denied&error_description=The+user+denied+the+request
after ?error_description page      http://localhost:3211/   []
goto /home/<slug>/settings
final                              http://localhost:3211/auth/sign-in?next=/home/<slug>/settings   []
```

The same with the 404 page (`/this-page-does-not-exist?error=x&error_description=y`):
cookies gone, next navigation on sign-in. Without `error_description`
(`/this-page-does-not-exist?one=1`, twice, and the same through a 307
redirect) the cookie survives and the next navigation stays signed in.

In FILM-1907's first Playwright run the symptom was a 401 from PostgREST on
the 404 page: the page's `accounts` query went out with the anon key,
because the session had just been removed by the URL parse.

### Proposed fix

The app never completes an auth flow by reading the page URL on an
arbitrary page: the implicit flow is not used, and the PKCE code exchange
happens on `/auth/callback` server-side. Create the browser client with
`auth: { detectSessionInUrl: false }` (the admin clients already do,
`server-admin-client.ts:25`; the banner says why that is not enough here), or scope detection to `/auth/*` only. Then
a URL's `error_description` is just a query parameter.

### Acceptance criteria

- [x] A signed-in user who opens `/home/<slug>/settings?error=x&error_description=y`
      and then navigates to `/home/<slug>/settings` is still signed in
      (Playwright, cookies measured, not the page).
- [x] The same for a 404 URL carrying `error_description`.
- [x] Sign-in, sign-up, password reset and the MFA challenge still work
      (`authentication/*.spec.ts`).
