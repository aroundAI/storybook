## KB-200 — The deploy log says every ClickHouse migration ran, and nothing stopped an emptied _migrations from re-dropping the metrics

> **Fixed (2026-10-19), #679.** `scripts/deploy.sh` §5b now runs
> `packages/clickhouse/src/migrations/run.ts` once and its output is the
> log. The runner's logic moved to `runner.ts` (`runMigrations`), which
> throws `MigrationBaselineError` and applies nothing when `_migrations` is
> empty but the database has tables; `run.ts --baseline` records every
> migration as applied without running it, and deploy.sh never passes it.
> `002_metrics_v2` skips its `DROP TABLE video_metrics` when the table holds
> rows. Tests: `packages/clickhouse/__tests__/run-guard.test.ts` (red on
> main), mutation guards `tooling/mutation-guards/kb-200.json`.

**Severity:** Medium — no data was lost: every deploy printed a false
"applied" line per migration file, and one lost `_migrations` table away
from dropping the production metrics. **Found:** the owner read the deploy
log and asked whether each deploy deletes ClickHouse data.

### What happened

- `scripts/deploy.sh` §5b listed `packages/clickhouse/src/migrations/*.ts`
  and ran each with `npx tsx`, printing `✓ <file> applied` when it exited 0.
  `001_…ts` to `025_…ts` only export a `migration` object, and
  `migration-types.ts` only a type, so running them did nothing; the
  "applied" lines were false. `run.ts` was also in the list and is the only
  file that applies anything: it records each migration in `_migrations`
  and skips the recorded ones, which is why no data was deleted.
- `run.ts` treated an empty `_migrations` as a fresh database. If the table
  were lost or emptied while the data tables existed, the next deploy would
  replay 001–025, and `002_metrics_v2` starts with
  `DROP TABLE IF EXISTS video_metrics`.

### Reproduced (local ClickHouse 24.8, scratch database)

- On main, the deploy loop's per-file "applied" lines are printed for files
  that only export SQL (read from `deploy.sh`; `npx tsx 001_create_tables.ts`
  exits 0 having sent no query).
- With the fix: a fresh scratch database applies 25 migrations, a second run
  skips all 25; with a row in `video_metrics` and `_migrations` truncated,
  the runner refuses (exit 1), `video_metrics` keeps its row and nothing is
  recorded; `--baseline` records 25 without running, and the next run has
  nothing to do. Running 002 directly over the populated table logs
  "video_metrics holds rows — not dropping it" and keeps the row.

### Acceptance criteria

- [x] deploy.sh runs the runner once and loops over no migration file
- [x] an empty `_migrations` over existing tables refuses and applies nothing
- [x] `--baseline` records without running; deploy.sh never passes it
- [x] 002 does not drop a `video_metrics` that holds rows
