## KB-211 — Every YouTube video's hourly analytics sync failed: YouTube refused the per-video country query

> **Fixed (2026-10-20), #690.** `fetchGeography` no longer asks for
> `viewerPercentage`: it asks `views,estimatedMinutesWatched` by `country`
> and computes each country's share of views (`countryShares`). A refusal of
> the traffic-source or geography query now costs only those figures
> (`optionalQuery`: a `youtube-analytics.query-refused` warning naming the
> query, the figures stored as not reported), and every `reports.query`
> failure is a `YouTubeAnalyticsQueryError` whose message names the query
> and its dimensions, metrics, filters, sort and maxResults (never the
> token). The vendor sandbox now refuses a metric outside its report's list
> (`reportServes`), so CI would have caught it. Tests:
> `packages/features/content-analytics/__tests__/youtube-analytics.test.ts`
> "a refused query (KB-211)" (5 tests, red on main) and
> `apps/vendor-sandbox/__tests__/google-fidelity.test.ts` "each report
> serves only its own metrics" (red without the sandbox change).

**Severity:** High. No YouTube analytics were stored for any published
video once KB-203 (#682) switched analytics on in production: no views,
watch time, retention or traffic sources, so the morning report (FILM-1735)
showed YouTube as not measured.

**Found:** 2026-10-19, production CloudWatch, after the YouTube Analytics
and Reporting APIs were enabled in the Google Cloud project: every hourly
run logged, for each published YouTube long video,
`analytics-sync-cron "Analytics sync failed" platform=youtube error="The
query is not supported. Check the documentation at
https://developers.google.com/youtube/analytics/v2/available_reports for a
list of supported queries."`

**Cause:** `getVideoAnalytics` runs ten `reports.query` calls in one
`Promise.all`. Each was checked against the channel reports reference
(developers.google.com/youtube/analytics/channel_reports, read 2026-10-20):

| Query | Shape | Verdict |
|---|---|---|
| daily metrics | `day`, video filter, views … subscribersLost | Supported (time-based report) |
| engagedViews | `day`, video filter | Supported; already optional (KB-50) |
| revenue | `day`, video filter, three revenue metrics | Supported; already optional |
| traffic sources | `day,insightTrafficSourceType`, views, watch time | Supported (traffic source report) |
| **geography** | `country`, views, watch time, **viewerPercentage** | **Not supported**: `viewerPercentage` is the demographics report's metric, served only beside `ageGroup`/`gender`; the "User activity by country" report does not list it |
| retention | `elapsedVideoTimeRatio`, video filter | Supported (`audienceType` optional); already caught |
| age, gender | `viewerPercentage` | Supported; already caught |
| device, OS | views (+ watch time) | Supported; already caught |
| city | views, `sort=-views`, `maxResults=50` | Supported (sort and ≤ 250 required); already caught |
| subscribed status | views | Supported; already caught |

Geography was one of three queries with no `catch` (with the daily metrics
and traffic sources), so its 400 rejected the whole `Promise.all`. The
vendor sandbox served any metric beside any single dimension, so the
sandbox-driven tests passed it. The error named no query, which is why the
log alone did not say which one.

The share stored in `video_audience.percentage` for a country is now the
country's share of the video's views (all countries are asked, then the top
25 kept), not YouTube's share of signed-in viewers, which this query could
never return.

**Facebook "views" not reported (checked in the same pass):** the producer
saw Facebook watch time arrive while "views" stayed not reported for both
long videos. That is by design, not a deprecated metric: a Facebook row's
`views` is NULL (migration 020, KB-153) because Facebook counts kinds of
view, each stored as its own figure (`views_3s` from `total_video_views`,
`complete_views`, `plays` from `blue_reels_play_count`). `total_video_views`
is current in Graph v26.0 (the v25.0 deprecations in
`docs/platform-capability-reference.md` retire only its `_unique` variants,
naming `total_video_views` as their replacement), and it travels in the same `video_insights` request as
`total_video_view_total_time`, so watch time arriving means that request
succeeded. What was wrong was the report's reason: "Not reported by
Facebook for this video yet." read as Meta's delay. `nullReason` now says
Facebook has no single views figure and points at `fbViews3s` and
`fbViewsComplete` (`daily-digest.test.ts`). If `fbViews3s` itself stays null
after 24 hours, that is Meta's processing and the next thing to look at,
with a Page token, outside this repo.

**Not done:** retention, demographics, device, OS, city and subscribed
status still swallow any failure silently (`catch {}`), as before; they
never failed the sync, but a refused one leaves no log line. Closed by
KB-212 (#691): they go through `optionalQuery` too.
