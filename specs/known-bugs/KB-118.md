## KB-118 — The voice worker writes a dialogue line by id without checking it belongs to the job's episode

> **Fixed (2026-09-25), #393.** `processDialogueVoiceGeneration` reads the
> line's `episode_id` first and refuses (`DialogueLineRefused`) unless it is
> the job's episode, before the key is read or anything is written; the three
> `dialogue_lines` updates also filter on `episode_id`. Red on `main` in
> `apps/web/lambda/voice-worker/__tests__/line-in-episode.test.ts` (3 of 3).

**Severity:** Low — every producer derives the line from the episode it
authorised (KB-46), so no known path sends a mismatched pair; this is the
worker's own check. **Found:** worker-authz, auditing the voice worker for
KB-49 (#384).

`apps/web/lambda/voice-worker/voice-generation.ts` wrote `dialogue_lines` by
`id` alone (status `generating`, the audio and metadata, then `failed` on
error), on the service-role key. The worker checks that the job's user can
write the job's episode (KB-49), but not that the line is in that episode: a
job naming an authorised episode and another project's line would spend the
payload account's key and overwrite that line's audio.

**Reproduced** with the real handler and a client that answers like the
database (`line-in-episode.test.ts`): on `main`, a line of another episode is
written (status `generating`, then `failed`), and the key lookup runs.

### Acceptance criteria

- [x] A line of another episode, or none, is refused before the key is read or the line written
- [x] Every write to the line is scoped to the job's episode
- [x] Mutation guards (VS4, VS5)

A refused job is still thrown, so SQS retries it and it dead-letters; #384's
acknowledged-refusal path (`QueuedJobRefused`) is where it could join.
