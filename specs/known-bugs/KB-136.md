## KB-136 — The audio library tests fail on a hidden copy of the page; users see one card

> **Fixed (2026-09-28), #459. Not what it looked like.** A traced failure
> (2 of 70 runs) showed the second card inside `<div hidden id="S:4">`: a
> copy of the page React streams from the server and normally moves into
> place, left behind here. The accessibility snapshot of the same page lists
> **one** card, so no user saw a double upload. The strict test locators
> matched the hidden copy too. Every audio-library card, upload-button and
> track-name locator (three specs, eight sites) now takes
> `.filter({ visible: true })`. Measured with no retries: 140 of 140 (the two
> specs 20 times each), against 2 failures in 70 before.
>
> **Not fixed here:** why React leaves that hidden container behind. It is
> invisible and inert, so it costs nothing a user can see; it is recorded so
> a strict locator elsewhere is not puzzled by it again.

**Severity:** Low. The track is stored once. The page shows it as two identical
cards until the next load, which reads as a double upload. **Found:**
2026-09-28, looking into why `media-storage.spec.ts › the owner uploads two
tracks in a row…` needed a retry in 3 of 30 local-CI runs.

### Seen (2026-09-28, production build)

`getByText('Opening theme 1790557546528')` resolved to two identical
`<h3 class="truncate text-sm font-medium">` elements, while `audio_assets`
held one row for that name. An earlier run of the same spec failed because
`[data-test="audio-library-upload"]` resolved to two elements.

`upload-audio-dialog.tsx` calls `onSuccess` once per submit, and
`audio-library-client.tsx` drops an added track once the server list has it.
It does not dedupe within its own `added` list. The two-upload-buttons
failure suggests the library client itself sometimes renders twice. Not yet
root-caused.
