## KB-88 — Public sharing pages are a 404 for anyone not signed in

> **Fixed (2026-09-25), #357, with KB-85.** `apps/web/supabase/migrations/20260925083724_kb85-kb88-anon-public-pages.sql` grants `anon` USAGE on
> `public`, last, after KB-85's revokes. Public pages no longer read the base
> tables:
>
> - **Lists** read `public_projects` and `public_episodes`, owner-rights,
>   read-only views in the KB-60 shape. They hold **public rows only**
>   (a public team's public project; a live, non-private episode of one) and
>   **only the columns the pages render**. `projects.metadata` is cut to the
>   three keys the page reads, so studio settings (canon, providers) stay
>   private.
> - **Links** open through `get_shared_project`, `get_shared_episode` and
>   `get_shared_project_episodes`: SECURITY DEFINER, `search_path = ''`, exact
>   key only. They open public **or unlisted** rows, so "Unlisted — only
>   people with the direct link" is true: an unlisted project can be fetched
>   by its link and listed nowhere (owner decision, 2026-09-25).
> - Both read one rule, `kit.shareable_projects` / `kit.shareable_episodes`.
>
> **The public-read policies on `projects` and `episodes` are dropped**
> (owner decision). They let any signed-in user read every column of a public
> or unlisted project and its episodes, soft-deleted ones included, and list
> the unlisted ones (#346's lead). Signed-in strangers now read the views,
> like everyone else. **Behaviour change:** `linkAsSequel`
> (`packages/features/episodes/src/lib/canon/sequel-system.ts`) could link a
> project as the sequel of *another account's* public project, reading that
> project's `metadata` through those policies. It now finds only projects
> the caller is a member of, and says "Project not found" otherwise.
>
> Public reads now log a failed read (with the PostgREST code) instead of
> turning it into a silent 404, which is how this bug hid.
>
> **The sitemap was not frozen at build time.** The EDD suspected it, because
> `next build` writes a `sitemap.xml.body`. Checked red first on `main`'s
> production build: the route is dynamic and runs per request (the running
> server logged `permission denied for schema public` for each fetch), so
> the missing slugs were this bug alone. No `force-dynamic` was added.
>
> Five older tests assumed the old reach and were updated deliberately:
> `schema.test.sql` (anon now has USAGE), `personal-accounts.test.sql` (the
> refusal is now the table's), `project-assets-storage-rls.test.sql` and
> `research-uploads-rls.test.sql` (a public project's row is no longer
> readable by strangers), `readonly-viewer-reach.test.sql` (the two new views
> join `public_accounts` as public-by-design); and three E2E specs that made
> a project public to make it readable now read it through `public_projects`
> or `public_episodes`.

**Severity:** Medium — no data is exposed, but the feature does not work for
its audience. Every `/@company` page, and the project and episode pages under
it, is a 404 to a visitor who is not signed in, and so to search engines; the
sitemap has no public URLs for them either. **Found:** KB-60's planning,
2026-09-24. **Open** — scheduled by the lead, not fixed in the KB-60 PR.

`anon` has no USAGE on schema `public`: the baseline grants it only to
`authenticated` and `service_role` (`20221215192558_schema.sql:77-80`), and no
later migration grants it. So PostgREST refuses every anonymous read before
any policy runs, including the `TO anon` public-read policies on `projects`
and `episodes` (`20260108120000_public_sharing_rls.sql`). The public queries
turn any error into `null`, so the page calls `notFound()`. This contradicts
`specs/PRD-public-sharing.md` ("Basic rendering without auth").

### Reproduced (local stack, 2026-09-24)

| Request | Result |
|---|---|
| `GET /rest/v1/accounts?select=id,name,slug&public_profile->>is_public=eq.true` with the anon key | `401 {"code":"42501","message":"permission denied for schema public"}` |
| `select count(*) from public.accounts` as `anon` (SQL) | `ERROR: permission denied for schema public` |
| A public team (`public_profile.is_public`, a public project and a released episode, seeded by `apps/e2e/tests/public-sharing/public-pages.spec.ts`), opened **signed in** as a stranger on a production build (`build:test` + `next start`) | `200`, the company page renders |
| The same `/@<slug>`, **logged out**, same build | `404` |
| `/sitemap.xml`, same build | the team's slug does not appear |

### Proposed fix

Grant `anon` USAGE on `public` and SELECT on exactly what public pages read:
`public_accounts` (KB-60 made it; it already holds the grant), and `projects`
and `episodes` through their public-read policies. First sweep every `anon`
table grant. `anon` holds every privilege on `accounts`, and a write privilege
on 64 of the 86 public tables (measured 2026-09-25, on `main` after #338, #342 and #348), by Supabase's defaults.
Today only the missing schema USAGE hides them, so
granting USAGE without revoking those first would open writes wherever a
policy permits them.
