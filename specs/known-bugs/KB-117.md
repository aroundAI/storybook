## KB-117 — A client navigation can hang forever: the create-project form stays frozen after the project is saved

> **Fixed in part (2026-09-25), #394.** The eight places that navigate after a
> server action (project create, both project deletes, the YouTube channel
> picker, two social-post actions, the episode wizard and add-fact) now call
> `navigateWithFallback` from `@kit/next/navigation`. It pushes softly, and if
> the address still shows the starting page after 5s it does a hard navigation,
> which cannot take the path below. Nobody is left on a frozen form any more.
> **The cause is not fixed:** the router still stalls at the same rate, it just
> no longer strands the user. The rest of this entry, the root cause and
> vercel/next.js#83386, stay open.

> **Cause found; left as it is (owner, 2026-09-30).** The upstream issue
> (vercel/next.js#83386) was closed in February 2026 as a React bug, fixed by
> facebook/react#35839: a Suspense boundary that suspends during a client
> navigation could stay stuck, because context propagation could not find the
> consumer fibers of a discarded subtree. The fix is in React 19.3.0 (released
> 2026-09-09) and was not backported to 19.2.x. Next.js 15.5 bundles its own
> React (19.2.0-canary, 2025-08-18, the same in 15.5.3 and 15.5.26, whose
> `serverPatchReducer` is also identical), so upgrading within 15.5.x changes
> nothing. The only Next line that bundles React 19.3 is Next 16 (16.3.7 bundles
> a 2026-07-31 canary), a major migration on an SST/OpenNext 3.8 deploy whose
> OpenNext support was not checked. The owner chose to leave it: #394's fallback
> already lands the user on the new page. Reopen it with a Next 16 migration
> for its own reasons; this bug goes with it. Seen again on 2026-09-30: a
> client-side click from `assets?tab=location` to `?tab=character` stalled about
> one time in six in `sidebar-active.spec.ts`, which navigates by address for
> that step for this reason.

**Severity:** Medium. It affects every creator who creates a project, about 1
creation in 6 on a local production build. The project **is** saved, but the
page never leaves the form, every field stays disabled ("Creating..."), and no
error appears. The only way out is a reload; retrying the form instead gets "A
project with this name already exists". No data is lost or corrupted.
**Found:** task #21, the flaky `apps/e2e/tests/projects/create-film-project.spec.ts`
(ci-hygiene, 2026-09-25). The spec is right and its wait is not the problem:
the product hangs.

### Reproduced

On a `build:test` of main (`8e532cf7`), `next start`, Playwright with `CI=1`,
one worker, no retries:

| Run | Stalled |
|---|---|
| the spec, `--repeat-each=15` | 4 / 15 |
| the spec, `--repeat-each=8` | 2 / 8 |
| a probe that watches the URL for 120s after **Create** | 1 / 12, **stuck all 120s** |
| probe, 3s pause before the click (not a page-load race) | 2 / 20 |
| probe, `experimental.clientSegmentCache: false` (not the segment cache) | 7 / 30 |
| probe, `router.push` moved **out of** the form's async `startTransition` (plain state instead) | 13 / 55 (baseline 9 / 55): not the cause |
| **no server action at all:** seed a project, open `/studio/projects/new`, call `window.next.router.push` to the project | **6 / 25** |

The last row matters most: **the create action is not involved.** Any client
navigation from `/studio/projects/new` to a project's studio page can hang. The
create form is simply where users meet it, because it is the one place that
always navigates there. Seven other components call `router.push` after an
`await` in the same way (both `delete-project-dialog.tsx`, `channel-picker.tsx`,
`social-posts-dashboard.tsx`, `create-episode-wizard.tsx`, `add-fact-form.tsx`).
Whether they can hang depends on the target route, not on their own code.

### What is stuck

Measured in the stuck state:
- **The network is done.** Both RSC requests for the target (one with a
  `Next-Url` header, one without) return 200 and **finish** in ~60 ms at normal
  sizes (≈4.4 KB and ≈15.3 KB). Every JS chunk loads. No stylesheet is pending.
  The studio layout's cinema-fonts `<link>` is not even in the DOM, which rules
  out a suspensey stylesheet.
- **React's own state** (FiberRoot, read from `document`'s container key,
  3 stuck runs):
  `pendingLanes == suspendedLanes` (transition lanes), `pingedLanes = 0`,
  `cancelPendingCommit = null`, `callbackNode = null`. The navigation's render
  **suspended on a promise that never resolved**, and React scheduled no more
  work. It is not a finished render waiting to commit.
- **Nothing commits:** no URL change, and not even the target's `loading.tsx`
  skeleton. So the suspension sits above that boundary: in the router or in
  `studio/[projectSlug]/layout.tsx`.

### Mechanism (read from Next 15.5.3; the upstream fix is not confirmed)

`next/dist/client/components/layout-router.js`, `InnerLayoutRouter`:
1. When a segment's `rsc` is missing after a navigation, it starts a lazy
   refetch (`fetchServerResponse` **without** `nextUrl` when the tree has no
   interception route). That is the second RSC request seen above, in passing
   runs as well as stuck ones.
2. When the refetch resolves, it dispatches `ACTION_SERVER_PATCH`, and
   meanwhile `use(unresolvedThenable)`: a promise that **never resolves by
   design**, on the assumption that the patch re-renders another part of the
   tree.
3. `router-reducer/reducers/server-patch-reducer.js` returns `state`
   **unchanged** when `applyRouterStatePatchToTree` says the patch "is not
   applicable to the current tree". Its comment: *"Previously this case
   triggered an MPA navigation but it should be safe to simply discard the
   server response."*

When step 3 discards the patch, nothing re-renders the suspended navigation,
and it waits forever on `unresolvedThenable`. That is exactly the
`pingedLanes = 0`, no-callback state measured. The same symptom (RSC 200, no
navigation, intermittent, `redirect()` doesn't help) is open upstream as
[vercel/next.js#83386](https://github.com/vercel/next.js/issues/83386), with no
root cause or fix there.

### Not yet known (next step)

**What changes the router tree between the navigation and its lazy patch,**
so that the patch is judged inapplicable. No app-wide `router.refresh()` or
`router.replace()` runs on `/studio/projects/new`, and the Supabase auth
listener only does hard reloads. Next probe: in the stuck state, read
`InnerLayoutRouter`'s `cacheNode` (`rsc`, `lazyData`) from the WIP fiber for
the `[projectSlug]` segment, and log every router action the app dispatches
(wrap `window.next.router`) between **Create** and the stall. Also worth
checking: whether a later Next 15.5.x changes `serverPatchReducer`.

### Proposed fix

- **Mitigation, ours:** one shared helper for "navigate after an action". It
  calls `router.push`, and if the URL has not changed within a few seconds,
  falls back to `window.location.assign(url)`: a hard navigation, which cannot
  hit this path. It should replace the eight hand-written `router.push` calls
  above, so the form can no longer be left frozen. It treats the symptom; keep
  this entry open for the cause.
- **Cause, upstream:** report the measurements above on #83386, or fix it in
  our Next version if a later 15.5.x already has.

### Acceptance criteria

- The same probe (create → watch the URL) on a production build: **0 stalls
  in ≥55 runs**, against the baseline of 9/55.
- `create-film-project.spec.ts` passes `--repeat-each=20` with `CI=1`, with its
  wait unchanged.
- A creator whose navigation stalls still lands on the new project's page,
  without reloading.
