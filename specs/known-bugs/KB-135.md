## KB-135 — A changed team role often does not show on the members page until a reload

> **Fixed (2026-09-28), #455.** The members table shows the change the
> server confirmed for your own action (the new role, or the removed row)
> while the page's list still has the value it replaced; once the list
> catches up, or someone else changes that member, the list wins. The same
> pattern as the audio library (KB-79, KB-95). Measured with no retries on a
> production build: the role test **20 of 20** (main: 3 of 8), the whole
> spec file 5 times with the ownership transfer 5 of 5.
>
> **What was found.** A traced failure showed the role-change action's own
> response already carried the new role (four `"owner"`, no `"member"`), and
> the badge still read "Member" 10 s later. The data was right; the refreshed
> list was not applied to the page. Adding `router.refresh()` after the
> action did not fix it (14 of 20). Why Next's router drops that update was
> not found.
>
> **Also in #455:** the page object waits for the dialog to close (the action
> succeeded) instead of for the URL it is already on, and the fixed
> `waitForTimeout(1000)` is gone. `unauthorized user cannot access team
> account` failed 5 of 5 on the same server with `page.goto:
> net::ERR_ABORTED`: the page it visits redirects before its load event. It
> now returns on commit and lets the URL assertion wait (5 of 5).
>
> **Ownership transfer, #458.** A transfer changes two rows and the viewer's
> own permissions, so the confirmed-change override does not fit it. It passed
> 5 of 5 locally but needed a retry in the #452, #454 and #455 runs, the same
> stale page. After a confirmed transfer the dialog now reloads the page from
> the server, and the test waits for that load instead of a URL it is already
> on (and its fixed 1 s sleep is gone). Measured on lane B, 20 runs each, no
> retries: without the reload 9 of 20 passed, with it 20 of 20.

**Severity:** Medium. An owner changes a member's role, the change is saved,
and the members page keeps showing the old role, so the owner reasonably
concludes it failed and may try again. **Found:** 2026-09-28, looking into why
`team-accounts.spec.ts › owner can update a team member's role` needed a retry
in 7 of 30 local-CI runs.

### Reproduced (2026-09-28, main `98eff878`'s code, production build)

The test was run 8 times with no retries, logging the badge and
`accounts_memberships.account_role` for the member at 0 s, 1 s and 10 s after
the update. **5 of 8 failed**, and in every failure the database already said
`owner` at 1 s while the badge still read "Member" at 10 s, with no reload.

- `updateMemberRoleAction` calls `revalidatePath('/home/[account]', 'layout')`.
- The members page loader reads `get_account_members` directly (no cache).
- `AccountMembersTable`'s cells read `row.original`.

So the refreshed server payload is not applied about half the time. Not yet
root-caused.

The test also hides it: the page object's `waitForURL('**/home/*/members')`
resolves at once (the page is already there), so `updateMemberRole` returns
before the action finishes, and a fixed `waitForTimeout(1000)` stands in for a
real wait.

### Acceptance criteria

- [x] The members page shows the new role after a change, without a reload,
  every time: the spec passes 20 of 20 with no retries
- [x] The page object waits for the action, not for a URL it is already on
