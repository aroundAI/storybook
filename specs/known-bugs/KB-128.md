## KB-128 — Reading a social post scans every account's RLS: 9s on 735 accounts, so the post page times out

> **Fixed (2026-09-28), #453, as KB-137.** The same read, the same policy and
> the same cause were filed a second time as KB-137, and #453 fixed them there:
> `20260928045249_kb137-policy-auth-uid-once.sql` rewrites `social_posts_select`
> (and fourteen more) with `(select auth.uid())`, evaluated once, in place of a
> bare `auth.uid()`. KB-137 measured the same one-row read at 4.0 s before and
> 1.4 ms after in `EXPLAIN ANALYZE`, and `kb137-policy-auth-uid-once.test.sql`
> fails on any such policy with a bare `auth.uid()`. This entry stayed open
> only because the two were not connected; found by the 2026-09-29 records
> audit.

**Severity:** Medium. On the shared local database it already breaks a page,
and the cost grows with the number of accounts on the platform, not with the
reader's. **Found:** KB-6, while proving a refusal on a production build
(2026-09-25).

**Reproduced.** The publishing refusal scenario
(`apps/e2e/tests/refusals/refusals.po.ts`) failed on two runs in a row,
4 of 4 attempts each: the social post page showed "Failed to load post /
Post not found". `getSocialPostAction` swallows the PostgREST error, so I
made the request by hand as the post's own owner, a real signed-in token
against PostgREST. Both the page's `select` and `select=id` returned
`57014 canceling statement due to statement timeout`.

Then `EXPLAIN ANALYZE` on the same read (one row by primary key, as
`authenticated`, with the statement timeout lifted) took **9,153 ms**, on a
database of 735 `accounts`, 349 `accounts_memberships` and 9 `social_posts`.
The same scenario passed on #355's and #356's runs, when the local database
had just been reset and held far fewer accounts.

**Why.** `social_posts_select`
(`apps/web/supabase/migrations/20260528121732_add-social-posts.sql:65`) is

```sql
account_id in (select accounts.id from accounts where accounts.id = auth.uid()
               union all
               select account_id from accounts_memberships where user_id = auth.uid())
```

That set is built once (a hashed subplan), which is right. But it reads
`accounts` and `accounts_memberships` as the caller, so their own RLS
applies, and the plan evaluates those tables' policy functions on **every
row**, before the cheap `id = auth.uid()` test:

- `is_mfa_compliant()`
- `is_super_admin()`
- `has_role_on_account(id)`
- `is_account_team_member(id)` / `is_team_member(…)`

Result: 735 + 349 rows each paid those calls to find the caller's one or
two. Which of the functions dominates was not measured, because the shared
database went down mid-investigation. That is the next step.

**Where else.** Any policy of the shape
`account_id in (select … from accounts … union … accounts_memberships …)`
pays this, and the cost scales with the platform's account count. Grep
before fixing: fix the class, not the instance.

### Proposed fix

Keep who can see what unchanged, and prove it with pgTAP, as KB-13 did.
Then do one of two things:

- test the caller's own accounts without re-entering those tables' RLS, for
  example with a `security definer` helper that returns the caller's account
  ids by `auth.uid()` alone and states its rule in its header; or
- make the cheap equality filter run first.

Measure before and after on a database seeded with a realistic account
count.

### Acceptance criteria

- [ ] Reading one social post as its owner takes milliseconds on a database with ≥1,000 accounts (EXPLAIN ANALYZE, before/after table)
- [ ] pgTAP shows the same readers before and after
- [ ] The publishing refusal scenario passes on the production build against that database
