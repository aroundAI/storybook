## KB-37 — Shared research-source registry: the "owner of any account" check

> **Fixed (2026-09-25), #398.** Reproduced first on main (`ddc5568a`): with
> the real actions and a caller whose only membership is owner of one team,
> `deleteExternalSourceAction` sent `update external_sources set is_active =
> false where id = <another project's source>` through the admin client with
> no project filter, and `addExternalSourceAction` inserted a row with no
> owner that every team's hub lists. Any signed-in user can become "owner of
> some team" with one `create_team_account` call. On production's migration
> sequence, a signed-in stranger could also read the name of a pre-fix upload
> (`paper1.pdf`) that KB-26 left with no project.
>
> Research sources now belong to a team (owner decision, 2026-09-25: "C,
> project focused. Research sources would be different for every different
> team"). Migration `20260925115518_kb37_team_owned_research_sources.sql`:
> every row is a **built-in** (`is_builtin`: the 12 seeded NewsAPI rows, read
> by all, written only by migrations, the only rows the aggregator searches),
> a **team source** (`account_id`: read by members, written by owners), a
> **project source** (`project_id`, with its project's team: read and written
> by project writers), or an **orphan** (a pre-fix row: readable by nobody).
> Write policies on `external_sources` are the rule. The actions use the
> caller's own client, return refusals as values, and no longer use the admin
> client. `requireAccountOwner` and the unused `updateExternalSourceAction`
> are deleted. Design: `specs/plans/KB-37-edd.md`.

**Severity:** High — a cross-tenant write: any signed-in user could change the
research sources every team sees, and deactivate another team's by id. No
one is exposed today only because the owner is the only account.
**Found:** KB-26 (2026-09-23), decision D3. **Fixed.**

Split out of KB-26's decision D3: writes to the shared research-source registry are allowed to the owner of any account, and an owner has no enforced MFA.

### After deploying (owner, production)

`paper1.pdf` (`84cd347c-8fb1-4fb4-89f7-cdbf3d5d0723`) is a pre-fix upload
with no owner. After the migration nobody can read it. The owner decided to
delete it (2026-09-25). Run after the deploy:

```sql
-- preview (read-only): one manual row, no team, no project, not built-in
select id, name, slug, provider_type, is_builtin, account_id, project_id, created_at
from public.external_sources where id = '84cd347c-8fb1-4fb4-89f7-cdbf3d5d0723';
select id, external_id, title, is_upload, project_id, length(content) as characters
from public.external_content where source_id = '84cd347c-8fb1-4fb4-89f7-cdbf3d5d0723';

-- delete (external_content.source_id also cascades)
delete from public.external_content
where source_id = '84cd347c-8fb1-4fb4-89f7-cdbf3d5d0723' and external_id like 'manual-%';
delete from public.external_sources
where id = '84cd347c-8fb1-4fb4-89f7-cdbf3d5d0723' and provider_type = 'manual'
  and not is_builtin and account_id is null and project_id is null;
```

No storage object exists for it: in 2026-06 an upload stored its text only.
Facts extracted from it are the project's own rows (`verified_facts`, cited by
name) and are not touched.
