## KB-113 — `manual_tasks` and `analytics_experiments.project_id` accept another account's rows

**Severity:** Low. Both need another account's UUIDs, and no reader acts on
the foreign row: nothing in the app reads or writes `manual_tasks`, and
`analytics_experiments.project_id` is only a filter on the caller's own
Change log list, read through RLS. **Found:** KB-98's class sweep ("a row
names another account's object and nothing checks it"), 2026-09-25.

The same class as KB-98 and KB-93: a foreign key does not run RLS, and these
insert policies check only the row's own `account_id`.

- `manual_tasks_create` is `has_account_access(account_id)`. It never looks at
  `publish_id` or `episode_id`.
- `analytics_experiments_create` is `has_account_access(account_id)`. It never
  looks at `project_id`. `connection_id` is already safe: it is a composite
  foreign key on `(connection_id, account_id)`.

**Reproduced** on a throwaway database built from main's 185 migrations, in a
rolled-back transaction, acting as `authenticated` for a user who owns team A
and is **not** a member of team T:

| Write | Result |
|---|---|
| `manual_tasks` in A naming T's `publish_id` and `episode_id` | accepted |
| `analytics_experiments` in A with T's `project_id` | accepted |

**Proposed fix:** the idiom `social_posts` uses since KB-98. Where the child
has `account_id`, a composite foreign key to the parent's `(id, account_id)`
binds every role. `publishes` and `episodes` have no `account_id` of their
own, so `manual_tasks` needs a `WITH CHECK` through the helpers KB-98 added,
or a new helper for publishes and episodes. Also include a pgTAP case per
column, and a count of existing rows before any cleanup.
