## KB-164 — LinkedIn calls send LinkedIn-Version 202401, which LinkedIn sunset on 2025-01-22

> **Fixed (2026-10-02), #TBD-LI. Resolved: LinkedIn removed.** The owner
> chose to remove LinkedIn (FILM-717) rather than move the pin: first
> "retire LinkedIn for now", then, the same day, delete it everywhere. The
> integration is gone: `LINKEDIN_REST_VERSION`, the provider, the worker's
> LinkedIn calls, LinkedIn's row in `VENDOR_API_PINS` and the capability
> reference. Nothing calls LinkedIn, so no header is sent. The version was
> never moved and no LinkedIn publish was verified; the criteria below
> belong to a return, FILM-718 (DEFERRED), not to this fix.

**Found:** 2026-10-01, recording each pinned vendor version's end date for
FILM-1723 ("the next expected deprecation date is recorded somewhere a person
will see it"). Unrated, because the effect could not be reproduced without a
LinkedIn token: if LinkedIn honours the header on the paths we call, every
LinkedIn publish fails; if it ignores it there, nothing is wrong today.

### What was reproduced

- Every LinkedIn request that sends a version sends `LinkedIn-Version: 202401`
  (`LINKEDIN_REST_VERSION`, `packages/shared/src/vendors/linkedin.ts`): the
  provider's `getHeaders()` (`linkedin-provider.ts`) and the publish lambda's
  text post (`apps/web/lambda/publish-worker/index.ts`), both to `/v2/...`.
- LinkedIn's [migrations table](https://learn.microsoft.com/en-us/linkedin/marketing/integrations/migrations),
  read 2026-10-01, lists 202401 with sunset date January 22, 2025, status
  Deprecated. The oldest active version is 202510 (until 2026-10-15); the
  latest is 202609 (until 2027-09-15).
- LinkedIn's [versioning page](https://learn.microsoft.com/en-us/linkedin/marketing/versioning)
  says "An error response is returned when the version header is deprecated
  (e.g., 202401)", and its [error responses page](https://learn.microsoft.com/en-us/linkedin/marketing/error-responses)
  gives the body: `426`, `NONEXISTENT_VERSION`, "Requested version yyyymmdd is
  not active".

### What could not be reproduced

Whether `/v2/` reads the header at all. LinkedIn documents it for
`https://api.linkedin.com/rest/`. An unauthenticated POST to `/rest/posts`,
`/v2/posts` and `/v2/ugcPosts`, with 202401 and with 202609 alike, returns
401 `EMPTY_ACCESS_TOKEN` (2026-10-01T19:10Z), so authentication is checked
before the version and the probe cannot tell.

### Proposed fix

Choose a version deliberately, as `linkedin.ts` asks: read the changelog
from 202401 to the current version for the endpoints we call (`/v2/assets`,
`/v2/ugcPosts`, `/v2/posts`, `/v2/userinfo`), then either set the header to an
active version or drop it from `/v2/` calls if LinkedIn confirms it is not
read there. Then run one LinkedIn publish against a real connection.

### Acceptance criteria

- [ ] `LINKEDIN_REST_VERSION` is an active version, or the header is removed
      from calls that do not read it, with the reason recorded
- [ ] The LinkedIn row in "Pinned vendor API versions"
      (`docs/platform-capability-reference.md`) and `VENDOR_API_PINS` carry
      the new version's end date, and `trackedBy` is cleared
- [ ] One LinkedIn publish verified against a real connection after the change
