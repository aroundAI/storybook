## KB-201 — ClickHouse migration 025 fails in production: it raises a setting the managed server forbids changing

> **Fixed (2026-10-19), #679.** `025_complete_collection.ts` no longer
> changes any server setting. Its `up` runs the three column statements,
> then reads the months that hold pre-025 traffic rows
> (`SELECT DISTINCT toYYYYMM(metric_date) … WHERE metric_source = ''`) and
> copies each month in its own insert (`copyLegacyTrafficMonth`), so no
> insert spans more than one partition; then it deletes the old rows and
> creates `channel_metrics_daily`. Tests:
> `packages/clickhouse/__tests__/migration-025-per-month.test.ts` (red on
> main: the setting was present and the copy was one insert). Reproduced
> and verified locally on ClickHouse 24.8 with a user whose profile makes
> `max_partitions_per_insert_block` READONLY: main's 025 failed with code
> 452 exactly as production did, leaving 001–024 applied and 025 half
> applied; the fixed 025 then applied from that state, copied three
> months of old rows to `reporting_api` (3 before, 3 after, none left
> under ''), created `channel_metrics_daily`, and a second run did nothing.

**Severity:** High — it blocked the production deploy (`scripts/deploy.sh`
stops when a ClickHouse migration fails).

**Found:** 2026-10-19, on `pnpm deploy:production`:

```
Applying 025_complete_collection...
❌ Migration failed: ClickHouseError: Setting max_partitions_per_insert_block should not be changed.
  code: '452', type: 'SETTING_CONSTRAINT_VIOLATION'
```

**State left in production:** ClickHouse runs statements one by one. 025's
three column statements ran (all `IF NOT EXISTS` / idempotent); the copy
was refused before writing a row; the delete and the table creation never
ran; 025 was not recorded in `_migrations`. No data was lost or duplicated,
and the deploy stopped before shipping application code.

**Cause:** FILM-1734 (#669) added the setting to get past the
100-partitions-per-insert limit on the local server (`fb916bf7b`). Local
ClickHouse allows changing it; the managed production server does not, and
nothing in CI runs migrations against a server with production's
constraints.
