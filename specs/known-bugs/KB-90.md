## KB-90 — The intro and thumbnail actions save any URL as the file

> **Fixed (2026-09-25), #PR.** Both actions now store only a URL for which
> `ownedStorageKey(storage, 'project-assets', url, folder)` returns a key:
> one this adapter issued, inside `projects/<P>/assets/intros/` for an intro
> (`projects/<P>/assets/` for its optional poster) and
> `episodes/<E>/thumbnails/` for a thumbnail. The folders come from the same
> module as the path builders the uploads use (`projectIntroFolder`,
> `episodeThumbnailFolder` in `@kit/storage/upload-paths`), and
> `deleteOwnedObject` now deletes by the same rule, so a row can only name a
> file its own delete may remove. Anything else is refused as a value and
> nothing is written. Rows saved before the fix are left as they are; a
> replace goes through the check. The same shape elsewhere — the publish
> request's own `thumbnailUrl`, which reaches the platforms — is KB-104.

**Severity:** Low. The storage side is contained by KB-54's fix (a delete
only touches the row's own folder), but a writer can make an intro or
thumbnail point anywhere. **Found:** KB-54 (2026-09-24). **Reproduced**
2026-09-24 against the real actions with a fake database (the
`replacement-deletes.test.ts` harness): `uploadProjectIntroAction` with
`videoUrl: 'https://attacker.example/page.html'` and
`uploadEpisodeThumbnailAction` with another project's cover URL both
returned `success: true` and saved that URL. Reproduced again on `main`
ddc5568a on 2026-09-25, the same way, before the fix.

The schemas accept any URL (`intro-actions.ts` `videoUrl: z.string().url()`,
`thumbnail-actions.ts` `thumbnailUrl: z.string().url()`). The render step
that stitches intros, and the publish step that sends thumbnails to the
platforms, would fetch whatever is saved there.

**Fixed** in #PR — see the banner.
