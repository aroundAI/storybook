## KB-109 — A publish row can name another account's platform connection, and the service-role workers use its token

> **Fixed (2026-09-25), #384 and #387.** #387 (KB-98) closed the database
> side: the `publishes` insert and update policies, both publishing-config
> tables, `short_publications` and `social_posts` refuse a connection of
> another account; `platform_connections.account_id` is frozen for signed-in
> callers; and existing publishes naming another account's channel had
> `platform_connection_id` cleared
> (`20260925120329_kb98-account-scoped-references.sql`, pgTAP
> `connection-account-scope-rls.test.sql`).
>
> #384, the application side: the
> publish worker refuses a publish or delete job whose connection belongs to
> another account than the episode's, and uses the row's connection, not the
> message's. `publishToAllAction`, `retryPublishAction` and
> `publishSocialPostAction` check `connection.account_id` against the episode's
> (or post's) account **before** `getAccessToken`, which decrypts on the
> service-role key and may refresh the token.

**Severity:** Medium — a user can have another account's channel used for an
upload or a takedown, but needs that connection's UUID, which RLS does not
show them. **Found:** KB-47's survey of the publish queue (worker-authz,
2026-09-25); the inline-action half by tag-scope's sweep for KB-98.

`publishes_create` and `publishes_update` check the caller's role on the
episode's project and nothing about `platform_connection_id`. The workers that
act on a publish run on the service-role key and read the connection's token
by that id.

**Reproduced** on `main` (`ddc5568a`), with main's 185 migrations in a
throwaway Postgres, as a user in their own personal project who knows another
account's connection id: they cannot read the connection (0 rows), but
`insert into publishes` naming it returns 1 row, `update … set
platform_content_id` to any video id returns 1 row, and `update … set
status = 'scheduled', scheduled_at = now()` returns 1 row, which the
`scheduled-publish` cron (`index.ts:171`) queues with that connection.
Unpublish would have deleted the chosen video from the other account's
channel.

The inline actions: `publishToAll`, `retryPublish` and `publishSocialPost`
called `getAccessToken(connectionId)` before anything checked the connection's
account. The only later check was a read through the caller's client, which
proves the caller can see the connection's account, not that it is the
episode's: a user in two accounts could publish one account's episode to the
other's channel. Red on `main` in
`packages/features/publishing/__tests__/publish-queue-authorization.test.ts`
("a channel of another account"): each action read the token.

### Acceptance criteria

- [x] The publish worker refuses a job whose connection is another account's (`apps/web/lambda/publish-worker/__tests__/job-guard.test.ts`, guards WA13, WA15)
- [x] The three inline actions refuse it before any token is read (guard WA11)
- [x] `publishes` insert/update refuse it (pgTAP) — #387, `apps/web/supabase/tests/database/connection-account-scope-rls.test.sql`
