## KB-196 — Two overlapping scheduled-publish runs can both send one post

> **Fixed (2026-10-15), #666.** The scheduled Lambda's claim
> (`apps/web/lambda/scheduled-publish/index.ts`) is now
> `update({ status: 'queued' }).eq('id', …).eq('status', 'scheduled')`
> with `.select('id')`. A run that gets no row back skips the post: another
> run claimed it. The in-process job (`process-scheduled-publishes.ts`)
> claims the same way. Its revert after a failed queue send only touches a
> row still `queued`. Test: `lambda/scheduled-publish/__tests__/index.test.ts`
> 'sends a post once when two runs overlap'. Without the status filter it
> sends `['p1', 'p1']`. Guard L1 in
> `tooling/mutation-guards/film-719-cadence.json`. Found while designing
> FILM-719.

**Severity:** Medium. A duplicate upload of a real video is what the
platforms' spam signals look for (FILM-719). It needs two runs to overlap.
The Lambda runs every 5 minutes with a 5-minute timeout, and EventBridge can
deliver twice.

### What happened

The run read up to 50 due rows with `status = 'scheduled'`. For each one it
set `status = 'queued'` filtered on `id` alone, then sent the job to SQS.
Two runs that read the same row before either updated it both updated it,
with no error, and both sent it. The publish worker uploaded each message.

### Reproduced

An in-memory `publishes` table, with two `handler()` calls run concurrently
against one due row, sent the row's id twice.
