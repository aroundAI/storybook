## KB-202 — Every scheduled publish of an R2-stored video fails: "That video isn't one of this project's files"

> **Fixed (2026-10-19), #681.** `sst.config.ts` gives the scheduled-publish
> Lambda `STORAGE_PROVIDER` (default `r2`) and `R2_PUBLIC_URL`, the same
> values the publish worker and the web app read. Test:
> `packages/shared/__tests__/lambda-storage-env.test.ts` finds every Lambda
> under `apps/web/lambda/` whose code checks storage URLs
> (`ownedEpisodeVideo`, `ownedThumbnail`, `publicUrlPrefix`, …) and requires
> both variables in its environment block; red on main for
> `scheduled-publish`, green with the fix.

**Severity:** Critical: nothing scheduled could publish. The first real
schedules (Fault & Frontier FF-001's long video on YouTube and Facebook,
due 02:10 IST on 19 Oct) were both marked failed.

**Found:** 2026-10-19 by the owner's producer session:

> That video isn't one of this project's files. Upload it again from the
> episode's publish screen.

**Cause:** `apps/web/lambda/scheduled-publish/index.ts` runs
`ownedEpisodeVideo` before queueing a due publish. That check compares the
video URL with `publicUrlPrefix(PROJECT_ASSETS_BUCKET)`, which reads
`STORAGE_PROVIDER` and, for R2, `R2_PUBLIC_URL`. The Lambda's environment
had only Supabase and the queue URL, so the provider defaulted to
`supabase` and the prefix became the Supabase storage URL, which no R2 URL
matches. It is not specific to MCP uploads: any R2-stored video scheduled
for later was refused. Publish now was unaffected (it runs in the web app,
which has both variables).

**After the fix is deployed:** posts already marked failed stay failed;
schedule them again.
