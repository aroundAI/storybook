## KB-185 — Claude's and ChatGPT's real CIMD documents are refused at /oauth/authorize

> **Fixed (2026-10-04), #599.** A client metadata document (or a DCR
> request) whose client can act as public — `token_endpoint_auth_method`
> `none`, or `none` among `token_endpoint_auth_methods_supported` — is
> registered as public with only the grants we issue, provided
> `authorization_code` is among its grants. A client that can only
> authenticate is refused on our page with `invalid_client` naming its
> method. A `client_assertion`, `client_secret` or Authorization header at
> `/oauth/token` or `/oauth/revoke` is refused with `invalid_client`, never
> ignored. PKCE S256 and exact redirect matching are unchanged. The two
> documents are committed as fixtures
> (`packages/features/studio-mcp/__tests__/oauth/fixtures/*.2026-10-04.json`);
> the vendor sandbox serves them to a local app (`VENDOR_URL_CLIENTDOCS`),
> so E2E needs neither vendor. A cached document is fetched again once it is
> a day old, keeping the cached copy if the refetch fails, so a vendor's
> rotated redirect URIs take effect.

**Severity:** High — every Claude and ChatGPT user adding the connector with
the client's default settings. **Found:** FILM-1911, checking ChatGPT
compatibility after the owner's 2026-10-04 decision.

We advertise `client_id_metadata_document_supported: true` and `none` among
`token_endpoint_auth_methods_supported`, so both clients present their
published document URL as `client_id`. Fetched 2026-10-04:

- Claude, `https://claude.ai/oauth/mcp-oauth-client-metadata`: `grant_types`
  includes `urn:ietf:params:oauth:grant-type:jwt-bearer` beside
  `authorization_code` and `refresh_token`. `validateClientMetadata` refused
  any grant type it does not issue.
- ChatGPT, `https://chatgpt.com/oauth/client.json`:
  `token_endpoint_auth_method: "private_key_jwt"` with
  `token_endpoint_auth_methods_supported: ["none","private_key_jwt"]`.
  `validateClientMetadata` refused anything but `none`.

`resolveClient` turned both refusals into `null`, so `/oauth/authorize`
rendered "This client is not registered with StoryBook" (`invalid_client`)
for both clients. Reproduced with
`apps/e2e/tests/mcp/published-clients.spec.ts` against main's `clients.ts`:
both tests fail on that page, with the server fetching the live documents.

**Why it shipped:** FILM-1907's unit tests used a made-up document URL
(`https://claude.ai/.well-known/oauth-client`) with an invented body, so the
validator was never run against either client's real document, and FILM-1907's
Claude Desktop check (owner, open) had not been run yet.

**Acceptance criteria:**

- [x] Both real documents, committed as fixtures, resolve to a public client
  (`__tests__/oauth/client-compatibility.test.ts`), red on main's validator.
- [x] A key- or secret-only client, and one without `authorization_code`, are
  refused; the key-only one with a reason on our page.
- [x] A presented client credential at the token or revoke endpoint is
  `invalid_client`.
- [x] Each client id signs in through consent and calls `whoami`
  (`published-clients.spec.ts`: the sandbox's copies with `SANDBOX_E2E=1`,
  the vendors' live documents with `LIVE_CLIENT_DOCS=1`), red against the
  copies under the validator mutations.
- [x] A cached document older than a day is refetched; a failed refetch
  keeps the cached copy.
