**Twelve identical NewsAPI queries per live search** (found by KB-37, 2026-09-25; read, not run)
- The aggregator builds one provider per active built-in row (`context-aggregator.ts` `initialize`, `createProvider`). All 12 built-ins are `newsapi`, and a `NewsAPIProvider` takes only the row's id and tier (`newsapi-provider.ts:45-48`): it calls `/v2/everything` with the same `q`, and no `sources=` filter from the row's `config.source_id`. So a live search with no cache hit makes 12 identical NewsAPI requests on the platform's `NEWSAPI_KEY`, and `deduplicateContent` throws 11 answers away. Every result is also attributed to whichever built-in's provider returned it first. The fix is to pass `config.source_id` as `sources=`, or to build one provider per `provider_type`

**Owner follow-ups decided "not now" in KB-37 (2026-09-25)** (not bugs; recorded so they are not lost)
- **Q-b: a team's own API sources are not searched.** Team and project sources with an API `provider_type` (`newsapi`, `semantic_scholar`, `custom_api`) are listed in the hub, but the aggregator searches built-ins only: it is one process-wide instance, and a team's rows must never enter it (KB-26, KB-37). Searching them needs a per-team aggregator, plus a rule for whose API key pays
- **Q-c: a team cannot hide a built-in for itself.** Before KB-37, deactivating a built-in hid it for every team. Now nobody can change a built-in through the app. A per-team "don't use this built-in" needs a preference table (team, source)
