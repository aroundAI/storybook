## Library files that nothing deletes

`deleteAudioAssetAction` keeps an asset's file in three cases, and no job
removes it later:

- **Still in use.** A timeline track or cue used it at delete time (lead
  decision, 2026-09-25). When the last track stops using it, the file stays.
- **Delete failed.** The row is soft-deleted, then the storage call fails.
  The action logs `delete-failed` and reports the delete as done.
- **Not the asset's own.** `file_url` points outside the three layouts
  `ownedAudioAssetLocation` accepts (`file_not_owned` in the log). That covers
  legacy rows and a URL a writer edited.

A sweep would list soft-deleted `audio_assets` rows whose owned file still
exists and that no `audio_tracks` or `audio_cues` row uses, then delete
them. The lead decided against it in the KB-95 PR (Q5).

## The worker's generated-file URL may not match the adapter's

The LLM worker uploads cue audio with its own `uploadToR2`
(`apps/web/lambda/llm-worker/utils/r2-storage.ts`), and builds the URL as
`${publicUrl}/${fullPath}`. If that prefix differs from the app adapter's
`getPublicUrl('audio', '')`, `ownedAudioAssetLocation` cannot map it, and
deleting such an asset keeps the file (`file_not_owned`). The failure is
safe, but it leaves an orphan. Check this on R2 with a worker-generated asset.
