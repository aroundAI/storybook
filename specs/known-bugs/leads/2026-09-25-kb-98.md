# Leads from KB-98 (2026-09-25)

Read, not reproduced. The rule for leads is in [the README](../README.md#leads).

**Publishing-config actions report success when a write was refused** (found by KB-98, 2026-09-25)
- `updateEpisodePublishingConfigsAction` (`packages/features/publishing/src/server/episode-publishing-actions.ts`) awaits its delete, update and insert calls without reading `error`, then returns `{ success: true }`. `project-publishing-actions.ts` has the same shape. PostgREST reports a refused write as a value, not a throw, so a write RLS refuses reads as saved. Since KB-98 that includes a config naming another account's channel. The UI's pickers list only the account's own channels, so reaching it needs a crafted request today. The fix is to read each call's `error` and return a refusal (KB-6's `returnRefusals`).

**Analytics already synced from another account's channel stay in ClickHouse** (found by KB-98, 2026-09-25)
- Before KB-98, a publish could name another account's channel. The analytics sync (admin client) fetches metrics with a publish's channel token, so any such publish could have pulled the other channel's figures into this account's `video_metrics`. KB-98's migration clears the channel on those publishes, which stops further syncs. It does not delete rows already written. Production runs with ClickHouse off, so there is nothing there. Any other environment with ClickHouse on should count `video_metrics` rows for the publish ids KB-98's migration reports in its NOTICE, before deciding whether to delete them.
