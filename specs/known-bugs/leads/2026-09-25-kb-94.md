# Leads from KB-94 (2026-09-25)

Read, not reproduced. The rule for leads is in [the README](../README.md#leads).

**The Reporting parser writes 0 for a column the report does not carry** (found by KB-94, 2026-09-25)
- `parseChannelBasicReport` (`packages/features/content-analytics/src/server/reporting/csv-parsers.ts`) reads every metric through `numberAt`, which returns `0` when the column index is `-1`. The same happens for a cell that is not a number. So a `channel_basic_a3` version that lacks `dislikes`, `subscribers_lost`, `average_view_duration_percentage` (or `views`, `likes` …) would write a measured-looking 0. That 0 then replaces the Analytics-API sync's figure for the day, which is KB-94 in the other direction. `engaged_views` is the one exception: the parser already makes it `null` when its column is absent (KB-50). Not seen in a real report; YouTube's documented `channel_basic_a3` carries all of them. The fix would be the one KB-94 made for the sync: refuse a report that is missing a column the row needs, rather than defaulting it.

**`extra_metrics` is overwritten the other way, harmlessly today** (found by KB-94, 2026-09-25)
- The Reporting ingest writes `extra_metrics: '{}'` for the same key where the sync writes the day's raw payload JSON, so the Reporting row erases it. Nothing reads `video_metrics.extra_metrics` (`git grep extra_metrics`: writers, types and comments only; audience data lives in `video_audience`). It becomes a bug only when something starts reading it.
