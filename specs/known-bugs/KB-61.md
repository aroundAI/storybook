## KB-61 — A `.delete()` without `.select()` reports success when RLS matched no row

> **Fixed (2026-09-25), #PR.** `requireAffectedRows` (`@kit/next/refusals`)
> turns a write that changed no row into an `ActionRefusal` the user reads.
> Sixteen deletes and soft deletes whose success is shown now end in
> `.select('id')` and pass through it, in actions wrapped by
> `returnRefusals` with their callers unwrapped. Anything that depended on the
> write — a stored file, a cascade, an audit entry, a cancelled job — now
> runs after it is confirmed. `packages/next/__tests__/kb61-unchecked-deletes.test.ts`
> fails on any new unchecked `.delete()` or `.update({ deleted_at })`; the
> ones that may stay (service role, cleanup nobody sees, replace-sets,
> cascades under a checked parent, and four files other open PRs hold) are
> listed there with their reason. The same shape in plain `.update()` calls
> is KB-105.

**Found:** KB-18 (2026-09-23). **Filed by the lead from the teammate's report; reproduced 2026-09-25 (below).**
**Fixed** in #PR — see the banner.

`.delete()` without `.select()` reports success when RLS matched no row. The pattern is widespread.

### Reproduced (2026-09-25, on `main` ddc5568a)

- **The mechanism, through RLS** (local database, one rolled-back pgTAP
  transaction run with `supabase test db`, 2026-09-25 18:32): a project
  **member** can read the thumbnail row, passes `can_write_project`, and may
  update it — and `delete from episode_thumbnails where id = …` affected
  **0 rows, with no error**; the row was still there afterwards, and the
  owner's same delete affected 1. A project **viewer**'s
  `update episodes set deleted_at = now() where id = …` (what
  `deleteEpisodeAction` sends) affected **0 rows, with no error**. All 8
  assertions passed.
- **The fix's own assumption, checked there too:** a soft delete ending in
  `.select('id')` is an `UPDATE … RETURNING`, and Postgres applies the read
  policy to the returned row. None of the read policies on `episodes`,
  `seasons`, `shots` or `assets` tests `deleted_at`, and the owner's soft
  delete of each returned its row.
- **What a user got** (the KB-54 fake-database harness, whose delete answers
  `{ data: null, error: null }` as PostgREST does for a filtered write):
  `deleteEpisodeThumbnailAction` returned `{"success":true}`, having called
  `storage.delete episodes/<E>/thumbnails/en-1.png` **before**
  `episode_thumbnails.delete`. A project member reaches exactly this: the
  action admitted `owner | admin | member`, the table's delete policy only
  `owner | admin` — so the file was deleted, the row kept, and the app said
  "Deleted". The row then named a missing file, which the publish step would
  send to the platforms.

### What else a refused write did

- `deleteEpisodeAction` hard-deleted the episode's shots and wrote a
  `delete` audit entry for an episode that was not deleted.
- `deleteProjectAction` and `removeProjectMemberAction` audited deletions
  that did not happen; `removeMemberFromAccount` went on to decrease the
  billed seat count.
- `deleteShotAction` cancelled the shot's generation job first.
- `deleteLanguageTranslationAction` said "Deleted 0 … translations".
