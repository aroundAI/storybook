## KB-94 — The Analytics-API sync overwrites Reporting-only `video_metrics` columns with zeros

> **Fixed (2026-09-25), #367.** The daily Analytics-API query now asks for
> `dislikes`, `averageViewPercentage` and `subscribersLost`, and
> `buildYouTubeDailyRows` writes them. That builder is shared by the hourly sync and
> the backfill, which had the same bug over the whole history. Both YouTube writers
> now return `YouTubeVideoMetric`, which makes every column they share required, so
> leaving one out is a `tsc` error. The daily answer is read by column name. When a
> requested metric is missing, or a day's figure is null, the answer is refused and
> that video's sync fails and retries: no 0 is written over a measured figure.
> Guarded by `verify-queries.ts` ("… survive the other video_metrics writer (KB-94)":
> both write orders, a restatement and a repair) and `tooling/mutation-guards/kb-94.json`.
> **Rows zeroed before the deploy need the repair below**; the sync rewrites only
> its own 3–5-day window. The same problem on TikTok and Instagram, where these
> columns are never measured but read as a measured 0, is **KB-111**.

**Severity:** Medium — `dislikes`, `subscribers_lost` and
`avg_view_percentage` for YouTube videos read 0 in steady state.
**Found:** KB-50's investigation, 2026-09-24 (it was a lead from the
2026-09-23 audit). **Reproduced.**

Two writers share one `ReplacingMergeTree(inserted_at)` key in
`video_metrics`: the Reporting ingest (`channel_basic_a3`, every 6 h, sets all
columns) and the hourly Analytics-API sync, whose `buildYouTubeDailyRows`
(`packages/features/content-analytics/src/server/ingest.ts`) does not send
`dislikes`, `subscribers_lost` or `avg_view_percentage`, so they take their
`DEFAULT 0`. The later row replaces the whole row. The sync re-fetches from
`last_data_date − 3 d` (`computeYouTubeWindow`), and the report for a day lands
about two days after it, so the sync's row lands last for every day.

Measured on local ClickHouse 24.8, a scratch clone of `video_metrics`:

```
metric_source  views  dislikes  subscribers_lost  avg_view_percentage
reporting_api  400    2         1                 45.5    <- the Reporting row
analytics_api  401    0         0                 0       <- after the sync rewrote the day
```

**Not fixed with KB-50.** `engaged_views` escaped it only because both
writers now send it. The fix needs a design choice per column: the sync
requests these three metrics too (the totals query already asks for all three),
or a day with a `reporting_api` row is not rewritten by the sync, or a
source-priority version. Restatement within the window has to keep working
either way.

**Reproduced again on `ddc5568a` (2026-09-25)**, through the app's own
readers, on a throwaway ClickHouse 24.8.14.39 migrated by
`pnpm --filter @kit/clickhouse migrate`: after the sync's row, a video's
average percentage viewed read 45.5 → **0**, and its net subscribers 4 → **5**.
A later Reporting row put both back.

**The choice made:** the sync requests the three. Skipping days that have a
Reporting row would stop YouTube's ~72-hour restatement from landing, and a
source-priority version means rebuilding the table. Nullable columns do not
help here: a later NULL replaces the whole row just as a 0 does.

### Repair: rows zeroed before the fix (one person, after the deploy)

Every YouTube day whose last write came from the sync or the backfill before
the deploy still reads 0 in these three columns. Most of history is affected.

1. **Count them** (ClickHouse, production console):
   ```sql
   SELECT count() FROM video_metrics FINAL
   WHERE platform = 'youtube' AND metric_source IN ('analytics_api', 'backfill')
     AND views > 0 AND avg_view_percentage = 0;
   ```
2. **Queue every YouTube publish for the backfill again** (Supabase SQL editor):
   ```sql
   update public.publishes
   set metadata = jsonb_set(metadata, '{sync}', (metadata->'sync') - 'backfill_completed_at')
   where platform = 'youtube'
     and status = 'published'
     and metadata->'sync' ? 'backfill_completed_at';
   ```
   It removes only that one key, and keeps `last_data_date` and the rest of
   `metadata`. It was run against a scratch table with a completed, an
   unfinished and an empty YouTube row plus a TikTok row: only the completed
   YouTube row changed.
3. **Drain the backfill.** Call
   `POST /api/analytics/backfill?dryRun=true` with `Authorization: Bearer $CRON_SECRET`
   to see the plan. Then call it without `dryRun`, repeatedly, until the
   response says `"remaining": 0`. Each call is capped at 50 videos and 150
   Analytics queries. Each video costs 2 queries per 180 days of its life.
4. **Re-run step 1.** The count of rows written before the deploy should be 0.
   Remaining rows are days YouTube itself reports as 0 (for example
   `views > 0` with an average percentage of 0). Read a few before assuming
   anything.

Experiment baselines already saved in Postgres were computed from zeroed rows
and are not changed by this repair. An experiment concluded after the repair
measures its baseline window again (KB-8) and shows corrected figures.

**Not verified against the live API.** The three metrics are documented as
valid on `dimensions=day` with `filters=video==ID`
(`docs/platform-capability-reference.md`), but that has only been confirmed
against mocks here. The owner's first sync after the deploy is the first time a
real answer is read. If YouTube refuses the query, every YouTube video's sync
fails with `YouTube daily report has no <metric> …` or a 400 from YouTube.
Revert this change if that happens.
