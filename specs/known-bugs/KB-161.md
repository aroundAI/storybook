## KB-161 — A failed read of a connection tells the user it no longer exists

> **Fixed (2026-10-02), #525.** `ensureValidToken`
> (`packages/features/publishing/src/lib/token-refresh.ts`) now throws a read
> that failed, worded by `whyNoRow` ("Platform connection not found: the read
> failed (…)"), and answers `NOT_FOUND` only for PostgREST's `PGRST116`, a
> missing row. That is the rule the publish worker's `checkConnectionToken`
> already follows (KB-138), through the same `readFailed` helper, so the two
> token checks now agree. Every one of its ten callers already runs it inside
> a per-row or per-request `try`, so a failed read costs that one row, never
> the run.

**Severity:** Low. Nothing is written and nothing is deactivated, but the
person publishing is told their channel connection is gone and to connect it
again, when the database only failed to answer once; reconnecting does
nothing, and a retry would have worked. **Found:** 2026-10-02, reviewing
KB-157 (#510), which turned `NOT_FOUND` from a bare code into that sentence.

### What happened

`doEnsureValidToken` reads the connection with `.single()` and then did:

```ts
if (error || !connection) {
  return { valid: false, error: 'NOT_FOUND' };
}
```

`.single()` reports "no row" as `PGRST116`. Every other error (a statement
timeout, `ECONNRESET`, a 5xx from PostgREST) is a read that failed, and says
nothing about whether the row exists. All of them became `NOT_FOUND`, and
after KB-157 the page shows `tokenErrorMessage('NOT_FOUND', …)`: "This YouTube
connection no longer exists. Connect YouTube in Settings → Platforms to
publish." The crons recorded the same false reason: `refreshExpiringTokens`
logged `error: 'NOT_FOUND'`, and the analytics sync wrote it to the publish's
`last_error`.

**Reproduced** in `packages/features/publishing/__tests__/token-refresh.test.ts`
by making the fake database fail one connection's read with
`57014 canceling statement due to statement timeout`. On the code before the
fix:

```
× ensureValidToken before any refresh > throws a failed read rather than answering NOT_FOUND
  → promise resolved "{ valid: false, error: 'NOT_FOUND' }" instead of rejecting
× refreshExpiringTokens > counts one failed read as one failure and refreshes the rest (KB-161)
  → expected [ [ { …(4) }, …(1) ] ] to deep equally contain [ ObjectContaining{…}, …(1) ]
```

(the cron logged the row as a `NOT_FOUND` token failure, not as the read
that failed).

### The choice: throw, not a new `READ_FAILED` code

Two designs fix it: throw the failed read, as the worker's token check does,
or add a `READ_FAILED` code to `TokenErrorCode` for every caller to handle.
**Throwing was chosen**, because:

1. **A failed read is not a fact about the token.** `TokenErrorCode` is the
   vocabulary of why a connection's token cannot be used, each with a
   sentence telling the person what to do. "The database did not answer" has
   no such action, and as a code it would also be stored as the publish's
   `metadata.errorCode` and the analytics sync's `last_error`, alongside real
   token states.
2. **Every caller already isolates a throw.** No loop stops on one row:

   | Caller | On a throw |
   |---|---|
   | `jobs/refresh-expiring-tokens.ts` (cron) | per-connection `try`: counted `failed`, logged, next connection |
   | `jobs/process-scheduled-publishes.ts` (cron) | per-publish `try`: that publish marked failed with the read's message, next publish |
   | `content-analytics/server/analytics-sync-cron.ts` (cron) | `syncSinglePublish`'s `try` around the whole sync |
   | `content-analytics/server/asset-duration-sync.ts` (cron, backfill) | per-connection `try`: a `provider_error` gap for that group, next group |
   | `content-analytics/server/backfill/youtube-backfill.ts` | per-publish `try` |
   | `content-analytics/server/channel-reach-windows.ts` (cron) | per-connection `try`: counted `failed` |
   | `content-analytics/server/reporting/report-ingest.ts` (cron) | per-connection `try`: pushed to `errors` |
   | `content-analytics/server/subscriber-snapshot.ts` (cron) | per-connection `try`: "never fatal to the batch" |
   | `server/connection-actions.ts` `refreshConnectionAction` | not a refusal, so `returnRefusals` rethrows it; production shows its generic failure sentence, not "no longer exists" |
   | `server/connection-tokens.ts` `getAccessToken` → `publish-actions.ts` (per-platform `try` in `Promise.allSettled`, and the retry action) and `social-post-actions.ts` | the platform's publish fails with the read's message; the others continue |

3. **One rule, in one place.** `readFailed`/`whyNoRow` (`@kit/shared/rows`)
   is KB-138's rule, and the worker's `checkConnectionToken` already throws
   this exact error for this exact read. A second, code-shaped answer to the
   same question would let the two token checks disagree again.

A code would have needed every one of the ten callers changed to tell it
apart from a real token state (the analytics sync, for one, classifies by
code); a throw needs none changed.

A side effect, also for the better: the optimistic-lock retry in
`doEnsureValidToken` recurses on a failed lock write. While the database is
down, each retry re-reads the connection, and that read now throws and ends
the loop instead of returning `NOT_FOUND`.

### Tests

- `token-refresh.test.ts`: "throws a failed read rather than answering
  NOT_FOUND" (nothing written, nothing deactivated, no vendor called), and
  "counts one failed read as one failure and refreshes the rest (KB-161)",
  which runs the real cron over two connections. Both red on the old code,
  above.
- `connection-actions.test.ts`: the Refresh button throws a failed read
  rather than refusing with a not-found sentence.
- `content-analytics/__tests__/asset-duration-sync.test.ts`: a connection
  whose token read throws costs only its own publishes; the next connection
  is still synced.
- Mutation guard `tooling/mutation-guards/kb-161.json` G1: removing the
  `readFailed` throw turns the two `token-refresh.test.ts` cases red.

### Not changed

`asset-duration-sync` files a failed read under the `provider_error` gap, as
it does any unclassified throw. The gap is counted and retried next run; a
separate `read_failed` gap kind is not worth a new reason in its report.
