## KB-189 — The edit package carries no sha256 for shots, dialogue, audio or dubs, because nothing records one at write time

> **Fixed (2026-10-05), #646.** Each file's SHA-256 and size is recorded
> once, where it is written, in `media_checksums` (migration
> `20261005115253_kb-189-media-checksums.sql`): one row per storage object,
> keyed by `(bucket, object_key)`, filed under the key's own project by
> `record_media_checksum` (executable by the service role only), readable by
> whoever reads the project. A table rather than `*_sha256` columns: six
> tables hold a media URL, one file can be named by several rows (an audio
> asset and its tracks), and the key is the one thing every writer holds.
>
> Every writer, not only the ones named below: `uploadToR2`
> (the voice worker's dialogue, `dub-runtime`'s dubbed lines, the LLM
> worker's music, SFX and ambience) and `writeProjectObject` (every web
> action that stores generated audio) take the client it is recorded on as
> a required argument, so a writer cannot leave it out. A browser upload is
> a presigned PUT the server never sees: `uploadWithPresignedUrl` and the two
> uploaders that presign their own PUT (shot video and its thumbnail, frames,
> character images, audio-library files) hash the file in the browser and
> report it to `POST /api/storage/checksum`, which records it once the
> caller is shown to write the key and a HEAD shows the stored object has
> the reported size. Re-hashing there would mean downloading the object.
> The reported hash is the uploader's claim; only a writer of the project
> can make it, about a key that writer could fill with any bytes anyway.
> `upload-checksums-recorded.test.ts` fails when an uploader presigns a PUT
> and does not report it.
>
> The reader: `load-edit-package.ts` places each URL the package names in
> its bucket and reads `media_checksums` for those keys under the caller's
> RLS, 40 keys per request (a key is ~100 characters and an `.in()` list
> rides in the URI), then `assets.file_hash` as before. `resolve-media.ts`
> keeps its shape; the etag moves when a hash is recorded. No read path
> writes or computes one. Media written before this keeps
> `sha256Reason: 'not_recorded'`.
>
> Evidence. Against lane B's Supabase, the FILM-2001 contract test records
> each seeded file as the writers do and checks every signed entry of the
> 60-shot package: 419 of 419 carry a sha256, each equal to the SHA-256 of
> the bytes its signed URL downloads (shot video, frames, dialogue, dubbed,
> music, SFX, ambience, character images); red with the recording left
> out. Package 505,616 bytes, calls 901-1,074 ms. pgTAP
> `media-checksums.test.sql` 9/9 (a viewer reads, a stranger does not, a
> signed-in user can neither call the function nor write the table; red
> with both opened), and the whole suite, 119 files, green on a throwaway
> Postgres. Unit tests, each seen red without its change: the storage
> layer (`project-write.test.ts`, `r2-upload-target.test.ts`), every writer
> (`voice-worker/__tests__/media-checksums.test.ts` for dialogue and dubs,
> `llm-worker/__tests__/audio-file-checksums.test.ts` for music, SFX and
> ambience, `audio-spend-authorization.test.ts` and
> `voice-authorization.test.ts` for the web actions), the browser path
> (`upload-checksum-client.test.ts`, `upload-checksum.test.ts`), and the
> reader (`get-edit-package.test.ts`, "recorded checksums (KB-189)").

**Severity:** Low — StorybookStudio cannot verify most downloads by content
hash, only by size. A truncated or swapped file of the same size would pass.
**Found:** building FILM-2001 (#618).

`get_edit_package` gives every media entry a `sha256` when StoryBook has
recorded one. The only recorded hash is `assets.file_hash`, which only the
master-video upload writes (`master-asset-manager.tsx` computes it in the
browser). Shot videos and frames (`/api/projects/[projectId]/shots/[shotId]/upload`),
dialogue audio (voice worker), music, SFX and ambience (audio workers) and
dubbed audio have no `assets` row and no hash anywhere.

Reproduced on the FILM-2001 contract test's 60-shot seed: of the package's
600 media entries, one (a character image with `assets.file_hash`) has a
sha256; every other signed entry is `sha256: null, sha256Reason:
'not_recorded'`.

Computing the hash on request was considered and refused (FILM-2001 notes):
it means downloading every object inside a 2 s tool call, and storing it
gives a read-only MCP tool a write surface.

**Proposed fix.** Record the SHA-256 where each file is written, in a place
StoryBook owns and the reader's RLS can see (a checksum keyed by storage
key, written by the uploader route and the workers, which already hold the
bytes). `resolve-media.ts` then reads it as it reads `assets.file_hash`
today.

**Acceptance.**
- A shot video uploaded through the upload route, a generated dialogue
  line, a generated music/SFX track and a dubbed line each appear in the
  edit package with a sha256 equal to `sha256sum` of the downloaded file.
- No read path writes a checksum; a key replaced with new bytes gets a new
  hash (or a new key).
- The FILM-2001 remaining criterion is ticked.
