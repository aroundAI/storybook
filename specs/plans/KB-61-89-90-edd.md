**KB-61 is not hypothetical inside these tickets.** `canEditEpisode` (`thumbnail-actions.ts:103-129`) admits `owner | admin | member`. But the table's delete policy (`20260103042141_add_episode_thumbnails.sql:114-123`) admits only `owner | admin`. A **member** who deletes a thumbnail therefore gets this sequence:
1. It passes the action's check.
2. The file is deleted from storage. On Supabase, storage RLS uses the project-write rule, which includes members. On R2 the app's own credentials are used.
3. `DELETE` matches 0 rows.
4. The action returns `success: true`.

After a reload, the row is back, pointing at a file that no longer exists (a broken image), and the publish step would send that URL to the platforms. The same member **can** replace the thumbnail, and a replace deletes the old file (KB-54). So the policy blocks only the row delete, which is the harmless half.

Project intros are consistent: `project.edit` (owner/admin) matches the intro delete policy (owner/admin).

## 1. The user

**Who:** a creator (project owner, admin or member) preparing an episode for publishing, and anyone who deletes something in the studio.

**What they get:**
1. **KB-61:** when the app says something was deleted (or soft-deleted), it was. When the database refused, or there was nothing to delete, the user reads a sentence saying so, e.g. *"Nothing was deleted: it was already gone, or you can't delete it. Reload and try again."* The list isn't silently out of step with the database, and no file is deleted for a row that stays.
2. **KB-89:** on the publish screen, each language's thumbnail slot that has its own thumbnail gets a **Remove** control. It asks for confirmation, then removes the row and the file. After a reload the thumbnail is still gone.
3. **KB-90:** the intro and thumbnail actions store only a file that this app uploaded into **this** project's (or episode's) own folder. Anything else is refused as a value. The normal upload path is unaffected.

**What they could not do before:** remove a per-language thumbnail at all (KB-89). Trust a "Deleted" toast (KB-61). And a writer could plant any URL, which the publish worker would fetch (KB-90).

**What persists:** removals (row and file). **What does not:** nothing new is cached client-side. The slot re-reads through `getEpisodeThumbnailsAction`.

## 7. Non-functional

- **Performance:** `.select('id')` returns the ids of affected rows. Episode-scoped deletes return at most one row per shot or cue. This is not a read of more than 1000 rows: the helper needs only "≥1", and none of these deletes is used as a count. Where a count is shown (`deleteLanguageTranslationAction` uses `{count:'exact'}`), the count stays authoritative and `count === 0` becomes the refusal.
- **Security:** R7/R8 close a stored-URL injection that the publish worker (`apps/web/lambda/publish-worker/handlers/youtube.ts:88`, `facebook.ts:28`) would fetch. R4 stops a member's refused delete from destroying a file.
- **Observability:** each refusal is logged at `warn` with ids only (the existing `idsOf` in `withRefusals`, or the action's `ctx`).
- **Compatibility:** existing rows are not revalidated. Only new writes are checked (§24).

## 15. Low-level design

```ts
// @kit/next/refusals
export function requireAffectedRows<T>(rows: T[] | null | undefined, refusal: string): T[] {
  if (!rows || rows.length === 0) throw new ActionRefusal(refusal);
  return rows;
}

// typical site (before → after)
const { error } = await client.from('social_posts').delete().eq('id', id);
// →
const { data, error } = await client.from('social_posts').delete().eq('id', id).select('id');
if (error) throw new Error(`Failed to delete social post: ${error.message}`);
requireAffectedRows(data, SOCIAL_POST_REFUSALS.delete);
```

- **Thumbnail delete (R4):** read the row (unchanged) → `delete … .select('id')` → `requireAffectedRows` → `removeThumbnailFile`. The existing `try/catch` in the action turns `ActionRefusal` into `{ success:false, error: refusal }` (it already returns that shape). The catch will return `error.message` only for `ActionRefusal`, and a generic sentence otherwise (today it leaks `Failed to delete thumbnail: <pg message>`).
- **Intro delete:** the same.
- **Refusal wording:** kept in a `*_REFUSALS` const per file, as `EPISODE_FACT_REFUSALS` does.
- **Actions that throw today:** I'll wrap them in `returnRefusals` (crashes stay thrown; KB-6) and switch each client caller to `unwrap` + `refusalMessage`. There are about 10 callers, listed in §8.
- **Concurrency:** the row delete is the linearisation point. Two tabs: one wins, the other is refused with the "already gone" sentence.

## 19. Security

- Tenant isolation: R7/R8 require the key under the row's own folder; `..` and empty segments are already refused by `storageKeyFromPublicUrl`.
- R4 closes "a refused member destroys the file" (§0).
- Q2 = align widens thumbnail **row** deletion to members. It's not a new capability in effect. pgTAP covers owner/admin/member allowed, viewer and outsider refused.
- **What the fix newly permits:** with Q2 = align, members removing thumbnails, the one intended change. R3's allowlist could hide a future offender behind a stale reason, so each entry names its reason and the test fails when a listed site starts selecting (the "can only shrink" rule).

## 29. Alternatives

- **Helper shape:** a builder wrapper (`deleteOrRefuse(client.from(t), filters)`) was rejected. It hides PostgREST's typing and every filter chain differs. A post-check over `{data}` is the shape #344 and #352 already inline, now named once.
- **Guard vs. lint rule:** an ESLint rule would need AST plumbing for PostgREST chains. The repo already guards KB-6 with a Vitest source scan, so this follows that.
- **KB-89: render the orphaned panel** (on the publish page or a new episode-settings tab) was rejected, recommended against in Q1. It duplicates the per-language slot, builds its own storage path (not `episodeThumbnailPath`), keys languages by free text rather than `SupportedLanguage`, and its "set default" is read nowhere except as a fallback. Two UIs for one row set is how KB-89 happened.
- **KB-90: domain allowlist** (as `validateContentUrl`) was rejected, since it admits any tenant's file on the same host.
