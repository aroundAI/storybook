All three reproduce, so none is already fixed. **What the ticket records leave out** (it changes the scope):

1. **KB-54 becomes a data-loss bug once the key is right.** Both upload actions delete the old file **before** the upsert (`intro-actions.ts:126-144` then `:161`; `thumbnail-actions.ts:177-191` then `:212`). If the upsert fails, the row still points at a file that is now gone. It is harmless today only because the delete removes nothing. The fix has to move the delete after a successful upsert.
2. **KB-54 becomes a cross-tenant delete primitive on R2 once the key is right.** `videoUrl`/`thumbnailUrl` are client-supplied (`z.string().url()`). The R2 adapter deletes with the app's own credentials, and RLS does not apply. A writer of project A could save A's intro URL as `…/project-assets/projects/<B>/…`, then click "Replace" or "Delete", and the server would delete B's object. On Supabase, RLS (`can_write_project_storage`) would refuse; on R2 (production) nothing would. The fix therefore **confines every derived key to the row's own project/episode prefix**.
3. **KB-53 is three bugs, not one.** The bucket, the path and the RLS file-name contract all refuse. The key has to be `<accountId>.<ext>`, a fixed name. On Supabase that needs an upsert-capable signed URL; the adapter never passes `upsert` today.
4. `apps/web/lib/presigned-upload.ts:66-76` `uploadImage` builds `projects/<id>/<category>/…`, which the route refuses. It has **zero callers** (KB-38 EDD U2 said so too). It is the same class of bug as KB-39 and gets deleted here.
5. `EpisodeThumbnailSettings` (`episodes/[episodeSlug]/_components/episode-thumbnail-settings.tsx`) is **rendered nowhere**, so `deleteEpisodeThumbnailAction` has no UI caller. The only live path to a thumbnail replacement is the publish screen (`publish-screen.tsx:260-310` → `uploadEpisodeThumbnailAction`). This is reported as a lead, not removed (outside the ticket).

## 1. The user

- **Who:** a creator (project owner/admin/member = a *writer*) who runs a channel; the owner is the first end-to-end user. For avatars, any signed-in user (personal) or a team member with `settings.manage` (team).
- **Problems today:**
  - *KB-39:* Project Settings → Publishing & Branding → Add Intro → pick a video → "Failed to upload intro video". Every time, for everyone. Intros are what gets stitched onto each episode, so the feature does not exist.
  - *KB-53:* Account settings → profile picture → pick an image → the error toast. Same for team pictures. Nobody can set an avatar.
  - *KB-54:* replacing an intro (once KB-39 is fixed) or an episode thumbnail leaves the old file in public storage forever, and deleting an intro leaves its file. The user sees nothing wrong, but storage fills with orphans, and a "deleted" intro stays publicly reachable at its old URL.
- **After:**
  - Intros upload, show up in the list with a preview, can be replaced (the old file is deleted) and deleted (the file is deleted).
  - Avatars upload for personal and team accounts, show immediately, and a second upload visibly replaces the first (no stale cached image).
  - Replaced thumbnails delete their old file.
- **Success:** the new item is visible after a refresh, and exactly one stored object exists per live intro, thumbnail or avatar.
- **Failure:** a clear, specific toast, such as "Content type not allowed: video/x-matroska", "File is 600 MB; videos may be at most 500 MB" or "You do not have permission…", and no row is written.
- **Persists:** the DB rows (`project_intros`, `episode_thumbnails`, `accounts.picture_url`) and the stored objects. **Does not persist:** dialog state, progress, the local preview blob.

## 2. User journeys

**J1 — Add an intro.** Settings page (writer) → "Add Language" → dialog: code `en`, optional label, file (`accept="video/*"`) → "Upload". System: reads the duration in the browser (refuses over 60 s), asks presign for `projects/<P>/assets/intros/en-<ts>.<ext>` → PUT → `uploadProjectIntroAction` → row upserted. User sees the toast "Added en intro", the dialog closes, and the card shows the language with a preview. Next: Replace, Delete, or leave. Refresh: the card is still there (RSC read of `project_intros`).
**J2 — Replace an intro.** Card → "Replace" → dialog prefilled with the language (locked) → new file → Upload → new object PUT, row upserted **then** the old object is deleted. Toast "Replaced en intro"; the card previews the new video.
**J3 — Delete an intro.** Card → Delete → confirm → the action deletes the object (key confined to `projects/<P>/`) then the row. The toast confirms and the card disappears.
**J4 — Replace a thumbnail** (publish screen, per language) → new object PUT → action upserts the row, then deletes the old object (key confined to `episodes/<E>/`).
**J5 — Set a personal avatar.** `/home/settings` → the profile-picture uploader → choose an image → toast loading→success → the avatar updates in the page and the header dropdown. Refresh: it persists. Choose another → the new image shows (cache-busted URL).
**J6 — Set a team avatar.** `/home/<team>/settings` (needs `settings.manage`) → same as J5 with the team id.
**J7 — Remove an avatar.** Clear → `picture_url = null` (unchanged behaviour; the object is not deleted — see §31 Q2).
**Interruption / cancel / back:** closing the dialog before Upload does nothing. Navigating away mid-PUT leaves at most one orphan object and no row (pre-existing, KB-28 §12). Session expiry: presign returns 401 → toast.

## 3. Happy path (J1, the one that has never worked)

1. The user picks `intro.mp4` (video/mp4, 2 MB, 5 s) with language `en`.
2. The client builds the key with **`projectIntroPath(projectId, 'en', 'video/mp4')`** → `projects/<P>/assets/intros/en-<ts>.mp4`. The extension comes from the MIME type, not a hard-coded `.mp4`.
3. `POST /api/storage/presign {bucket:'project-assets', path, contentType:'video/mp4', size}` → bucket allowed → path matches the project-assets rule → type allowed → size ≤ 500 MB → `can_write_project_storage(path)` true → signed URL (R2: type + length bound; Supabase: bucket limits).
4. PUT the bytes → 200.
5. `uploadProjectIntroAction({…, videoUrl: publicUrl})` → `canPerformProjectAction` → read the existing row (none) → upsert → no old file → returns the intro.
6. The toast and card render. **Why it is success:** a row plus an object whose key lies under the project, reachable by public URL, and it survives a refresh.

## 7. Non-functional requirements

- **Security:** no loosening. `project-assets` rules are byte-identical; the new bucket gets its own stricter rule and a type/size cap; R2 remains signed for the exact type and length (KB-38). New deletes are confined to the row's own prefix (see §0 finding 2).
- **Performance:** adds one RPC per avatar presign (same as the project RPC) — negligible. Deletes happen after the upsert (same count).
- **Compatibility:** the presign request and response shapes are unchanged; `SignedUploadRequest.upsert` is optional.
- **Observability:** `Presign refused` warns keep their `reason` tag (new reasons: `account-image-not-owner`); the delete skip logs `{reason: 'foreign-url' | 'outside-prefix'}`.
- **Accessibility:** N/A beyond the existing dialog (labels already present); `data-test` only.
- Other NFRs (i18n, DR, cost): N/A — no new surface.

## 9. Desired system behaviour

- **Intro upload:** client `projectIntroPath()` → presign (project-assets rule) → PUT → action upsert → then `deleteOwnedObject(storage, 'project-assets', oldUrl, 'projects/<P>/')`.
- **Intro delete:** action → read the row → `deleteOwnedObject(…, 'projects/<P>/')` → delete the row.
- **Thumbnail upload/delete:** the same with `'episodes/<E>/'`.
- **Avatar:** client `accountImagePath(accountId, file.type)` → presign (account_image rule: shape, image type, 10 MB, `can_write_account_image`) → the adapter signs with `upsert:true` → PUT → the browser updates `accounts.picture_url = publicUrl + '?v=' + ts`.

## 10. High-level architecture

No new components. Three changes in placement:
1. **One upload-path module** (`packages/features/storage/src/upload-paths.ts`, pure, no `server-only`, exported as `@kit/storage/upload-paths`) holds **the path builders and the per-bucket path rules the route checks**. KB-39 happened because the builder (in a React file) and the rule (in the route) lived apart. The route imports the rules, the uploaders import the builders, and one test binds them.
2. **One key-from-URL function** (`storageKeyFromPublicUrl` + `deleteOwnedObject`) in `@kit/storage` (server), used by all four delete sites.
3. **One account-image write rule** in SQL (`public.can_write_account_image`), used by both the policy and the route — the KB-28 pattern.

Trust boundary: the route is the only gate on R2. Every decision about bucket, path, type, size and permission stays in the route. The delete confinement lives server-side in the actions.

## 12. Data flow

File → presign metadata → validation (route) → signed URL → PUT → object → public URL → action → row (`video_url`/`thumbnail_url`/`picture_url`) → rendered. **Deletion:** row URL → `storageKeyFromPublicUrl` (null if not ours) → prefix check → adapter delete. **Loss points:** the old object deleted before the upsert (fixed by the ordering); the new object orphaned if the upsert fails (pre-existing; unchanged). **Stale:** avatar CDN/browser cache on overwrite → `?v=` buster. **Incorrect transform:** URL-encoded keys (`%20`) → decode once; keys are built from `[a-z0-9_.-]` anyway.

## 13. Data model

No entity changes. Authoritative: the DB row's URL is the reference; the object key is derived from it. Invariant (new, enforced in code): *an action only deletes keys inside its own row's project/episode prefix.* The avatar key invariant: `account_image/<accountId>.<ext>`, where the file-name uuid **is** the owning account (the existing RLS contract).

## 14. Database changes

One migration, `apps/web/supabase/migrations/<ts>_kb53-account-image-writes.sql`:

```sql
create or replace function public.can_write_account_image (path text)
returns boolean language plpgsql stable security definer set search_path = '' as $$
declare account uuid;
begin
  begin
    account := kit.get_storage_filename_as_uuid(path);
  exception when invalid_text_representation then
    return false;
  end;
  return account = auth.uid()
      or public.has_permission(auth.uid(), account, 'settings.manage'::public.app_permissions);
end; $$;
revoke all on function public.can_write_account_image (text) from public, anon;
grant execute on function public.can_write_account_image (text) to authenticated, service_role;

drop policy if exists account_image on storage.objects;
create policy account_image on storage.objects for all
  using (bucket_id = 'account_image' and (kit.get_storage_filename_as_uuid(name) = auth.uid()
         or public.has_role_on_account(kit.get_storage_filename_as_uuid(name))))   -- unchanged
  with check (bucket_id = 'account_image' and public.can_write_account_image(name));

update storage.buckets
   set file_size_limit = 10485760,
       allowed_mime_types = array['image/jpeg','image/png','image/webp','image/gif']
 where id = 'account_image';
```

- **WITH CHECK semantics:** identical to today except that a malformed name is *denied* instead of *erroring*. That is equal or stricter. USING is untouched (the KB-28 note "insert stricter than delete" stays as recorded; not this ticket).
- **Existing data:** `account_image` has had no successful app uploads (R2c). Bucket limits apply to new PUTs only.
- **Locking/duration:** a policy swap and a one-row update — instant.
- **Rollback:** a forward migration restoring the old WITH CHECK and nulling the limits (only needed if the avatar is refused wrongly).
- **Schema mirror:** `apps/web/supabase/schemas/16-storage.sql` is updated alongside (the policy + function live there).
- **Types:** `pnpm supabase:web:typegen` (the new RPC appears in `Functions`).

## 15. Low-level design

**`packages/features/storage/src/upload-paths.ts`** (new, pure):
```ts
export const PROJECT_ASSETS_PATH = /…the current PATH_PATTERN, moved verbatim…/i;
export const ACCOUNT_IMAGE_PATH = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.(png|jpg|webp|gif)$/;
const IMAGE_EXT = { 'image/png':'png','image/jpeg':'jpg','image/webp':'webp','image/gif':'gif' };
const VIDEO_EXT = { 'video/mp4':'mp4','video/webm':'webm','video/quicktime':'mov' };
export function projectIntroPath(projectId, language, contentType, now = Date.now())
  // `projects/${projectId}/assets/intros/${slug(language)}-${now}.${VIDEO_EXT[contentType] ?? 'mp4'}`
export function accountImagePath(accountId, contentType) // `${accountId}.${IMAGE_EXT[contentType] ?? 'png'}`
export function projectCoverPath(...), episodeThumbnailPath(...), publishVideoPath(...), shotVideoPath(...)
  // the existing inline builders, moved so the binding test covers them all
```
`slug` = lower-case, `[^a-z0-9-]` → `-`, collapse repeats.

**Route** — the bucket table replaces `ALLOWED_BUCKETS` + the single pattern:
```ts
const RULES = {
  'project-assets': { path: PROJECT_ASSETS_PATH, types: ALLOWED_PROJECT_ASSET_TYPES, canWrite: 'can_write_project_storage', upsert: false },
  'account_image':  { path: ACCOUNT_IMAGE_PATH,  types: UPLOAD_CONSTRAINTS.image.allowedTypes, canWrite: 'can_write_account_image', upsert: true },
} as const;
```
The order of checks, the messages, the size cap (category of the type) and `refuse()` logging are unchanged. `getSignedUploadUrl(bucket, path, { contentType, contentLength, expiresIn, upsert: rule.upsert })`.

**Adapters:** `SignedUploadRequest.upsert?: boolean`. Supabase: `createSignedUploadUrl(path, upsert ? { upsert: true } : undefined)`. R2/B2/local: ignored (PUT overwrites; documented).

**`storageKeyFromPublicUrl(storage, bucket, url): string | null`** (in `@kit/storage`, server): `prefix = storage.getPublicUrl(bucket, '')`, normalised to end in `/`; `u = url.split('?')[0]`; if it does not start with the prefix → null; `key = decodeURIComponent(rest)`; reject empty or `..` → null.
**`deleteOwnedObject(storage, bucket, url, ownPrefix, logger, ctx)`**: key = ↑; if `!key?.startsWith(ownPrefix)` → warn and return; else `storage.delete(bucket, key)` inside try/catch (best-effort, as now).

**Actions:** intro/thumbnail upload — read the existing row → upsert → **if the upsert succeeds and the old URL ≠ the new one** → `deleteOwnedObject`. Delete actions → `deleteOwnedObject` then the row delete (unchanged order; if the row delete fails, the file is gone but the row remains — pre-existing, the same as before minus the no-op; noted as §30 R3).

**Client:** `project-intro-settings.tsx:385` uses `projectIntroPath(projectId, language, selectedFile.type)`; the catch shows the route's message. *As built:* `refusalMessage` passes only an `ActionRefusal` through, and a presign refusal is a plain `Error`, so `@kit/storage/client` now throws `UploadRefusal` for a 4xx with a message and the dialog shows that. `uploadAvatar(file, accountId)` → `accountImagePath` → `uploadWithPresignedUrl(file, 'account_image', path)` → returns `url: \`${publicUrl}?v=${Date.now()}\``. The `bucket` param is dropped. The dead `uploadImage` is removed from `apps/web/lib/presigned-upload.ts`.

## 16. API design

`POST /api/storage/presign` — the request and response are unchanged. **Newly accepted:** `{bucket:'account_image', path:'<uuid>.<png|jpg|webp|gif>', contentType: image/*(4), size ≤ 10 MB}` for self or `settings.manage`. `projects/<P>/assets/intros/…` was already admitted by the regex; the fix moves the caller, not the rule. **Newly refused:** nothing that works today. Status codes: 400 (bucket/path/type/size), 401, 403 (`not-a-writer` / `account-image-not-owner`), 500/501 as before. Server actions: signatures unchanged.

## 17. State and lifecycle

Intro/thumbnail row: absent → present (upsert) → replaced (upsert; the old object deleted after) → deleted (object then row). Avatar: `picture_url` null ↔ URL (overwrite in place). No new states.

## 18. Failure handling

See §4. The principle: a storage delete never fails a user action and never precedes the write it cleans up after; a key that cannot be proven to belong to the row is left alone.

## 19. Security

- **Authz:** avatar writes are gated by the same SQL rule as RLS, now in the route too (the R2 path had no gate, and the route was simply closed). Intro writes: `can_write_project_storage` (unchanged).
- **New attack surface considered:**
  - (a) Foreign-URL deletes — closed by the prefix confinement (§0 finding 2). A test proves that a cross-project URL is not deleted.
  - (b) An avatar overwrite of another account's image — the path's file name must be an account the caller may write; the RPC decides.
  - (c) An `upsert` on `project-assets` — not enabled (per-bucket flag). A test asserts `upsert` is false for project-assets.
  - (d) An HTML/SVG avatar — only 4 image types; R2-signed type and length; Supabase bucket MIME list.
  - (e) Traversal — the patterns have no `/` in the avatar, and `..` stays excluded for project-assets; the derived keys reject `..`.
- **Tenant isolation:** unchanged or improved. **Secrets:** none. **Prod creds:** none used.

## 20. Performance and scale

One extra RPC per avatar presign; deletes are unchanged in count. Negligible.

## 21. Accessibility / client

The intro dialog keeps its labels; errors go through `toast` (announced by sonner's live region). `data-test` hooks are added. Avatar: the unchanged ImageUploader.

## 22. Observability

Warn logs: `Presign refused {reason}`; `Storage delete skipped {reason:'foreign-url'|'outside-prefix', url}`; `Failed to delete old intro/thumbnail` (existing). **How the operator knows it works:** R2 object count under `project-assets/projects/*/assets/intros/` matches the `project_intros` rows; no `outside-prefix` warns in normal use (any one is either a legacy URL or an attempted abuse).

## 23. Configuration

No new config. `STORAGE_PROVIDER`, `R2_PUBLIC_URL` as today. If `STORAGE_PROVIDER` changed between upload and delete, the prefix no longer matches → delete skipped (safe).

## 24. Compatibility

- **Existing rows:** no intro rows can exist from the app (R1). Thumbnail rows: `episodes/<E>/thumbnails/…` keys → the new derivation finds them.
- **Rows written under an older provider:** skipped, not mis-deleted.
- **Existing avatars:** none via the app. `picture_url` values from OAuth (external URLs) are untouched: the avatar flow never deletes by URL.
- **Deployment order:** the migration first (the policy and the function the route RPCs). The route deployed without the function → the account_image RPC errors → 500 on avatar presign only. Standard: migrations run before the app deploy.

## 25. Rollout

Normal merge → migration applied → app deploy. No flag (these flows are fully broken today, so there is nothing to protect). Verify in production (the owner, per the runbook): upload an avatar, an intro, and replace a thumbnail; check the R2 console for exactly one object per item. **Rollback:** revert the app PR; the migration is harmless on its own (it only tightens and adds a function).

## 29. Alternatives

| Decision | Chosen | Alternative | Why |
|---|---|---|---|
| KB-39 fix | Move the intro under `projects/<P>/assets/intros/` | Widen `PATH_PATTERN` to allow `projects/<P>/intros/` | The brief says not to loosen KB-28's rule; the `assets/<type>/` shape already exists for exactly this; nothing is stored at the old path |
| Avatar key | Fixed `<accountId>.<ext>` + upsert | Unique `<accountId>/<ts>.png` + rewrite RLS to key on the folder | The fixed key matches the existing RLS contract (no semantic policy change) and leaves no orphans per upload; the cost is a cache buster and `upsert` on one bucket |
| Avatar rule | SQL function shared by the policy and the route | The route calls `has_permission` RPC directly | One rule in one place (KB-28 precedent; ENGINEERING-WORKFLOW "fix the class") |
| Key from URL | Adapter's own `getPublicUrl(bucket,'')` as the prefix | Regex per provider | Adapter-agnostic, exact, and refuses anything the adapter did not issue |
| Delete confinement | Prefix check in the action | Validate `videoUrl` on write as well | Deletes are where the damage is; write-validation would also be good, but it changes what the action accepts; listed as §31 Q1 |
| Upsert | Per-bucket flag | Always upsert | `project-assets` keys are unique per upload; enabling overwrite there would be a loosening on Supabase |
