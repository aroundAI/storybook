## 1. The user

A creator, the project's owner or a writer on a team project, keeps music and SFX in a project's **Audio Library** for use in episodes.

**Today:**
1. They cannot upload a typical track. Most MP3s are over 1 MB and all fail with "Failed to upload audio", while the dialog promises 50 MB.
2. After their first upload they cannot upload again, because the Upload button is gone.
3. A new or generated asset shows only after a manual reload.

**After the fix:**
- Any MP3, WAV or M4A up to 50 MB uploads.
- The Upload button is always in the header.
- Each new asset appears in the grid as soon as the dialog closes, and a second and third upload work in a row.
- A viewer, or someone outside the account, cannot store a file in the project, even by crafting a request.

For the account (KB-83): voice generation the platform pays for is added to the account's monthly usage. The admin account page shows real usage. When a budget is set, the budget check sees it.

**Persists:**
- The file in storage.
- The `audio_assets` row.
- `accounts.current_usage_cents`.

**Does not persist:**
- The dialog state: type tab, chosen file and name.
- Any file whose save step failed. It is deleted, best effort (§18).

## 3. Happy path (canonical)

1. Owner selects `theme.mp3` (4.2 MB, `audio/mpeg`), name "Theme", Music.
2. The client builds `path = audioLibraryUploadPath(projectId, 'audio/mpeg')`, giving `projects/<projectId>/assets/audio/<ts>-<rand>.mp3`.
   - The builder lives in `@kit/storage/upload-paths` (#340).
   - The path contains no user text. The name is kept in the row, not the key.
3. `uploadWithPresignedUrl(file, 'project-assets', path, { contentType })` calls the presign route. The route:
   - checks bucket and path (`isUploadPath`) and type (`ALLOWED_PROJECT_ASSET_TYPES`);
   - checks size ≤ 50 MB for audio;
   - checks `can_write_project_storage(path)` as the caller;
   - signs type and exact length on R2 (KB-38).
   The browser `PUT`s the bytes with the returned headers.
4. The client calls `createUploadedAudioAssetAction({ projectId, audioType:'music', name:'Theme', path, contentType:'audio/mpeg', fileSizeBytes })`. The body is about 300 bytes. The action:
   1. `requireUser`.
   2. `authorizeProjectTarget(client, projectId)`, i.e. `can_write_project`. Refused → `ActionRefusal('Project not found')`.
   3. `isAudioLibraryPath(projectId, path)`. The path must sit in *this* project's `assets/audio/` folder. Refused → refusal.
   4. `storage.exists('project-assets', path)`. If the object is missing → "The upload didn't finish. Try again."
   5. If a live row with the same `file_path` exists, return it. This makes the action idempotent.
   6. Insert the `audio_assets` row with the **user client** (RLS unchanged):
      - `file_url = storage.getPublicUrl(bucket, path)`, computed by the server; the client never sends a URL;
      - `provider = 'upload'`, `status = 'completed'`;
      - `metadata.source = 'uploaded'`, `metadata.contentType`.
   7. Return the asset.
5. The dialog calls `onSuccess(asset)`. The client puts the asset at the top of its list and calls `router.refresh()`. The grid shows "Theme" at once.

Why this is success: bytes never pass through a server action, so the 1 MB and 6 MB limits no longer apply. The storage write is gated by the KB-28 project-write rule and bound by KB-38's type and length signature. The row points only at a file inside the project's own folder.

## 7. Non-functional requirements

- **Size:** 50 MB per file, the same as today's promise. The route cap already exists (`UPLOAD_CONSTRAINTS.audio.maxSize`). The action body stays under 1 KB.
- **Latency:** one presign (~100 ms), one PUT (bandwidth-bound), one action (≤ 3 queries + 1 HEAD). There is no server-side buffering of file bytes, so server memory no longer grows with file size.
- **Security:** no new grants. The DB change only tightens (§14).
- **Accessibility:** the header Upload is a real `<button>` with a text label. The dialog is Radix, so focus is trapped and returns to the trigger. The error is text in the dialog.
- **Compatibility:**
  - Existing `audio-assets/music/…` rows and files keep working; they are read by URL.
  - New uploads land in `project-assets`.
- **Observability:** `audioAsset.uploadFile` logs keep the same names, plus refusal reasons (`not_writable`, `foreign_path`, `missing_object`).

## 9. Desired system behaviour

- **Upload:** click Upload → `canonicalAudioType(file)` → `audioLibraryUploadPath` → presign route (authz: `can_write_project_storage`; type, size, sign) → PUT to storage → `createUploadedAudioAssetAction`:
  1. authz (`can_write_project`);
  2. path in the project's folder;
  3. the object exists;
  4. idempotency;
  5. insert (RLS);
  6. on failure, delete the object.
  It returns the asset, and the client prepends it and refreshes.
- **Voice (sync):** action → `authorizeEpisodeTarget` (#337) → provider call → `recordVoiceSpend(target, cents)`. That function calls `increment_account_usage` with the **admin client**, using `target.accountId` and a server-computed cost.

## 10. High-level architecture

No new components. The work reuses the presign route (the one write gate, KB-28/KB-38) instead of the admin-client side door. Trust boundaries:
- the browser is untrusted;
- the presign route and action run as the caller (user client);
- storage is signed (R2) or policy-checked (Supabase);
- the budget RPC is reachable only from server code holding the service-role key.

## 12. End-to-end data flow

**File**
1. Source: the user's disk.
2. Validation: client type/size, then the route's type/size/path/authz, then the storage signature or policy.
3. Persisted in `project-assets` at a server-shaped key. No user text is in the key.
4. The `audio_assets.file_url` and `file_path` are derived by the server.
5. Read by the grid and card via the public URL.

Where it could go wrong:
- **Lost:** none. A failure before the row means nothing to show, and the user sees an error.
- **Orphaned:** PUT ok and action never reached (tab closed, network). The orphan is confined to the project's own folder and is writer-caused. It is KB-74/KB-20 retention territory; recorded in §30.
- **Duplicated:** a retry of the action with the same path returns the existing row. A retry of the whole flow creates a second path and row by design, the same as uploading twice.

**Usage**
- Source: provider-reported cost (`result.cost`) or the server-side estimate.
- Written with an atomic `UPDATE … SET x = x + n`.
- Can be lost only if the RPC errors. It is logged, and generation is not failed (unchanged policy).
- Worker double count on an SQS redelivery after success: over-counts, which is the safe direction for a cap (§30 R6).

## 16. API / event design

**New server action `createUploadedAudioAssetAction`**
- Input: §15.
- Output: `ActionResult<AudioAsset>` (via `returnRefusals`).
- Refusals, as values, per KB-6/production redaction:
  - "Project not found" (not a writer);
  - "Upload not found" (bad path or missing object);
  - "This file type isn't supported.";
  - "Couldn't save this upload" (insert failed).
- Auth: session required. Idempotent per `path`.

**Removed actions:**
- `uploadAudioFileAndCreateAssetAction` (the only UI caller moves);
- `uploadAudioAssetAction` (no caller).

## 17. State and lifecycle

- `audio_assets` uploaded rows are born `completed`, as today; there is no pending state.

## 18. Failure handling

See §4. Additionally:
- **Storage `exists` errors:** refuse with "Upload not found" and log. The user retries.
- **Admin delete of the orphan fails:** log `audioAsset.orphan_delete_failed` with the path. The user still sees the refusal.
- **Usage RPC fails:** log and continue (existing policy). A budget counter must not fail a paid-for generation.

## 19. Security

- **R3 closed.**
  - The admin-client storage write is removed.
  - Every audio-library write passes `can_write_project_storage` (route) and, on Supabase, the bucket policy.
  - On R2 the URL is signed for type and length.
  - The row write needs `can_write_project` in the action, and RLS still applies.
- **No arbitrary URLs.**
  - `file_url` is derived by the server.
  - `uploadAudioAssetAction`, which took any URL (KB-90 class), is deleted.
  - `updateAudioAssetAction` still accepts `fileUrl`. It is noted in §31 Q5, not fixed here.
- **No user text in keys:** `<ts>-<rand>.<ext>`. The name lives in the row.
- **KB-28/KB-38 are not loosened.**
  - No new bucket in the presign route.
  - No new path shape: `projects/{id}/assets/{type}/{file}` is existing.
  - No new MIME type in `project-assets`: `x-m4a`/`x-wav` are canonicalised client-side to types already on the list, and the PUT sends the canonical header.
  - `audio-assets` stays server-written only, and after this change nothing user-driven writes it.
- **KB-83: how granting is avoided, and why.** The lead asked that a fix granting the RPC to `authenticated` must not let a user decrement usage or write another account's row. **I propose not granting it at all.**
  - The RPC stays `service_role`-only.
  - The two server actions call it with the admin client *after* #337 authorises the target. The account id comes from the branded `LlmJobTarget`, not from the client, and the amount from the provider result or the server estimate.
  - So no browser can reach the RPC, and it cannot pick an account or an amount.
  - Defence in depth: the function refuses negative amounts even for the service role.
  - A grant to `authenticated` would need an account check *and* an amount check in SQL. Even then, any writer could call it directly with a huge positive amount and exhaust a team's budget. So the grant is strictly weaker.
  - **But decrementing is already possible without the RPC (R5):** the primary owner can `UPDATE accounts SET current_usage_cents = -1000` over PostgREST today. The fix therefore also adds the usage column (and, per Q1, the budget column) to `kit.protect_account_fields`. That is what makes "a user cannot decrement usage" true.
  - Another account's row is already unreachable: `accounts_self_update` is primary-owner-only, and the protect trigger refuses id changes.
- **Tenant isolation:** `isAudioLibraryPath` binds the row to its own project's folder.

## 29. Alternatives

| Decision | Alternatives | Why not |
|---|---|---|
| Direct-to-storage via presign | Raise `serverActions.bodySizeLimit` to 70 MB | It still loses to Lambda's 6 MB payload in production. It also buffers 50 MB × base64 in server memory, and keeps the admin-client write (R3). |
| Store in `project-assets/projects/{id}/assets/audio/` | Add `audio-assets` to the presign route with a new Supabase write policy and a project-bearing path | That changes KB-55's "server-written only" rule and adds a bucket and path shape to the write gate: more surface, a migration and pgTAP. Using `project-assets` reuses KB-28/KB-38 unchanged. Cost: new uploads live beside images and video, not in `audio-assets`. |
| Canonicalise `x-m4a`/`x-wav` on the client | Add the `x-` types to `project-assets` MIME and `ALLOWED_PROJECT_ASSET_TYPES` | That widens a KB-28 list. Canonicalising is invisible to the user and keeps the list as is. |
| Insert with the user client (RLS) | Insert with the admin client after `can_write_project` | That would also let personal owners in (KB-48), but it bypasses RLS for a table whose policies are KB-48's to fix. Kept narrow. |
| Budget RPC stays service-role, called with the admin client after authorisation | Grant to `authenticated` with SQL checks | See §19: strictly weaker (any writer can inflate), more SQL to test, and it does not fix R5 anyway. |
| Protect the columns in `protect_account_fields` | Column-level `REVOKE UPDATE (current_usage_cents)` | Makerkit grants table-wide UPDATE; column revokes do not subtract from a table grant. You would have to re-grant every other column, which is fragile. The trigger is the established place. |

## 34. Consistency pass

**Forward.** The user can't upload real tracks, can't upload twice, and doesn't see new ones. After the fix:
- bytes go browser → storage through the one write gate, and a tiny action writes an honest row;
- the header always offers Upload, and the list follows the server;
- tests drive exactly those steps, with 2 MB, twice, and no reload.

The spend path: the server authorises, then counts with a key the browser never holds. Users cannot lower the counter by any route.

**Reverse.** In production:
- the app will PUT to R2 under `projects/<id>/assets/audio/`, signed for type and length;
- it will insert one row per upload and call the RPC after voice generation;
- the user sees an upload that works at 50 MB, a second upload, and instant cards;
- the admin sees usage that rises.

That matches §1. Nothing a user or stranger could do before is newly allowed. The only rule changes tighten: the removed admin-client write, a negative-amount refusal, and protected usage columns.
