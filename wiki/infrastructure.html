☁️ AWS & Supabase Infrastructure

Why we use both AWS and Supabase, all Lambda functions, SQS queues, and the vendor-agnostic deployment strategy.

Think of it like a restaurant. Supabase is the recipe book (database) and the front door (authentication). AWS is the kitchen (Lambda workers doing heavy cooking), the delivery trucks (SQS queues), the storage room (S3), and the menu board outside (CloudFront CDN).

Why Both?

Each platform excels at different things. Instead of forcing one to do everything, we let each do what it does best.

⚡
Supabase
Developer experience & auth
  • PostgreSQL with RLS — Row-level security for multi-tenant data isolation
  • Connection pooling — Built-in PgBouncer, no infra to manage
  • OAuth / MFA / Magic Links — Auth out of the box
  • Free unlimited users — No per-seat costs on auth
🏗️
AWS
Heavy lifting & scale
  • Background jobs — SQS + Lambda for async processing
  • WebSocket tracking — DynamoDB for connection management
  • Video rendering — FFmpeg on Lambda with 2 GB RAM
  • CDN / DNS — CloudFront + Route53
  • Email at scale — SES for production volume

SQS Queue Architecture

Every queue has a matching dead-letter queue (DLQ) for failed messages. All DLQs retain messages for 14 days for debugging.

Queue Visibility Timeout Max Retries DLQ
email-queue 120 seconds 3 email-dlq
llm-queue 900 seconds (15 min) 2 llm-dlq
publish-queue 300 seconds (5 min) 3 publish-dlq
render-queue 900 seconds (15 min) 2 render-dlq
💡 Why Visibility Timeout Matters

The visibility timeout must be ≥ the Lambda timeout. If a Lambda takes 15 minutes to process a message but the queue's visibility timeout is only 5 minutes, SQS thinks the message failed and retries it — causing duplicate work. That's why llm-queue and render-queue both use 900-second timeouts.

Vendor Agnosticism

The platform uses provider abstraction packages so you can switch vendors by changing environment variables — zero code changes required.

Package Supported Providers
@kit/providers-database Supabase, PostgreSQL, MySQL
@kit/providers-storage Supabase Storage, S3, GCS, Azure Blob
@kit/providers-email Resend, SES, SendGrid, Nodemailer
@kit/providers-queue SQS, BullMQ
@kit/providers-cache Redis (Upstash, ElastiCache), Memory

Switching Providers

To switch from Supabase to a full AWS stack, just update your .env:

# Before: Supabase stack
DATABASE_PROVIDER=supabase
AUTH_PROVIDER=supabase
STORAGE_PROVIDER=supabase
EMAIL_PROVIDER=resend

# After: Full AWS stack
DATABASE_PROVIDER=postgresql
AUTH_PROVIDER=cognito
STORAGE_PROVIDER=s3
EMAIL_PROVIDER=ses
QUEUE_PROVIDER=sqs
CACHE_PROVIDER=redis
REDIS_URL=redis://upstash-or-elasticache...
✅ No Vendor Lock-In

Every provider abstraction follows the same interface pattern. Application code imports from @kit/providers-* and never touches vendor-specific SDKs directly. See SUPABASE_VENDOR_LOCKIN_REPORT.md for detailed migration strategies.

Monitoring & Alarms

4 CloudWatch alarms provide automated alerting for cost and operational anomalies:

Alarm Threshold What It Catches
Billing Alarm > $250 / month Runaway costs from misconfigured resources or traffic spikes
Lambda Invocations > 100K / hour Infinite retry loops, DDoS, or misconfigured triggers
DLQ Messages > 10 messages Persistent worker failures — jobs failing all retries
S3 Storage > 100 GB Storage growth anomaly — leaked temp files or upload spam
💡 Alarm Actions

All alarms send notifications to an SNS topic. In production, this connects to PagerDuty or Slack for on-call alerting. During development, alarms are email-only to the team lead.
