✨ Prompt Engine

The JSON-based LLM prompt management system: templates, variable injection, layered system prompts, output schemas, and the complete template inventory.

Think of prompts like recipe cards for the AI. Each card tells the AI exactly what role to play, what to think about, what format to answer in, and what variables to fill in. The Prompt Engine is the box that holds all 26 recipe cards and makes sure the AI follows each one perfectly.

JSON Template Structure

Every prompt template is a standalone .json file stored in packages/features/prompt-engine/src/prompts/. Here's the anatomy of a template:

{
  "slug": "story-generation",
  "name": "Story Generation",
  "version": 2,
  "category": "story-generation",
  "llm": {
    "provider": "gemini",
    "model": "gemini-3.1-flash-lite",
    "max_tokens": 16000,
    "temperature": 0.65
  },
  "system_prompts": [
    { "slug": "role",   "content": "...", "layer_type": "role",        "order": 1 },
    { "slug": "craft",  "content": "...", "layer_type": "constraints", "order": 2 }
  ],
  "user_prompt": "Write a story based on: {{premise}}\nCharacters: {{characters}}",
  "variables": {
    "premise": { "type": "text", "required": true }
  },
  "output": {
    "schema": { "type": "zod", "definition": "z.object({...})" }
  }
}
🏷️
Identity

slug, name, version, category — uniquely identify and organize each template. The slug is used for lookup at runtime.

🤖
LLM Config

Each template declares its own model, temperature, and token budget. Creative tasks use higher temperatures; analytical tasks use lower.

📐
Output Schema

A Zod schema definition that validates the LLM's response. If the output doesn't match, the engine retries automatically.

💡 Retry Logic

If the LLM response fails Zod validation, the engine automatically retries up to 3 times with the same prompt. Each retry is logged with its failure reason. If all attempts fail, the error bubbles up to the calling action with a structured error message.

System Prompt Layer Types

System prompts are composed of ordered layers. Each layer has a layer_type that defines its purpose. Layers are concatenated in order to form the complete system prompt sent to the LLM.

🎭
role

Defines the AI's persona and expertise. Always order: 1. Sets the foundational identity that shapes all subsequent responses.

⚖️
constraints

Hard rules the AI must follow — character locks, location restrictions, content policies. Violations cause pipeline failures.

📐
format

Output structure requirements — JSON schemas, field names, required properties. Works alongside the Zod validation layer.

📋
context

Dynamic project context — character registries, location data, episode history. Injected at runtime from the database.

👤
persona

Tone and voice modifiers — \"write like a showrunner\", \"use age-appropriate language\". Shapes stylistic output without changing factual content.

⚙️
system

Low-level engine instructions — retry behavior, error format, fallback handling. Rarely modified by prompt authors.

💡 Layer Composition

Layers are concatenated with double newlines between them. A template with layers [role, constraints, format] produces a single system prompt string: role_content + "\n\n" + constraints_content + "\n\n" + format_content. This modular approach lets you swap or update individual layers without touching the rest.

Variable Interpolation

Templates use {{variable_name}} mustache-style placeholders that are replaced at runtime. Variables come from four sources:

👤
User Input
Direct from the UI form

{{premise}}, {{number_of_ideas}}, {{target_duration}} — values the user explicitly provides when triggering a pipeline stage.

🗄️
Project Metadata
From database tables

{{characters}}, {{locations}}, {{genre}}, {{visual_style}} — automatically loaded from the project's metadata tables.

🔢
Calculated Values
From content scaling

{{target_word_count}}, {{scene_count}}, {{dialogue_lines}} — computed by calculateContentScaling() based on target duration.

📚
Canon Context
From episode history

{{previous_episodes}}, {{season_context}}, {{canon_facts}} — continuity data ensuring the AI doesn't contradict established story elements.

// Variable interpolation at runtime
const rendered = template.user_prompt
  .replace(/\{\{(\w+)\}\}/g, (_, key) => vars[key] ?? "");

// Example:
// "Write a story based on: {{premise}}"
// → "Write a story based on: Dante investigates a missing zoo animal"

Quality Gates

Quality gate templates score content across multiple weighted dimensions. The most complex gate is story-quality, which evaluates stories on 7 dimensions:

Score Thresholds

The weighted composite score determines the verdict:

✅
Pass ≥ 0.65

Story meets quality bar. Proceed to the next pipeline stage (Screenplay Conversion) without changes.

⚠️
Revise 0.50 – 0.64

Story has potential but needs targeted improvements. The quality report highlights which dimensions are dragging the score down.

🔴
Major Rewrite < 0.50

Fundamental issues. The user should return to the Story stage and regenerate with a refined premise or different concept.

// Quality score formula
const score =
  hook       × 0.20 +
  curiosity  × 0.20 +
  setupPayoff × 0.20 +
  emotional  × 0.15 +
  dialogue   × 0.10 +
  loopability × 0.10 +
  memorable  × 0.05;

// Verdict mapping
if (score >= 0.65) return "pass";
if (score >= 0.50) return "revise";
return "major_rewrite";

All LLM prompt executions are dispatched via AWS SQS to decouple the UI from long-running AI tasks. The platform defines 14 job types that flow through the queue:

⛔ Queue Ordering Matters

High-priority quality check jobs are always processed before standard generation jobs. This prevents a backlog of unchecked content from accumulating. The SQS FIFO queue uses message group IDs keyed to projectId, ensuring jobs for the same project execute in order.

📊 Queue Architecture

Each job message includes the template slug, interpolated variables, and a callback URL. When the Lambda worker processes a job, it:

  1. Loads the JSON template by slug
  2. Interpolates variables into the user prompt
  3. Assembles system prompt layers in order
  4. Calls the LLM provider with retry logic
  5. Validates the response against the Zod schema
  6. Writes the result to the database
  7. Sends a Realtime notification to the UI via WebSocket

Average processing time: 3–8 seconds for simple prompts, 15–45 seconds for complex multi-scene shot generation.
