🗄️ Database Schema

All tables, relationships, RLS policies, multi-tenancy, and the episode pipeline data model.

The database is a huge filing cabinet with labeled drawers. Each drawer has rules about who can open it — that's Row-Level Security (RLS). You can only see the files that belong to your team.

Core Tables

These are the primary tables that power the content creation pipeline. Every piece of content flows through this schema.

👤
accounts
User & team identity

Central identity table. Personal accounts mirror auth.users.id. Team accounts have their own IDs. All data hangs off account_id foreign keys.

📁
projects
Show / series container

A project represents a show (e.g., "Little Detective Dante"). Contains metadata JSONB with characters, locations, genre, visual style, and recurring elements.

📺
episodes
Individual content unit

One episode per video. Contains story_data and screenplay_data as JSONB columns. Tracks pipeline status through each stage (ideation → audio).

📸
shots
VEO 3.1 visual prompts

Each row is a single shot with its 7-component VEO prompt (subject, action, scene, style, dialogue, sounds, negative). Ordered by sequence_number.

💬
dialogue_lines
Character speech timeline

Individual lines of dialogue with character attribution, emotion tags, timing data, and TTS voice mapping. Linked to shots via shot_id.

🗂️
assets
Generated media files

References to generated videos, audio clips, images, and music tracks. Stores S3 URLs, file metadata, and generation status.

Entity Relationship Overview

-- Core relationship chain
accounts  1───∞  projects  1───∞  episodes  1───∞  shots
                                                  1───∞  dialogue_lines
                                                  1───∞  assets

-- Projects contain JSONB: metadata (characters, locations, etc.)

Canon Tables

The Continuity Canon System maintains narrative consistency across episodes. These tables are the "memory" of the series — immutable records of what happened and how the world changed.

📜
immutable_events
Permanent plot points

Events that cannot be retconned — character introductions, major reveals, relationship changes. Once written, these are append-only.

🧬
character_states
Character evolution tracking

Snapshot of each character's state at the end of an episode — emotional state, knowledge gained, relationships changed. Powers continuity injection.

🧵
narrative_threads
Running storylines

Multi-episode story arcs with status tracking (open, progressed, resolved). Ensures long-running mysteries and character arcs are maintained.

🌍
world_states
Universe consistency

Tracks the "state of the world" — new locations unlocked, objects discovered, rules established. Prevents contradictions across episodes.

📋
episode_summaries
SCORE framework data

Compact summaries using the SCORE framework — episodeSummary, sentimentScore, keyEvents. Injected into future prompts for continuity.

📊
state_deltas
Change log per episode

Diff-style records of what changed in each episode — new knowledge, relationship shifts, world modifications. Enables "what changed?" queries.

Infrastructure Tables

Supporting tables for job management, cost tracking, and content organization.

⚙️
generation_jobs

Tracks async generation tasks — video rendering, TTS generation, music composition. Status: pending → processing → completed / failed.

💰
llm_usage

Every LLM call is logged with provider, model, token counts, cost, and pipeline stage. Powers the cost dashboard and quota management.

📅
seasons

Groups episodes into seasons. Contains season-level metadata like arc descriptions, target episode count, and release schedule.

Multi-Tenancy & Row-Level Security

Every data table includes an account_id column. PostgreSQL Row-Level Security (RLS) ensures users can only access data belonging to their personal or team accounts.

How RLS Works

-- Example RLS policy on projects table
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own projects"
  ON projects
  FOR SELECT
  USING (
    account_id IN (
      -- Personal account
      auth.uid()
      UNION
      -- Team accounts the user belongs to
      SELECT account_id FROM accounts_memberships
      WHERE user_id = auth.uid()
    )
  );

Personal vs. Team Accounts

👤
Personal Accounts
auth.users.id = accounts.id

Created automatically on signup. The account ID is the user's auth ID. Solo creators use this for personal projects.

👥
Team Accounts
Separate ID, multiple members

Created explicitly by users. Members join via invitation with roles (owner, admin, member). All team data uses the team's account_id.

🔒 RLS Is Always On

RLS policies are enforced at the database level, not the application level. Even if application code has a bug that forgets to filter by account_id, PostgreSQL will silently exclude rows the user shouldn't see. This is defense-in-depth.

JSONB Design Decision

💡 Why story_data & screenplay_data are JSONB, Not Relational

The episodes table stores story_data and screenplay_data as JSONB columns instead of breaking them into normalized relational tables. This was a deliberate architectural choice:

✅
Why JSONB Works Here
  • Atomic writes: An entire story or screenplay is generated in one LLM call. Writing it as a single JSONB value is one INSERT — no multi-table transactions needed.
  • Schema flexibility: Story structures evolve frequently as prompts improve. JSONB avoids constant migrations.
  • Read pattern: Stories and screenplays are always read in full — never queried by individual scene. No need for per-row indexing.
  • Versioning: Easy to snapshot the entire document by copying the JSONB value. No need to version 15 related tables.
⚠️
Why Shots Are Relational
  • Individual operations: Shots are reordered, edited, regenerated, and deleted individually. Relational rows support this naturally.
  • Foreign keys: Dialogue lines and assets link to specific shots via shot_id. JSONB would require array index references — fragile.
  • Status tracking: Each shot has its own generation status (pending, generating, completed). Per-row status columns are cleaner than JSONB field updates.
  • RLS granularity: Row-level policies can be applied per-shot. JSONB arrays can't be partially restricted.

📐 The Rule of Thumb

Use JSONB when data is:

  • Written atomically (one big write)
  • Read in full (never queried by sub-field)
  • Schema is unstable or evolving
  • No foreign keys point into the structure

Use relational tables when data is:

  • Individually created, updated, or deleted
  • Referenced by other tables (FK targets)
  • Queried or filtered by specific fields
  • Needs per-row RLS or status tracking
