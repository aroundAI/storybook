⚖️ Product Decisions

The reasoning behind every major architectural, infrastructure, and product choice — so future developers understand why, not just what.

Every app has hundreds of choices: Which database? Which AI? How should episodes work? This page explains WHY each choice was made — like a diary of decisions so future developers understand the reasoning behind the code.

1. Why Supabase + AWS Hybrid?

Decision: Use Supabase for database + auth, and AWS for compute, queues, storage, CDN, and background processing.
🗄️
Supabase Does Best
Database & Authentication
  • PostgreSQL with Row-Level Security built in
  • Connection pooling — handles thousands of concurrent connections
  • Auth — OAuth, MFA, magic links, all free for unlimited users
  • Excellent DX — TypeScript types auto-generated from schema
  • Migrations — SQL-based, version controlled
⚡
AWS Does Best
Compute & Background Jobs
  • SQS + Lambda — reliable async job processing (Supabase has no queue system)
  • DynamoDB — WebSocket connection tracking at scale
  • Lambda + FFmpeg — server-side video rendering
  • CloudFront / Route53 — CDN and DNS management
  • SES — email at production scale
Result: Hybrid costs $37/month vs $95/month for full AWS. Best of both worlds.

2. Why JSON Prompt Templates?

Decision: Store all LLM prompts as JSON files with layered system prompts, not as hardcoded strings in TypeScript.
✅
JSON Templates
What We Chose
  • Editable without code deploys
  • Version tracked per template
  • LLM config (model, temperature) co-located with prompt
  • Layered system prompts are composable
  • Output schemas defined alongside prompts
  • Non-developers can modify prompts
❌
Hardcoded Strings
The Alternative
  • Requires code changes for prompt edits
  • No version tracking
  • Model config scattered across codebase
  • Can't compose layers
  • Difficult to A/B test prompts
  • Only developers can modify

3. Why JSONB for Story & Screenplay Data?

Decision: Store story_data and screenplay_data as JSONB columns in the episodes table, not as separate relational tables.

🔬 The Trade-off

FactorJSONB (✅ Chosen)Separate Tables
Schema EvolutionAdd fields without migrationsRequires migration for every change
Read PerformanceOne query gets all data (atomic)Multiple JOINs needed
Write PatternReplace entire documentGranular updates possible
QueryingPostgreSQL JSONB operatorsStandard SQL
FlexibilityNested structures, arrays, evolving schemasFixed column types

Why it works here: Story and screenplay data is always read/written as a whole unit. The schema evolves frequently as new fields are added (e.g., SCORE framework fields, viral scoring). JSONB avoids migration churn while maintaining query capability via PostgreSQL's excellent JSONB operators.

4. Why Scene-by-Scene Shot Generation?

Decision: Generate shots scene-by-scene with filtered context, not monolithically for the whole screenplay.
50-80%
Token Savings
Parallel
Processing
Higher
Quality

How It Works

  1. Build global context once — Character registry (15+ attributes per character) + location registry
  2. For each scene — filterContextForScene() extracts ONLY the characters and locations that appear in that scene
  3. Generate shots — LLM receives focused, relevant context instead of the entire screenplay
  4. Aggregate — Assign global sequence numbers across all scenes

Why monolithic fails: A 30-minute video has ~45 scenes. Sending ALL character descriptions and ALL location descriptions for every scene wastes 50-80% of the token budget on irrelevant context. Scene-by-scene gives the LLM exactly what it needs.

5. Why the Canon System?

Decision: Build a full Canon Management System with immutable events, character state tracking, narrative threads, and continuity validation — not just "pass the previous episode summary."
✅
Canon System
What We Built
  • Immutable events prevent contradictions (dead characters stay dead)
  • Token-budgeted context fits any LLM window (6,000 tokens = 15%)
  • 9 validation rules catch errors before they reach users
  • Content-type strategies (series vs movie vs ad vs documentary)
  • Sequel inheritance across movies
  • Change authorization (trigger + cost + constraint triplet)
❌
"Previous Summary" Approach
The Naive Alternative
  • Summary grows unbounded — exceeds token limits
  • No structured knowledge — can't check for contradictions
  • No death tracking — characters can be "resurrected" by accident
  • No thread tracking — plot lines get abandoned
  • One-size-fits-all — can't adapt to content types
  • No validation — errors only caught by humans

7. Why 7-Component VEO 3.1 Prompts?

Decision: Structure every shot prompt with 7 distinct components (Subject, Action, Scene, Style, Dialogue, Sounds, Negative) rather than freeform descriptions.

Why Each Component Exists

ComponentWhy Not Optional
Subject15+ attributes ensure character consistency across shots. Without it, the same character looks different in every clip.
ActionMicro-expressions and timing create believable animation. "Smiles" vs "corner of mouth twitches upward" — huge quality difference.
SceneProps, lighting, weather establish mood. Without it, shots feel disconnected.
StyleCamera lens (24mm vs 100mm), angle, movement map to emotions. A dolly-in creates intimacy; a wide shot creates isolation.
DialogueColon syntax (Dante: 'text') prevents VEO from rendering subtitles on screen.
SoundsSpecifying ambient + SFX prevents audio hallucinations (random noises VEO might add).
Negative"No subtitles, no captions, no watermarks" — explicit exclusion is essential for clean output.

8. Why Server Actions over API Routes?

Decision: Use Next.js Server Actions for all mutations instead of traditional REST API routes.
✅
Server Actions
  • Type-safe — Input/output types shared between client and server
  • Collocated — Action logic lives near the UI that calls it
  • No boilerplate — No route files, no fetch calls, no URL management
  • Zod validation — Built-in via enhanceAction() wrapper
  • Progressive enhancement — Works without JavaScript
❌
REST API Routes
  • Separate route files for every endpoint
  • Manual fetch calls with URL strings
  • Type safety requires extra tooling (tRPC, etc.)
  • Validation logic separated from handler
  • More files, more indirection

9. Why Turborepo Monorepo?

Decision: Use Turborepo with pnpm workspaces for a monorepo containing 20+ packages.
📦
Monorepo Benefits
  • Parallel builds — Turborepo builds independent packages simultaneously
  • Shared configs — TypeScript, ESLint, Prettier configs defined once in tooling/
  • Single lockfile — One pnpm-lock.yaml for all packages
  • Feature isolation — @kit/episodes, @kit/billing, @kit/auth etc. are independent packages
  • Atomic changes — Cross-package changes in a single commit
  • Disk efficient — pnpm's content-addressable storage deduplicates node_modules

10. Why Vendor-Agnostic Provider Abstraction?

Decision: Wrap every external service in a @kit/providers-* package so switching providers requires zero code changes.

Switch Providers via Environment Variables

# Switch from Supabase to full AWS stack
DATABASE_PROVIDER=postgresql  # Was: supabase
AUTH_PROVIDER=cognito          # Was: supabase
STORAGE_PROVIDER=s3            # Was: supabase
EMAIL_PROVIDER=ses             # Was: resend
QUEUE_PROVIDER=sqs
CACHE_PROVIDER=redis

Provider packages:

  • @kit/providers-database — Supabase, PostgreSQL, MySQL
  • @kit/providers-storage — Supabase Storage, S3, GCS, Azure Blob
  • @kit/providers-email — Resend, SES, SendGrid, Nodemailer
  • @kit/providers-queue — SQS, BullMQ
  • @kit/providers-cache — Redis (Upstash, ElastiCache), Memory
Why it matters: Vendor lock-in is a business risk. If Supabase raises prices or goes down, we can migrate to AWS Cognito + RDS without changing application code. If AWS becomes too expensive, we can move to Vercel. The abstraction layer makes this a configuration change, not a rewrite.
