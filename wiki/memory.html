🧠 Memory & Continuity System

How the app remembers everything across episodes: the Canon Management System, memory context builder, and continuity validator.

Imagine you're telling a bedtime story every night. You need to remember who's alive, who's friends, what secrets were revealed, and what's still a mystery. If you forget and bring back a character who died, the story breaks! This system is like a "memory notebook" that keeps track of everything — and tells the AI what it absolutely cannot contradict.

The 3 Layers of Canon

Not all facts are created equal. The Canon Management System classifies every piece of narrative truth into one of three layers, each with different persistence and enforcement rules.

💡 Why Only A + B?

Token budgets are finite (6,000 tokens for memory). Layer C details like "Dante sneezed in Episode 3" would waste precious context that should be spent on facts the AI cannot get wrong. The system aggressively prioritizes high-impact canon over flavor text.

🔒
Layer A Examples
Immutable — hard errors if violated
  • Professor Whiskers died in Ep 12
  • Dante learned Luna's secret identity
  • The Treehouse Lab was destroyed
  • Time travel is impossible in this world
⚡
Layer B Examples
Evolves forward, never reverses
  • Dante's trust in adults: low → medium
  • Luna's goal: "find her missing brother"
  • Emotional scar: betrayal by best friend
  • Motivation: prove he's not "just a kid"
💨
Layer C Examples
Ephemeral — not tracked
  • "Dante's favorite lunch is PB&J"
  • Background character at the park
  • Specific joke from Episode 3
  • Color of a one-time prop

Database Tables

The canon management system is backed by 6 specialized Postgres tables. Together they form a complete audit trail of every narrative fact, character state change, and world event across the entire series.

1. immutable_events

Layer A canon. Once written, these rows are never updated or deleted. The continuity validator checks every generation against this table.

Column Type Description
id uuid Primary key
project_id uuid FK → projects
event_type enum death | world_fact | relationship | timeline | ability_loss
event_key text Unique identifier e.g. "character:whiskers:death"
description text Human-readable description of the event
season integer Season number when event occurred
episode_number integer Episode number when event occurred
created_at timestamptz When the event was recorded

2. character_states

Layer B canon. Append-only — new rows are added for each state transition, linked via previous_state_id to form a chain. This creates a full history of how each character evolves.

Column Type Description
id uuid Primary key
character_id uuid FK → project_characters
state_type enum emotional | physical | relationship | knowledge | ability | location | goal
state_value jsonb Structured state data e.g. {"mood": "determined", "intensity": 0.8}
trigger_event text What caused this state change
cost text What was irreversibly lost (Change Authorization requirement)
new_constraints text[] New narrative constraints imposed by this change
previous_state_id uuid FK → character_states (self-referencing chain)
episode_id uuid FK → episodes
created_at timestamptz When this state was recorded

3. narrative_threads

Tracks every ongoing storyline — open mysteries, character arcs, romantic subplots. Each thread records its promises (what was set up) and payoffs (what was resolved), preventing dangling plotlines.

Column Type Description
id uuid Primary key
project_id uuid FK → projects
thread_name text e.g. "Mystery of the Golden Key"
thread_type enum plot | character | mystery | romantic | conflict | thematic
status enum open | progressed | resolved | abandoned
promises text[] Setup elements that need eventual payoff
payoffs text[] Resolved promises with episode references
episodes_touched integer[] Episode numbers where this thread appears
created_at timestamptz When the thread was created

4. world_states

Captures the current state of the story world — where things are, what time it is, what conflicts are active. Updated after each episode.

Column Type Description
id uuid Primary key
project_id uuid FK → projects
location text Primary location for this world state
time_period text In-universe timeline e.g. "3 months after the fire"
active_conflicts text[] Currently unresolved world-level tensions
atmosphere text Overall mood/tone of the world right now
constraints text[] Hard restrictions on what can happen
episode_id uuid FK → episodes (snapshot per episode)

5. episode_summaries

Compressed summaries of each episode, used by the memory context builder to give the LLM a "previously on…" window without exceeding the token budget.

Column Type Description
id uuid Primary key
episode_id uuid FK → episodes
plot_summary text 2–3 sentence plot overview
key_events text[] Major plot points affecting future episodes
character_changes jsonb Map of character → state changes this episode
sentiment_score float Emotional tone 0.0 (dark) → 1.0 (uplifting)
created_at timestamptz When this summary was generated

6. state_deltas

The audit trail. Every change to character or world state generates a delta record that captures the before/after and the reason. This enables debugging "why did the AI think X was true?"

Column Type Description
id uuid Primary key
entity_type enum character | world | thread
entity_id uuid FK → the changed entity
before_state jsonb Snapshot of the entity before the change
after_state jsonb Snapshot of the entity after the change
change_reason text Why this change happened (links to trigger event)
episode_id uuid FK → episodes
created_at timestamptz When the delta was recorded

Memory Context Builder

The Memory Context Builder is the bridge between the database and the LLM prompt. It loads all relevant canon data, compresses it to fit within a strict token budget, and formats it as structured text that the AI can parse reliably.

⚠️ Token Budget: 6,000 of 40,000

Memory context gets exactly 15% of the total 40K token context window = 6,000 tokens. This is a hard ceiling — exceeding it would crowd out the actual story generation instructions. The budget is distributed across categories to ensure balanced coverage.

Token Budget Allocation

How It Works

buildMemoryContext() loads all 5 data sources in parallel using Promise.all(), then each category is compressed and truncated to fit its budget slice:

// Simplified implementation
async function buildMemoryContext(projectId: string, episodeNumber: number) {
  const [
    immutableEvents,
    characterStates,
    worldStates,
    narrativeThreads,
    episodeSummaries
  ] = await Promise.all([
    loadImmutableEvents(projectId),
    loadLatestCharacterStates(projectId),
    loadCurrentWorldState(projectId),
    loadActiveThreads(projectId),
    loadRecentSummaries(projectId, episodeNumber, 5)
  ]);

  return formatMemoryContextForPrompt({
    immutableEvents,   // budget: 2,100 tokens
    characterStates,   // budget: 1,500 tokens
    worldStates,       // budget:   600 tokens
    narrativeThreads,  // budget:   900 tokens
    episodeSummaries   // budget:   900 tokens
  });
}

Content-Type Memory Strategies

Different content types demand different memory approaches. A 12-episode series needs deep continuity tracking; a standalone ad only needs a single scene's context. The system adapts automatically based on the project's content type.

Content Type Memory Horizon Decay Pattern Focus
Short Film Single episode No decay — everything retained Internal consistency only; no cross-episode tracking
Series Full season + previous season summaries Gradual — older episodes compressed more aggressively Character arcs, plot threads, immutable events
Documentary Full project No decay — factual accuracy critical Facts, dates, names, source attributions
Educational Current module + prerequisites Module-boundary decay — old modules summarized Concept dependencies, learning progression, terminology consistency
Ad Single scene N/A — no history Brand voice, product facts, legal constraints
News 24-hour window Aggressive — stale news replaced entirely Breaking facts, corrections, source freshness

Continuity Validator

The Continuity Validator runs after every LLM generation, scanning the output for canon violations before the content is stored. It operates as a rule engine with 9 validation rules, each targeting a specific class of continuity error.

⛔ Errors Block Output — Warnings Flag for Review

If any error-level rule fires, the generated content is rejected and the LLM is re-prompted with the violation details. warning rules flag content for human review. info rules are logged for analytics only.

Rule ID Name Severity Detects
CANON_001 Resurrection error Dead character appears alive or acts in the scene
CANON_002 State Reversal error Character state reverts to a previous value without authorization
CANON_003 Knowledge Violation warning Character knows something they haven't learned yet
CANON_004 Auth Missing warning State change lacks Change Authorization (cause + cost + constraint)
CANON_005 World Contradiction error Content contradicts established world facts (e.g., using time travel in a no-time-travel world)
CANON_006 Reference Violation warning References a resolved thread as still open, or an abandoned thread as active
CANON_007 Connectivity Failure info Episode doesn't reference or advance any existing narrative thread
CANON_008 Escalation Overflow warning Stakes escalate beyond what the world-state supports (e.g., "alien invasion" in a grounded show)
CANON_009 Tone Drift info Sentiment score deviates more than 0.4 from recent episode average

The validator works by comparing the generated content against all loaded memory context. For each rule, it runs a specialized check function:

// Simplified validator pipeline
async function validateContinuity(
  generatedContent: GeneratedStory,
  memoryContext: MemoryContext
): Promise<ValidationResult> {
  const violations = [];

  // Error-level rules — block on failure
  violations.push(...checkResurrection(generatedContent, memoryContext.immutableEvents));
  violations.push(...checkStateReversal(generatedContent, memoryContext.characterStates));
  violations.push(...checkWorldContradiction(generatedContent, memoryContext.worldStates));

  // Warning-level rules — flag for review
  violations.push(...checkKnowledgeViolation(generatedContent, memoryContext.characterStates));
  violations.push(...checkAuthMissing(generatedContent));
  violations.push(...checkReferenceViolation(generatedContent, memoryContext.narrativeThreads));
  violations.push(...checkEscalationOverflow(generatedContent, memoryContext.worldStates));

  // Info-level rules — log only
  violations.push(...checkConnectivity(generatedContent, memoryContext.narrativeThreads));
  violations.push(...checkToneDrift(generatedContent, memoryContext.episodeSummaries));

  const hasErrors = violations.some(v => v.severity === 'error');

  return {
    passed: !hasErrors,
    violations,
    // If failed, include violation details for re-prompting
    repromptContext: hasErrors ? buildRepromptContext(violations) : null
  };
}

LLM Role Orchestrator

Content doesn't flow through a single LLM call. Instead, the system uses a 4-role pipeline where each role has distinct permissions over canon data. This mirrors a real writers' room: the writer drafts, the editor checks facts, the stylist polishes tone.

🗺️
Planner
Outlines structure & arc
→
✍️
Writer
Generates narrative
→
🔍
Editor
Validates canon
→
🎨
Stylist
Polishes tone & voice

Role Permissions

Role Read Canon Write Canon Modify Story Reject Output Responsibility
🗺️ Planner ✅ Full ❌ Structure only ❌ Decides scene order, pacing, arc placement, thread advancement
✍️ Writer ✅ Full ✅ Proposes ✅ Full ❌ Generates dialogue, descriptions, action — proposes new canon entries
🔍 Editor ✅ Full ✅ Approves/Rejects ❌ Read-only ✅ Runs continuity validator, approves or rejects proposed canon changes
🎨 Stylist ✅ Layer C only ❌ Surface text only ❌ Adjusts word choice, sentence rhythm, age-appropriateness — never changes facts
💡 Why Separate Roles?

A single LLM call that tries to be creative and fact-check itself performs poorly at both. By splitting responsibilities, each call has a focused objective and a constrained set of permissions. The Editor can't accidentally rewrite the story; the Writer can't approve its own canon changes.

Sequel System

When a project is marked as a sequel (e.g., "Dante Movie 2"), it inherits canon from its parent project. This enables franchise-level continuity without duplicating data.

📥
What's Inherited
From parent project
  • All Layer A events — deaths, world facts (immutable)
  • Final character states — latest state of each character
  • Open narrative threads — unresolved plotlines carry forward
  • World state snapshot — the world as it was at the end
🚫
What's NOT Inherited
Stays with parent
  • Episode summaries — sequel starts fresh episode tracking
  • State deltas — audit trail stays with originating project
  • Resolved threads — no need to track completed arcs
  • Layer C details — ephemeral data doesn't transfer

Change Authorization

Not every state change is allowed. The system enforces a three-part authorization test for any Layer B (soft canon) modification. A state change must satisfy all three criteria or it's rejected by the Editor role.

🔗
(a) Caused by Prior Event

The change must be traceable to a specific event that happened in a previous or current episode. No spontaneous character transformations.

✅ Valid: "Dante becomes distrustful" → caused by betrayal in Ep 4

❌ Invalid: "Dante is suddenly confident" → no triggering event

💰
(b) Costs Something Irreversible

Every meaningful change must have a permanent cost. This prevents "free" character growth and ensures narrative weight.

✅ Valid: "Dante gains confidence" → cost: "lost his naivety, sees danger everywhere"

❌ Invalid: "Dante gains confidence" → cost: none specified

🔮
(c) Alters Future Constraints

The change must create new narrative constraints that affect future episodes. This ensures changes have lasting consequences.

✅ Valid: "Luna learns the truth" → constraint: "Can no longer pretend ignorance around adults"

❌ Invalid: "Luna learns the truth" → no future impact specified

// Change Authorization check in the Editor role
interface ChangeAuthorization {
  triggerEvent: string;     // (a) What caused this?
  cost: string;              // (b) What was permanently lost?
  newConstraints: string[];  // (c) What new rules does this create?
}

function isChangeAuthorized(auth: ChangeAuthorization): boolean {
  return (
    auth.triggerEvent.length > 0 &&
    auth.cost.length > 0 &&
    auth.newConstraints.length > 0
  );
}
