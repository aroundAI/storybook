Content Generation Pipeline

How a single sentence becomes a fully produced video — the 5-stage pipeline that orchestrates AI generation, background processing, and real-time delivery from ideation through to final audio.

Imagine you're making a cartoon. First, you think of an idea — like "a dog who solves mysteries." Then you write the whole story with a beginning, middle, and end. Next, you write out who says what, like a movie script. After that, you draw each camera shot — close-ups, wide angles, action scenes. And finally, you add voices and music so everything sounds real. That's exactly what this pipeline does, except the AI does all the hard work — you just type one sentence and it creates everything for you!

The 5-Stage Pipeline

Every piece of content flows through five sequential stages. Each stage takes the output of the previous one, enriches it with AI generation, and passes a richer data structure to the next:

💡
Ideation
Generate story concepts from a premise with viral scoring
→
📖
Story
Full narrative with 3-act structure, characters & arcs
→
🎬
Screenplay
Scene-by-scene dialogue, audio cues & emotional beats
→
📸
Visual Studio
VEO 3.1 optimized shot prompts with 7-component structure
→
🔊
Audio Studio
TTS dialogue, music tracks, sound effects & timeline
💡 Each stage is independently re-runnable

Users can go back to any stage and regenerate without losing downstream work. The system tracks which stages have been completed and which need refresh via the episode status field.

Data Flow: What Goes In & Out

Each pipeline stage transforms specific inputs into structured outputs, stored in dedicated database locations:

Stage Input Output Database
💡 Ideation Premise (string), episode context, series history Array of idea objects — title, logline, themes, hook, viral scoring generation_jobs
📖 Story Title, logline, duration (60–7200s), contentStyle, characters, threadCandidates Full narrative (fullStory), 3-act breakdown, SCORE data, character arcs episodes.story_data (JSONB)
🎬 Screenplay Story text, target duration, dialogue style Scenes array with dialogue, audio cues, emotionalPeak, hookOut episodes.screenplay_data (JSONB), dialogue_lines
📸 Shot List Screenplay scenes, shot duration, video provider config VEO 3.1 prompts per shot — subject, action, scene, style, dialogue, sounds, negative shots table
🔊 Audio Dialogue lines, screenplay audio cues, voice profiles TTS audio files, music tracks, sound effects, complete timeline audio_* tables

For a 5-minute episode of "Little Detective Dante", the pipeline produces roughly: 750 words of story, 7 scenes in the screenplay, ~41 dialogue lines, and ~43 camera shots — each with a full VEO 3.1 prompt containing subject descriptions, camera movements, lighting, and sound design.

Users can move back to adjacent stages at any time. For example, from storyboard you can go back to story to revise the narrative. Going back does not automatically delete downstream data — the user can choose to keep or regenerate it.

🔒 Optimistic Locking

Every status transition is protected by optimistic locking via a version column. This prevents two users (or two tabs) from making conflicting edits simultaneously. See the section below for details.

Duration-Based Scaling

Content requirements scale automatically based on the target episode duration. The system uses a scaling function that calculates word count, scene count, dialogue lines, and shot count proportionally:

Duration Words Scenes Dialogue Lines Shots
1 min ~150 2 ~8 ~9
5 min ~750 ~7 ~41 ~43
30 min ~4,500 ~45 ~248 ~257
2 hrs ~18,000 ~180 ~660 ~1,028

Content Styles

The scaling function accepts a contentStyle parameter that adjusts the dialogue-to-action ratio:

💬
Dialogue-Heavy
×1.5 dialogue multiplier

More talking, character interactions, emotional beats. Ideal for drama, comedy, and interview-style content. Results in ~60 dialogue lines for a 5-min episode.

⚖️
Balanced
×1.0 base multiplier

Equal mix of dialogue and visual storytelling. The default mode for most series. Good for adventure, mystery, and educational content.

💥
Action-Heavy
×0.5 dialogue multiplier

More visual sequences, chase scenes, physical comedy. Fewer words, more shots. Results in ~20 dialogue lines for a 5-min episode.

Generation Job Pattern

Every AI generation in the pipeline follows the same asynchronous processing pattern. This ensures reliability, scalability, and real-time user feedback:

How Every Generation Works

The platform never calls an LLM synchronously from a user request. Instead, every generation follows this pattern:

The 6-Step Flow

  1. User clicks "Generate" — triggers a Next.js Server Action
  2. Server Action creates a generation_jobs row — with status 'pending', the job type (e.g., 'story', 'screenplay'), and all input parameters as JSONB
  3. queueLlmJob() sends the job to AWS SQS — the response returns immediately to the user with the job ID
  4. Lambda worker picks up the job — loads the prompt template from @kit/prompt-engine, injects variables, calls the LLM via @kit/llm
  5. Results are stored in the database — the appropriate table is updated (e.g., episodes.story_data, shots table)
  6. WebSocket pushes the result to the user — the UI updates in real-time without polling

Failure Handling

  • If the Lambda worker fails, SQS automatically retries up to 3 times with exponential backoff
  • After 3 failures, the message is moved to a Dead Letter Queue (DLQ)
  • The generation_jobs row is updated with status 'failed' and an error_message
  • The user sees a failure notification via WebSocket and can retry manually
// Simplified generation job flow
async function generateStoryAction(episodeId: string, params: StoryParams) {
  // 1. Create job record
  const job = await createGenerationJob({
    type: 'story-generation',
    episodeId,
    params,
    status: 'pending',
  });

  // 2. Queue to SQS (returns immediately)
  await queueLlmJob({
    jobId: job.id,
    queue: 'llm-generation',
  });

  // 3. User sees "generating..." state via WebSocket
  return { jobId: job.id, status: 'queued' };
}

Optimistic Locking

In a collaborative editing environment — or even when a single user has multiple tabs open — concurrent writes can cause data corruption. The platform uses optimistic locking to prevent this:

🔒 How Optimistic Locking Works

Every episodes row has a version integer column, auto-incremented by a database trigger on every update. When the UI loads an episode, it captures the current version. Before saving any changes, the mutation checks:

-- Database trigger: auto-increment version on every update
CREATE FUNCTION increment_version() RETURNS TRIGGER AS $$
BEGIN
  NEW.version := OLD.version + 1;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Applied to the episodes table
CREATE TRIGGER episodes_version_trigger
  BEFORE UPDATE ON episodes
  FOR EACH ROW EXECUTE FUNCTION increment_version();
// Every mutation checks version before saving
async function updateEpisodeStory(episodeId: string, data: StoryData, expectedVersion: number) {
  const { data: result, error } = await supabase
    .from('episodes')
    .update({ story_data: data })
    .eq('id', episodeId)
    .eq('version', expectedVersion)  // ← KEY: only update if version matches
    .select();

  if (!result?.length) {
    throw new Error('Episode was modified by another session. Please refresh and try again.');
  }
}
✅ When It Works

User A loads episode (version 5), edits story, saves → version becomes 6. Clean update, no conflict.

❌ When It Catches Conflicts

User A and B both load version 5. A saves first (→ version 6). B tries to save with version 5 → rejected. B must refresh and retry.
